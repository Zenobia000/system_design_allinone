## 參、逐頁 Storyboard

格式說明：
- **IN → OUT**：觀眾進入這頁時相信什麼 → 離開時相信什麼（AST）
- **版面**：實際放上投影片的文字（保持稀疏，血肉在講稿）
- **視覺**：visual intent，不是裝飾指示
- **講稿**：speaker intent——台上怎麼講、在哪裡停

### 第 0 幕 · 冷開場與結論（P1–P5）

#### P1 · 封面
- **版面**：`AI 時代的取捨與決策樹` ／ 副標：`何時 Vibe、何時 SDD、何時放手讓 AI 跑`
- **視覺**：chapter 深色底，只有標題。
- **講稿**：不自我介紹超過 20 秒，直接進 P2。

#### P2 · 「Spec 寫了五千行，AI 一次生成了整個系統。」
- **IN**：我用 AI coding 用得很順 → **OUT**：規模一大，事情會壞得很難看
- **版面**（敘事體，置中）：
  > Spec 寫了 5,000 行。
  > AI 一次生成了整個語音聊天系統。
  >
  > 上線壞掉那天——
  > 沒有人分得出，錯在模型、介面，還是實作。
- **視覺**：純文字頁，無圖。小字註：YC 團隊真實案例。
- **講稿**：唸完停三秒。問現場：「有人寫過一千行以上的 spec 嗎？」

#### P3 · 更可怕的是：測試全綠，邏輯是錯的
- **IN**：錯誤 = 紅字、exception → **OUT**：最貴的錯誤發生在綠燈底下
- **版面**（三行遞進）：
  > 以前的錯：`SyntaxError` ——一跑就炸。
  > 現在的錯：架構合理、API 能跑、測試全綠。
  > 但 domain logic 是錯的——三個月後才有人發現。
- **視覺**：一排綠色 ✓，中間一個不顯眼的 ✗。
- **講稿**：「錯誤沒有變少，它變安靜了。」

#### P4 · AI Engineering 是乘法，模型只是乘數
- **IN**：期待聽到工具技巧 → **OUT**：這場在講工程系統，不是講工具
- **版面**（全頁一句）：
  > **AI Engineering = 問題定義 × 環境 × 回饋 × 驗證**
  >
  > 模型只是乘數。
  > 乘在 0.2 的系統上，十倍速度 = 十倍速製造錯誤。
- **視覺**：公式置中，無其他元素。
- **講稿**：「今天整場，就講這一行。後面全是證據。」

#### P5 · 今天給四支釣竿，不給魚
- **IN**：等著抄工具清單 → **OUT**：我會帶走四個「以後問自己的問題」
- **版面**：
  > 🎣① 什麼時候該從 Vibe 升級成 SDD？
  > 🎣② 這份文件到底該不該寫？
  > 🎣③ AI 犯錯，該修哪一層？
  > 🎣④ 什麼時候可以放手讓它自己跑？
- **視覺**：四行問句，無框。
- **講稿**：「工具清單在最後一頁 QR，不用抄筆記。」

### 第一幕 · 為什麼判斷變稀缺（P6–P7）

#### P6 · AI 不會停下來問你——它會很有自信地做完錯的事
- **IN**：AI 犯錯是幻覺問題，模型變強就好 → **OUT**：是自主權跑贏監督的系統問題
- **版面**（數據三行）：
  > 41% 的真實 coding session，已經是「AI 寫幾乎全部 code」。
  > AI 產生的 code，真正留在 commit 裡的不到一半。
  > 主動開口問「我理解對嗎？」的——幾乎沒有。
  >
  > *Autonomy 正在跑得比 Oversight 快。*
- **視覺**：三個數字放大，出處小字（Stanford SWE-chat, 2026）。
- **講稿**：「而且模型越強，這件事越危險——因為錯得越像對的。」

#### P7 · 只有證據是真相
- **IN**：測試過了 = 做完了 → **OUT**：Done 需要證據，不是宣告
- **版面**（否定式排列，逐條浮現）：
  > Spec 寫了 ≠ 真相
  > AI 說完成 ≠ 真相
  > Code 能編譯 ≠ 真相
  > 測試是綠的 ≠ 真相
  >
  > **No Evidence, No Done.**
- **視覺**：前四行灰色，最後一行主色。
- **講稿**：「這五個字，是後面所有決策樹的地基。」

### 第二幕 · 何時 Vibe 何時 SDD——以及文件的真相（P8–P15）

#### P8 · Vibe 和 SDD 不是路線之爭，是同一條曲線的兩端
- **IN**：Vibe coding 派 vs 文件派，選邊站 → **OUT**：橫軸是確定性，不是信仰
- **版面**：一條水平軸——左端「不知道答案：Vibe（推翻很便宜）」、右端「知道答案：Spec / Test / Contract（修改很貴）」；軸下標註：`橫軸是確定性，不是時間`。
- **視覺**：單軸圖，手繪感箭頭。
- **講稿**：「越不知道答案，越應該 Vibe；越確定的東西，越應該釘死。」

#### P9 · 文件量跟確定性走，不跟時間走
- **IN**：專案越久文件越多是自然律 → **OUT**：文件量 = f(確定性 × 風險 × 依賴人數)
- **版面**：四階段階梯——
  > Explore（Free Vibe）：PROJECT.md 一頁就夠
  > Stabilize：小 Spec + Acceptance Test
  > Systemize：Architecture + Contract + ADR
  > Productize：PRD / QA / Runbook
- **視覺**：往右上的階梯，每階標最小文件集。
- **講稿**：「注意每一階寫的是『最小』——不是升到這階就把全套補齊。」

#### P10 · 🎣① 升級看四個訊號，不看週數
- **IN**：什麼時候進 SDD？大概第三週吧 → **OUT**：看系統發出的訊號，不看日曆
- **版面**：
  > 1. 出現「不能隨便改」的東西（API 被前端用了、DB 有真資料了）
  > 2. 長出第二個模組（A 該傳什麼給 B？）
  > 3. 同一種 regression 重複發生（修 A 壞 B）
  > 4. 你忘記當初為什麼這樣設計
- **視覺**：四個訊號燈，由綠轉黃。
- **講稿**：每個訊號配一句現場例子；「中兩個以上，你已經欠文件債了。」

#### P11 · 九個角色，其實是九份文件
- **IN**：SDLC 角色 = 九種職位 → **OUT**：角色的本質是產出，不是頭銜
- **版面**（一張表，每行一句）：
  > PM → PRD ｜ UX → User Flow ｜ SA → SRS
  > Architect → ADR ｜ SD → 模組設計 ｜ DBA → Schema
  > Dev → Code ｜ QA → Test Plan ｜ DevOps → Runbook
- **視覺**：九宮格或三欄表，角色淡、產出深（視覺重心在文件）。
- **講稿**：「三十年來我們以為在雇九個人，其實是在買九份文件。」

#### P12 · AI 合併了人，留下了產出
- **IN**：AI 會取代這些角色 → **OUT**：被合併的是人力，留下來的是產出鏈
- **版面**：
  > 九個人 → 兩三個人。
  > 九份產出 → 一份都沒少。
  >
  > **那——九份都要寫嗎？**
- **視覺**：上排九個人形淡出成三個；下排九份文件保持不動。
- **講稿**：問句停住，不回答，直接翻下一頁。（本幕唯一的懸念鉤）

#### P13 · 文件不是多就有用【核心觀點】
- **IN**：文件寫得齊 = 工程成熟 → **OUT**：可驗證性才是價值，頁數不是
- **版面**：
  > Waterfall 怎麼死的？文件成本 > 溝通成本。
  >
  > 文件只有三種：
  > **描述**——寫完就開始過期
  > **規格**——可以被驗證
  > **證據**——已經被驗證
  >
  > 值得維護的，只有後兩種。
- **視覺**：三欄，左欄灰、中右欄主色。
- **講稿**：「AI 時代死得更快——描述性文件塞進 context，是在污染 AI 的世界觀。」

#### P14 · 🎣② 這個知識不寫下來，AI 下次會重新猜一次嗎？
- **IN**：該寫哪些文件要看方法論 → **OUT**：一個問題就能判斷
- **版面**：
  > 會重新猜 → **固化**：
  > 　需求 → Spec ｜ 行為 → Test ｜ 介面 → Contract ｜ 決策 → ADR
  > 不會 → 不要寫。
- **視覺**：一個 yes/no 分岔的迷你決策樹。
- **講稿**：「這一問淘汰掉的文件，比任何模板產生的都多。」

#### P15 · 能當真相的東西，不要寫成散文
- **IN**：規格 = 一份 Markdown → **OUT**：規格的終極型態是可執行
- **版面**（左右對照）：
  > 左（會過期）：「API request 應包含 name、email、age」
  > 右（是真相）：
  > ```python
  > class UserRequest(BaseModel):
  >     name: str
  >     email: EmailStr
  >     age: int
  > ```
- **視覺**：左灰右亮，中間一個箭頭。
- **講稿**：「左邊那句話三個月後就是謊言；右邊那段 code 永遠不會。SDD ≠ Markdown Driven Development。」

### 第三幕 · 開發流程的演進（P16–P18）

#### P16 · 開發迴圈變成六步
- **IN**：AI 開發 = prompt → code → 再 prompt → **OUT**：有六步迴圈，human gate 在頭尾
- **版面**：環形圖 `Frame → Challenge → Contract → Execute → Verify → Learn`，Frame/Challenge/Learn 標 🧑（human gate），Execute/Verify 標 🤖。
- **視覺**：環形，不是瀑布——強調 Learn 回到 Frame。
- **講稿**：「注意 AI 只出現在兩步。剩下四步，就是九角色濃縮之後剩下的判斷。」（此處呼應 P11-12，一句帶過即可）

#### P17 · 🎣③ AI 犯錯，修系統不修 prompt
- **IN**：AI 錯了 → 罵它 → 重打 prompt → **OUT**：每個錯都該沉澱到某一層防線
- **版面**：
  > AI 犯錯時，只問一句：
  > **「這類錯，下次怎麼被自動擋住？」**
  >
  > Test？ Lint？ Architecture rule？ Context？ CI？
  >
  > *Failure becomes Harness.*
- **視覺**：一個錯誤往下落，被五層網其中一層接住。
- **講稿**：「重打 prompt 是把同一個錯再租一次；寫進 harness 是買斷它。」

#### P18 · 沒寫進 repo 的決策，等於沒發生過
- **IN**:repo 是放 code 的地方 → **OUT**：repo 是 AI 的長期記憶與世界模型
- **版面**：
  > Slack 裡的共識、會議室的決定、你腦袋裡的原因——
  > 對下一個開新 context 的 AI 而言：
  > **從、來、沒、發、生、過。**
  >
  > 沉澱：ADR ｜ Schema ｜ Contract ｜ Test ｜ Runbook
- **視覺**：左側對話泡泡淡出，右側 repo 目錄樹實心。
- **講稿**：「你不是在寫文件給同事，你是在餵記憶給下一個 agent。」

### 第四幕 · 自動化的極致（P19–P22）

#### P19 · 那……什麼時候可以去喝咖啡？
- **IN**：（前三幕的紀律有點累）→ **OUT**：期待被吊起來
- **版面**：全頁只有這一句 + ☕
- **視覺**：留白呼吸頁。
- **講稿**：「這是今天大家真正想問的問題，對吧。」停兩秒。

#### P20 · 自主權不是模型給的，是驗證掙來的
- **IN**：模型夠聰明就能放手 → **OUT**：Autonomy is earned by verification
- **版面**：
  > 錯誤答案：模型夠聰明，就可以放手。
  >
  > **Autonomy is earned by verification.**
  > 自主權不是模型給的，是驗證掙來的。
- **視覺**：上句劃掉（strikethrough），下句放大。
- **講稿**：「模型 IQ 決定它能跑多快；你的驗證系統決定它能跑多遠。」

#### P21 · 多數人卡在 L2，卻想直接跳 L7
- **IN**：自動化 = 開/關 兩檔 → **OUT**：是一把八階的梯子，一階一階掙
- **版面**：階梯 `L0 解釋 → L1 建議 → L2 改碼人審 → L3 跑測試 → L4 自動修復迴圈 → L5 長程任務 → L6 多 Agent → L7 生產環境`，在 L2 標「👈 多數人在這」、L7 標「👈 多數人想去這」。
- **視覺**：階梯圖，L2→L7 之間畫一條被劃掉的虛線捷徑。
- **講稿**：「中間那條虛線，就是五千行 Spec 那家人走的路。」（呼應 P2，收第一個伏筆）

#### P22 · 🎣④ 四個 Yes 才升一級
- **版面**：
  > 升級前，回答四個問題：
  > 我 **觀察** 得到它在做什麼嗎？
  > 我 **評估** 得到它做對了嗎？
  > 我 **停** 得下來嗎？
  > 我 **滾** 得回去嗎？
  >
  > 四個 Yes，才升一級。
- **IN**：想放手但不知道標準 → **OUT**：有一張可以立刻用的檢查表
- **視覺**：四個核取方塊。
- **講稿**：「注意這四問跟模型多強完全無關——全部在問你的系統。」
