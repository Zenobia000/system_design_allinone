# Myth vs Truth
## *打破「架構師必須是超級工程師」的迷思*


---


## MYTH · WHY

<span class="kicker">SECTION 1 · MYTH</span>

# 為何「架構師 = 最強工程師」是錯的？

<br>

<div class="highlight">

**架構師不是技術競賽的冠軍。**
是把「商業目標」拆解成「技術決策」的人。

技術強不強只是入場券，**判斷力**才是核心競爭力。

</div>

<br>

- 業界錯誤期待：架構師應該秒解所有技術問題
- 真實工作：80% 時間在開會、寫文件、做選型
- 寫 code 的時間反而比資深開發者少

> Source: `S1_Slides.pdf` · §架構師日常時間分配

## MYTH · 對照表

# 五個常見迷思

| 迷思 | 真相 |
|------|------|
| 架構師必須代碼最強 | 不必，但要看得懂並能評審 |
| 架構師決定所有技術細節 | 不，定方向與護欄即可 |
| 架構師越資深越會寫 code | 越資深越少寫 code |
| 架構師獨自設計整個系統 | 與 PM、Dev、Ops、QA 共創 |
| 架構師有最終裁決權 | 多數時候靠**說服**而非命令 |

<br>

<div class="alert">

**反模式**：升上架構師後仍緊抓 code review，拒絕授權。團隊會走光。

</div>

> Source: `S2_Slides.pdf` · §角色定位常見誤區

## MYTH · TRADE-OFF

# 升上去之前先想清楚

<div class="tradeoff">
  <div class="pro">
    <h3>架構師的吸引力</h3>
    <ul>
      <li>影響範圍大</li>
      <li>薪資成長曲線陡</li>
      <li>越老越值錢</li>
      <li>可橫向發展到 CTO</li>
      <li>知識可跨產業轉移</li>
    </ul>
  </div>
  <div class="con">
    <h3>架構師的代價</h3>
    <ul>
      <li>失去純粹 coding 的快樂</li>
      <li>背壓力大（決策影響整個團隊）</li>
      <li>會議與文件佔 60-70%</li>
      <li>沒實權但要負責任</li>
      <li>政治成分明顯增加</li>
    </ul>
  </div>
</div>

<span class="muted">**先問自己**：喜歡寫 code、不愛開會、討厭文件——這條路不適合你。</span>

> Source: 整合 `S1-S3.pdf` + `Software_Architecture_Warrior_Monk` 對照

## MYTH · AI 時代的真相

<span class="kicker">AI ERA</span>

# Copilot 能寫 80% 的 code

<div class="highlight">

**那剩下 20% 是什麼？**
就是「該寫哪個 function」、「該不該做這個 feature」。
這 20% 決定剩下 80% 是創造價值還是製造技術債。

</div>

<br>

- AI 把「實作能力」變成 commodity
- 稀缺的變成「判斷能力」與「商業翻譯能力」
- **架構師的價值反而被 AI 放大**：能用 AI 加速設計疊代

<br>

<span class="muted">「AI 寫得出完美的函式，但無法決定該寫哪個函式來賺錢。」</span>
