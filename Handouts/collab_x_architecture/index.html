Part I

Why：為什麼需要進化

第 0 章

AI 帶來的變化與學習心態

AI 改變了工程師的工作重心，也改變了學習時成就感的來源。本章先對齊為什麼要進化，以及用什麼心態學。

0.1

生成成本與驗證成本的落差

AI 產生程式碼幾乎不花時間，但判斷這段程式對不對，仍然要讀懂需求、讀懂程式、實際驗證。兩者之間的落差，就是工程師接下來的主要工作。

  • 重點撰寫程式碼的成本大幅下降，驗證是否正確的成本卻沒有
  • 圖表兩條曲線，生成成本下降、驗證成本持平
  • 講者備註過去的瓶頸是寫不完，現在的瓶頸是分不出對錯
0.2

錯誤型態的轉變

AI 很少寫錯語法，錯誤多半出在需求理解與設計判斷，而且這類錯誤測試不一定抓得到。重點因此從「會不會寫」轉到「能不能發現寫錯了」。

  • 重點語法錯誤變少，需求誤解與架構錯誤變多
  • 情境測試全數通過，業務邏輯卻是錯的
0.3

工程師價值的位移

需求定義與結果驗收的價值上升，中間的實作被 AI 大量接手。學習時間應該多花在這兩端。

  • 重點價值往上游（定義）與下游（驗收）移動，中段的實作被壓平
  • 圖表微笑曲線
0.4

學軟體開發真正在培養的能力

程式語言會換、工具會換，但邏輯思考、抽象轉具象、找出規格、建構系統這四種能力會一直有用。AI 可以替你打字，不能替你練這些能力。

  • 重點程式語言只是載體，要練的是背後的四種能力
  • 邏輯思考：把問題拆成步驟、條件與例外
  • 抽象轉具象：把「想要更方便」變成畫面、流程與資料
  • 找出規格：知道怎樣算完成、邊界在哪裡
  • 建構系統：把零件組成能長期運作的整體
  • 講者備註AI 能替你打字，不能替你練這四種能力；這四種能力剛好對應 PM、SA、Architect、QA 的工作（第 3 章）
0.5

成就感的轉移：從破關到解決別人的問題

AI 讓破關變容易，成就感自然變少。把目標從寫出程式改成解決某個人的問題，關卡就從 Bug 變成真實世界的需求，成就感會回來，而且更大。

  • 情境以前 Debug 三小時終於跑起來，像打贏魔王；現在 AI 三十秒給出答案，破關的感覺不見了
  • 重點成就感的來源要從「我寫出來了」轉成「我解決了誰的問題」
  • 野心放遠：以前一個人只做得出小工具，現在做得出完整產品
  • 把目光放在人身上：使用者、同事、身邊正被某個問題卡住的人
  • 講者備註關卡沒有消失，是變大了；以前的魔王是 Bug，現在的魔王是真實世界的問題
0.6

刻意反問「為什麼」

AI 給答案時，追問為什麼、有什麼替代做法、什麼情況會出錯。不問的話，你只是在轉貼答案，離開 AI 就不會做，也判斷不了答案對不對。

  • 重點只拿答案、不問為什麼，就像拿著翻譯機卻學不會英文
  • 翻譯機的問題：當下能溝通，但離開翻譯機就開不了口，也判斷不了翻譯對不對
  • 習慣：AI 每給一次解法，至少追問三題
    • 為什麼選這個做法？
    • 還有哪些做法，差在哪裡？
    • 這個做法在什麼情況下會出錯？
  • 目的：把 AI 的答案變成自己的判斷力
  • 講者備註看不懂的東西，你就無法驗收；而驗收是 AI 時代工程師最重要的工作
  • 對應8.2 AI 不擅長的工作、9.3 提問設計

Part II

What：軟體工程基礎

第 1 章

System Architecture 全景

先用六大組成建立系統的全貌，後面所有角色與決策都會對應到這張圖。

1.1

系統的六大組成

任何系統都能拆成介面、入口、服務、資料、外部整合、維運六塊。先記住這張圖，後面每個角色、每個決策都能對應到其中一塊。

  • ① Presentation Layer：使用者介面（App、Web、管理後台）
  • ② Entry Layer：API Gateway、Authentication、Rate Limiting
  • ③ Service Layer：業務邏輯（訂單、支付、推薦）
  • ④ Data Layer：Database、Cache、Message Queue、Object Storage、Vector DB
  • ⑤ External Integration：金流、地圖、LLM API
  • ⑥ Operations Layer：部署、監控、告警、成本控管
1.2

架構設計的三個核心問題

架構設計只在回答三件事：怎麼切、怎麼連、壞了怎麼辦。遇到任何架構討論，都可以先問它在回答哪一件。

  • 重點架構就是決定六大組成如何切分、如何連接、故障時如何應對
  • 切分：Monolith 或 Microservices
  • 連接：同步呼叫（REST、gRPC）或非同步事件（Message Queue）
  • 故障：單一元件失效時，其餘部分是否仍能運作
1.3

AI 應用的架構定位

LLM 在架構上就是一個又慢又貴、輸出不保證正確的外部服務。用設計外部相依的方式對待它：快取、逾時、降級。

  • 重點AI 應用仍是軟體系統，LLM 只是第⑤類的外部相依服務
  • 講者備註LLM 的三個特性——慢、貴、輸出不保證正確

第 2 章

開發方法論：Waterfall 與 Agile

兩種方法論的差別在於變更成本付在哪個階段，理解這點才能判斷 AI 時代的流程該怎麼調整。

2.1

Waterfall

Waterfall 先把需求和設計想清楚再動手，適合需求穩定、錯了代價很高的系統。缺點是文件成本高，而且要到最後才知道需求有沒有錯。

  • 流程：需求 → 設計 → 實作 → 測試 → 部署，逐階段完成
  • 適用：需求穩定、錯誤代價高（醫療、金融核心系統、硬體）
  • 限制：文件成本高於溝通成本；完成後才發現需求錯誤
2.2

Agile

Agile 用短週期交付可用的增量，靠回饋修正方向，適合需求不確定的產品。常見的問題是省略文件與架構，技術債越積越多。

  • 流程：短週期迭代 → 可用增量 → 回饋 → 調整
  • 適用：需求不確定、需要快速驗證市場
  • 限制：常演變成缺乏文件與架構，Technical Debt 持續累積
2.3

兩者的本質差異

兩者都要付變更成本，差別只在時間點：Waterfall 付在前期的文件，Agile 分攤在每次迭代的重構。選方法論，就是選在哪裡付這筆成本。

  • 重點差別在於「變更成本」付在哪個階段
  • 圖表Waterfall 前期集中投入文件，Agile 分攤到每次迭代的重構
2.4

AI 時代的影響

AI 讓迭代成本降得更低，但驗證沒有變便宜。迭代越快，越需要規格和測試撐住，否則只是更快累積錯誤。

  • 重點迭代成本更低，驗證成本相對更高
  • 講者備註一天迭代十次卻沒有規格與測試，等於以十倍速累積錯誤

第 3 章

現代分工模式

九個角色各自降低一種不確定性，也各自負責一份產出，這是理解 AI 時代分工的起點。

3.1

SDLC 的九個角色

九個角色對應九種不確定性，從價值、體驗、行為一路到維運。知道每個角色在降低哪一種不確定性，就知道缺了誰會出什麼問題。

  • 重點每個角色負責降低一種不確定性
  • PM：做什麼、為什麼做（價值）
  • UX/UI：使用者如何操作（體驗）
  • SA（System Analyst）：系統必須做到什麼、範圍到哪裡（行為與邊界）
  • Architect：系統如何達成品質要求（結構與品質）
  • SD（System Designer）：模組如何切分與串接（介面）
  • DBA：資料如何儲存（資料）
  • Developer：實際實作（實作）
  • QA：是否做對（驗證）
  • DevOps / SRE：上線後是否穩定（維運）
3.2

角色與產出的對應

每個角色負責一份關鍵產出，下游依賴上游的產出工作。看產出鏈，比看組織圖更能看懂一個團隊怎麼協作。

  • PM → PRD
  • UX/UI → User Flow、Wireframe
  • SA → SRS
  • Architect → SAD、ADR
  • SD → SDS、API Spec
  • DBA → Schema、Migration
  • Developer → Source Code
  • QA → Test Plan、Test Report
  • DevOps / SRE → Runbook、SLO
  • 重點每個角色都是一份關鍵產出的負責人
3.3

SA 與 Architect 的分工

SA 從外部定義系統要做什麼、範圍到哪裡；Architect 從內部決定怎麼做才能達到品質要求。SA 缺席時，架構師可能替錯誤的需求設計出很好的架構。

  • 重點SA 管「做什麼、做到哪」，Architect 管「怎麼做得夠好」
  • SA：業務語言 → 可實作的流程與規格；界定系統邊界
  • Architect：品質屬性 → 結構與技術決策；管理整體品質
  • 圖表SA 看黑箱（外部行為），Architect 看白箱（內部結構）
  • 講者備註SA 缺席，Architect 會替錯誤的需求設計出很好的架構

第 4 章

規格文件體系與 V-Model

四份規格文件由粗到細拆解需求，V-Model 讓每一層規格都有對應的測試。

4.1

規格文件鏈：PRD → SRS → SAD → SDS

四份文件回答四個不同層次的問題，從業務語言逐步轉成技術語言。每往下一層，粒度更細，讀者也更接近實作者。

  • 重點每份文件回答一個問題，粒度由粗到細、語言由業務到技術
  • 圖表四份文件由上而下的分解鏈，每層標註負責角色與讀者
4.2

PRD（Product Requirements Document）

PRD 說明為什麼做、為誰做、做什麼，以及不做什麼。它用業務語言寫給全團隊看，是後續所有規格的起點。

  • 回答：為什麼做、為誰做、做什麼
  • 負責：PM；讀者：全團隊、決策者
  • 內容：商業目標、Persona、User Story、範圍與不做的事、Success Metrics
  • 語言：業務語言
4.3

SRS（Software Requirements Specification）

SRS 只描述系統的外部行為，不談實作。每條需求都有編號、明確且可驗證；把同一條需求在 PRD 與 SRS 的寫法並排，最能看出兩者的差異。

  • 回答：系統必須做到什麼（只描述外部行為，不描述實作）
  • 負責：SA；讀者：Architect、SD、QA
  • 內容：系統邊界、Functional Requirement（編號）、NFR、業務規則、Use Case、外部介面
  • 參考標準：ISO/IEC/IEEE 29148
  • 好需求的特性：明確、單一、可行、可驗證、可追溯
  • 圖表同一需求在 PRD 與 SRS 的寫法對照
    • PRD：使用者可以快速重複上次的訂單
    • SRS：FR-012 系統應於首頁顯示最近 3 筆訂單；點擊後 2 秒內帶入購物車；餐廳休息中時顯示替代推薦
4.4

SAD（Software Architecture Document）

SAD 說明系統的整體結構如何滿足品質要求，內容包含架構視圖、品質情境、ADR 與風險，是 Architect 的主要產出。

  • 回答：系統的整體結構如何滿足品質要求
  • 負責：Architect；讀者：SD、DevOps、技術決策者
  • 內容：架構視圖（C4 Model）、Quality Attribute Scenario、ADR、技術選型、風險
  • 參考標準：ISO/IEC/IEEE 42010
4.5

SDS（Software Design Specification）

SDS 細到每個模組怎麼實作：API、Schema、序列圖與關鍵演算法。Developer 和 QA 直接依據它工作。

  • 回答：每個模組如何實作
  • 負責：SD、DBA；讀者：Developer、QA
  • 內容：模組設計、API Spec、Schema、Sequence Diagram、關鍵演算法
  • 參考標準：IEEE 1016
4.6

V-Model：每份規格都對應一層測試

V 字左側逐層拆解規格，右側逐層驗證，每一層測試的依據就是同一層的規格。規格寫得不清楚，那一層的測試也寫不出來。

  • 重點左側逐層拆解規格，右側逐層驗證；測試依據就是同層的規格
  • 圖表V 字形，左右對應
  • PRD ↔ Acceptance Test：是否解決了業務問題（使用者與 PM 驗收）
  • SRS ↔ System Test：系統整體是否符合功能與 NFR
  • SAD ↔ Integration Test：模組與服務之間的介面是否正確
  • SDS ↔ Unit Test：單一模組的邏輯是否正確
  • 參考：ISTQB 測試層級；測試流程標準 ISO/IEC/IEEE 29119
4.7

Verification 與 Validation

Verification 檢查有沒有照規格做，Validation 檢查做出來的東西是不是使用者真正要的。AI 的產出常通過前者，卻過不了後者。

  • Verification：是否依規格正確實作（Build the product right）
  • Validation：是否做出使用者真正需要的東西（Build the right product）
  • 講者備註AI 產出的程式常通過 Verification，卻過不了 Validation
4.8

Shift Left：測試在寫規格時就開始設計

每寫完一份規格，就寫出同一層的測試案例。寫不出測試案例，代表規格還不夠明確，而這時修改的成本最低。

  • 重點左側文件完成的當下，就寫出右側同層的測試案例
  • 講者備註規格寫不出測試案例，代表規格本身還不夠明確
4.9

Traceability Matrix

從商業目標一路追到需求編號、架構元件與測試案例。需求一改，就能立即找出受影響的設計與測試。

  • 重點每個商業目標都能追到需求、設計、程式碼與測試
  • 圖表PRD 目標 → FR 編號 → 架構元件 → 測試案例

Part III

What：AI 基礎

第 5 章

LLM 運作原理

從 Token、參數量、Context Window 到 Agent，說明模型如何運作，以及為什麼輸入決定輸出。

5.1

Next-Token Prediction

模型每次都在預測下一個最可能出現的 Token，輸出的是機率上最合理的內容，不保證事實正確。這是所有 AI 陷阱的根源。

  • 重點輸出的是機率上最可能的內容，不保證正確
5.2

Token 與計價

API 依輸入與輸出的 Token 數計費，輸出通常比輸入貴好幾倍。Agent 會反覆讀取大量程式碼，成本可能是一般對話的數百倍，設計前要先估算。

  • Token 是模型處理文字的最小單位，API 依輸入與輸出 Token 數計費
  • 輸出 Token 單價通常是輸入的 3–5 倍
  • 講者備註一次 Agent 任務常反覆讀取整個 Repository，Token 用量可能是單次對話的數百倍
5.3

參數量（Parameters）

參數量代表模型的容量，但不等於實際能力。MoE 模型總參數很大，每次只啟用一部分；比較模型時，看實測結果與價格比較可靠。

  • 重點參數量代表模型的容量，不等於實際表現
  • Dense Model：每次推論動用全部參數
  • MoE（Mixture of Experts）：總參數很大，每次只啟用一部分（例：總參數 1.6T、啟用 49B）
  • 講者備註美國主要廠商多半不公開參數量，比較模型應看實測結果與價格
5.4

Context Window

模型只知道放進 Context 的資訊。視窗再大，內容太長時中段的資訊仍容易被忽略，所以放進去的東西要精選。

  • 重點模型只知道放進 Context 的資訊
  • 主流旗艦模型已達 1M Token（約可放入一個中型 Repository 的重點程式碼）
  • 視窗大不等於記得牢：內容越長，中段資訊越容易被忽略
  • 未寫進 Prompt、Repository 或文件的內容，對模型而言不存在
5.5

無狀態（Stateless）

模型不會記得上一次對話。需要長期保留的知識，要寫在 Repository、規格或 Rule 檔案裡，每次重新提供給它。

  • 重點每次對話都從零開始
  • 長期記憶必須存放在外部：Repository、Spec、Rule 檔案（如 CLAUDE.md、AGENTS.md）
5.6

非確定性（Non-deterministic）

同樣的輸入可能得到不同的輸出，所以不能靠「上次它做對了」保證品質，需要能重複執行的 Test、Schema 與 Eval。

  • 重點相同輸入不保證相同輸出
  • 因此需要可重複執行的驗證機制：Test、Schema、Eval
5.7

Prompt 如何驅動模型

模型看到的是 System Prompt、Rule、工具定義、檢索資料、對話紀錄與提問組合起來的整份輸入。要改善輸出，最有效的通常是改善放進去的脈絡。

  • 重點模型看到的是一整份組合後的輸入，Prompt 只是其中一部分
  • 組成：System Prompt → Rule 檔案 → 工具定義 → 檢索到的資料與程式碼 → 對話紀錄 → 本次提問
  • 輸入決定輸出的機率分布：給什麼脈絡，就得到什麼方向的答案
  • 圖表Context 組裝示意，標示每一層由誰提供
5.8

Agent 的組成

Agent 是 LLM 加上工具與迴圈，會自己讀檔、執行指令、看結果再決定下一步。它能實際動手，犯錯時的影響也更大。

  • 重點Agent = LLM + Tools + Loop
  • 圖表推理 → 呼叫工具 → 觀察結果 → 再推理
  • 講者備註能執行操作的 AI，犯錯時也會實際執行錯誤操作

盤點 AI Coding 的應用情境與工具型態。選工具之前，先決定要給 AI 多少自主權。

常見的 AI Coding 應用

AI Coding 除了補全程式碼，還包括除錯、重構、Code Review、測試、文件與理解舊系統。先知道有哪些用途，才能判斷哪些工作適合交出去。

第 8 章

AI 的能力邊界

從 LLM 的運作原理推出 AI 擅長與不擅長的事，並為每個常見陷阱配上防範機制。

8.1

AI 擅長的工作

有大量既有範例的工作，AI 做得又快又好，例如樣板程式、格式轉換、列舉方案。這類工作可以放心交出去。

  • 重點有大量既有範例可參考的工作
  • Boilerplate：CRUD、設定檔、測試案例擴充
  • 轉換：需求轉草稿、程式碼轉文件、語言間轉譯
  • 廣度：列舉方案、找出遺漏、摘要大量資料
8.2

AI 不擅長的工作

缺乏範例、需要業務脈絡、或需要有人承擔後果的工作，AI 做不好。取捨與決策仍然由人負責。

  • 重點缺乏範例，或需要承擔後果的工作
  • 未明說的需求與業務脈絡
  • 取捨與決策（模型不承擔後果）
  • 跨大量檔案、長時間的一致性
  • 辨識自身的不確定（不會主動表示「我不確定」）
8.3

人機分工原則

人負責定義問題與驗收結果，AI 負責中間的產出。兩端都由人把關，AI 的錯誤才不會流到正式環境。

  • 重點人負責定義與驗收，AI 負責產出
  • 圖表定義（人）→ 產出（AI）→ 驗收（人）
8.4

常見陷阱與防範機制

每個常見陷阱都有對應的防範機制，例如關鍵測試由人撰寫、一次只給一個任務、規格寫進 Repository。把這張表變成團隊的日常習慣。

  • Hallucination：不存在的 API 或套件 → 鎖定版本，以實際執行結果為準
  • 測試通過但邏輯錯誤 → 關鍵測試案例由人撰寫，AI 負責擴充
  • 修改測試以符合程式碼 → 測試與實作分開產生，Review Diff
  • 修改範圍失控 → 一次一個任務，維持小幅度 Diff
  • Context 汙染與遺失 → 規格寫入 Repository，不依賴對話紀錄
  • 安全漏洞（Hardcoded Secret、Injection）→ CI 自動掃描、最小權限原則
  • 過度自信的錯誤回答 → No Evidence, No Done

第 9 章

與 AI 溝通：從提示詞到提問設計

技巧型提示詞正在失效，真正決定品質的是提供的脈絡、提問的方式與表達的邏輯。

9.1

Prompt Engineering 的重要性正在下降

模型已經能理解一般指令，角色扮演咒語這類技巧效果越來越小。現在該花力氣的地方，是提供脈絡與設計問題。

  • 重點模型已能理解一般指令，技巧型提示詞的效果越來越小
  • 失效的技巧：角色扮演咒語、「深呼吸一步一步想」、威脅或利誘
  • 仍然有效的：提供正確的脈絡、清楚的目標、可檢查的標準
  • 講者備註重點從「怎麼說」轉為「給什麼」與「問什麼」
9.2

Context Engineering：給對的資料

答案的品質上限由放進 Context 的資料決定。放入相關的程式碼、規格與限制，排除無關內容，反覆需要的脈絡寫成 Rule 檔案。

  • 重點答案的品質上限，取決於放進 Context 的資料
  • 放入：相關程式碼、規格、錯誤訊息、範例、限制條件
  • 排除：無關檔案、過期文件、冗長的對話紀錄
  • 固化：反覆需要的脈絡寫進 Rule 檔案與規格，不要每次重打
9.3

提問設計：問對問題

好問題包含目的、背景、約束、驗收標準與輸出形式。問不清楚通常代表自己還沒想清楚，設計問題其實就是在寫規格。

  • 重點問題本身就是規格；問不清楚，代表自己還沒想清楚
  • 好問題的五個要素
    • 目的：要解決什麼問題、為什麼
    • 背景：目前的狀態、已經試過什麼
    • 約束：不能改什麼、必須用什麼
    • 驗收標準：怎樣算完成
    • 輸出形式：要程式碼、方案比較，還是決策建議
  • 技巧：先請 AI 反問不清楚的地方；一次只問一件事；要求列出假設
  • 圖表同一需求的壞問題與好問題對照
9.4

邏輯表達力與語言

中文常省略主詞、代名詞指涉不清，容易讓模型誤解。用條列、數字與英文專有名詞表達，可以明顯減少歧義。

  • 重點AI 的輸出品質，受限於提問者的邏輯表達能力
  • 中文常見的歧義：省略主詞、代名詞指涉不清、修飾範圍不明
  • 改善方式：主詞明確、條列步驟、數字取代形容詞、專有名詞用英文
  • 模型訓練資料以英文為主，技術名詞使用英文較不易誤解
  • 講者備註會寫規格的人，就會問問題；寫作能力就是新的程式能力
9.5

AI 味從何而來

模型傾向選擇最常見的用詞，又經過偏好訓練與安全調校，輸出因此變得平均、客套、面面俱到，這就是 AI 味的來源。

  • 重點AI 味是訓練方式留下的統計痕跡
  • 機率傾向：選擇最常見的用詞與句型，結果趨於平均
  • 偏好訓練（RLHF）：傾向討好、面面俱到、語氣保守
  • 安全調校：過多的免責聲明與客套話
  • 翻譯腔：中文輸出帶有英文句構
9.6

AI 味的常見特徵

文字的 AI 味包括重複總結、制式句型、誇大形容與過量符號；程式碼的 AI 味包括過度註解、把錯誤吞掉與不必要的抽象。

  • 文字
    • 開場複述問題、結尾重複總結
    • 三段式排比、「不是……而是……」句型
    • 誇大的形容：「至關重要」「全方位」「賦能」
    • 過量的破折號、粗體、條列與表情符號
  • 程式碼
    • 每一行都有註解，且只是重述程式碼
    • 過度防禦：到處 try/except，把錯誤吞掉
    • 不必要的抽象層與設定參數
    • 冗長的 Docstring 與範例
9.7

消除 AI 味的方法

提供自己的範例、列出禁用清單、指定讀者與語氣，並要求具體內容。最後仍由人修改，刪掉不影響決策的句子。

  • 提供自己的寫作範例，讓模型模仿風格
  • 明確列出禁用詞與禁用句型
  • 指定讀者與語氣（例：資深工程師、只講結論）
  • 要求具體：數字、例子、檔案位置
  • 程式碼：以既有程式碼為風格基準，由 Linter 與 Code Review 把關
  • 最後一哩由人修改：刪除不影響決策的每一句

第 10 章

AI Builder 的工作模型

把 Vibe Coding、SDD、角色整併與文件鏈收成 AI Builder 的工作模型。

10.1

Vibe Coding

Vibe Coding 以對話推進開發，適合探索與做 Prototype。缺點是沒有單一的真相來源，改到第二次就容易失控。

  • 定義：以對話驅動開發，邊做邊調整
  • 適用：探索期、Prototype、需求尚不明確
  • 限制：缺乏 Single Source of Truth，第二次修改就開始失控
10.2

SDD（Spec-Driven Development）

SDD 先寫規格，AI 依規格實作，再用規格驗收。前期較慢，適合需求明確、多人依賴、錯了很貴的情況。

  • 定義：先撰寫規格，AI 依規格實作，再以規格驗收
  • 適用：需求已知、多人相依、錯誤代價高
  • 限制：前期投入較多，規格本身也可能有誤
10.3

以確定性決定開發方式

兩種做法是同一條曲線的兩端，依確定性切換。還不知道的先用 Vibe 探索，確定了就寫成規格，有人依賴就正式化。

  • 重點兩者並非二選一，而是同一條曲線的兩端，橫軸是確定性
  • 圖表Explore → Stabilize → Systemize → Productize
  • 原則：未知的先 Vibe，已知的就固化，有人相依就正式化
  • 對應：Vibe Coding 近似極端的 Agile；SDD 近似輕量的 Waterfall
10.4

AI 時代的角色整併

AI 讓一個人能做好幾個角色的事，但每個角色負責的判斷一項都不能少。人少了，每個人要承擔的判斷反而更多。

  • 重點人力可以整併，產出不能省略
  • 講者備註九人團隊可能縮減為兩三人，但九種判斷仍需有人負責
10.5

AI 時代的文件鏈

規格是 Agent 的輸入，測試是 Agent 的驗收標準。把規格寫成 Gherkin、OpenAPI、Schema 這類可執行的格式，Agent 的產出才能自動驗證。

  • 重點規格是 Agent 的輸入，測試是 Agent 的驗收標準
  • SRS 的驗收條件 → Gherkin（Given / When / Then）
  • SAD 的品質要求 → ADR 與自動化檢查（Fitness Function）
  • SDS → OpenAPI、Schema，可直接由工具驗證
  • 每個 Agent 任務都引用 FR 編號，產出才能追溯
10.6

AI Builder（Orchestrator）的定義

AI Builder 知道何時該調度哪個角色的能力，並為產出負責。每次調度都要想清楚三件事：給什麼輸入、交給誰做、怎麼驗收。

  • 重點知道何時調度哪個角色的能力，並負責驗收產出
  • 調度三要素：輸入（Input）→ 執行者（Skill / Agent）→ 驗收標準（Acceptance）

Part IV

What：架構設計心法

第 11 章

架構師思維

架構師的價值在於決策、翻譯與全局思考，並對系統品質負責。

11.1

架構師的三個核心價值

架構師的價值在於問對為什麼、把商業需求翻成技術指標，以及從整體做判斷。寫程式的能力是基本功。

  • 決策權重大於撰寫程式碼：架構師是系統的 Why 守護者
  • 商業翻譯重於技術實作：把「提升使用者體驗」翻譯成「P99 < 200ms」
  • 全局思考重於局部最佳化：單一服務未必最佳，整體系統更穩定
11.2

架構師是品質的負責人

功能決定系統能做什麼，品質決定系統能運作多久。SA 定義要做什麼，Architect 負責做到多好。

  • 重點功能決定系統做什麼，品質決定系統能活多久
  • SA 交付「做什麼」，Architect 負責「做到多好」並守住品質底線
11.3

從 Individual Contributor 到 Multiplier

個人貢獻者自己解決問題，架構師讓很多人更有效率地解決問題。AI Builder 則是以 Agent 為團隊的 Multiplier。

  • 個人貢獻者：我解決問題
  • 團隊領導者：我的團隊解決問題
  • 架構師：多個團隊因我的設計而更有效率地解決問題
  • 講者備註AI Builder 就是以 Agent 為團隊的 Multiplier
11.4

對不同對象使用不同語言

同一個設計，對 CEO 講成本與風險，對 PM 講時程與範圍，對工程師講技術與開發體驗。溝通時先想對方關心什麼。

  • CEO：成本與風險（「此設計可降低 30% 雲端成本」）
  • PM：時程與範圍（「新功能上線時間可縮短」）
  • 開發團隊：技術與開發體驗（「可移除大量 Boilerplate」）

第 12 章

需求量化與約束條件

把形容詞換成數字，並認清約束條件往往比功能需求更能決定架構。

12.1

拒絕形容詞

「要快」「要穩」無法設計，也無法驗收。每個形容詞都要換成數字，例如 P95 < 200ms、99.9% 可用性。

  • 重點每個形容詞都必須對應一個數字
  • 「要快」→ P95 < 200ms；「要穩」→ 99.9% Availability
12.2

NFR 五大指標

效能、負載、資料量、可用性與併發是最常用的五個 NFR 指標，每個都有量化方式與經驗公式。

  • Performance：P95 / P99 Latency、Throughput
  • Load：尖峰規劃 = 平時負載 × 預期倍數 × 1.5 安全係數
  • Data Volume：五年資料成長模型
  • Availability：99.9% ≈ 每年停機 8.8 小時；99.99% ≈ 52.6 分鐘
  • Concurrency：同時在線人數與行為模式
12.3

約束條件的否決權

時程、團隊技能與維運能力，往往比功能需求更能決定架構。沒有人能維運的系統，技術再好也不該選。

  • 重點約束條件往往比功能需求更具決定性
  • Deadline：時程是第一驅動力
  • Skill：團隊不熟悉的技術，再快也不該選
  • Operations：無人能維運的系統，上線之日就是故障之始
12.4

理想架構與務實架構

理想架構是沒有限制時的最佳解，務實架構是現實約束下的可行解。架構師要說得清楚兩者的差距，以及為什麼選後者。

  • 圖表理想方案 vs. 受約束後的方案（例：Kafka → Managed Queue，因缺乏 SRE 人力）

第 13 章

架構設計流程與決策紀錄

七步流程讓架構設計可以重複執行，ADR 讓決策理由不會消失。

13.1

七步架構設計流程

從需求理解、概念設計、技術選型、詳細設計、驗證評審、實施指導到演進優化，七個步驟讓架構設計可以重複執行，不必全靠個人經驗。

  • ① Understand：以 5W2H 將模糊需求轉為技術指標
  • ② Conceptualize：以 DDD 建立領域模型，暫不涉及技術
  • ③ Select：以 TCO 評估技術選型
  • ④ Design：產出 C4 Model、API Spec、安全設計
  • ⑤ Validate：Architecture Review，找出風險
  • ⑥ Guide：以 Code Review 與範例程式碼確保實作不偏離
  • ⑦ Evolve：依運行數據持續改善，以 Strangler Fig 汰換舊系統
13.2

ADR（Architecture Decision Record）

ADR 記錄當時的背景、做了什麼決定、會帶來什麼後果，以及放棄了哪些方案。決策錯了可以改，理由不見了才是重構時最大的風險。

  • 重點錯誤的決策可以修正，消失的決策理由會讓重構失控
  • 三要素：Context、Decision、Consequences（含被否決的方案）
13.3

TCO 與 Technical Debt

開發成本只占總成本的一小部分，維運與技術債占了大部分。技術債要有計畫地還，並以漸進替換取代全面重寫。

  • TCO 冰山：可見的開發成本約兩成，維運與債務占多數
  • Technical Debt 是為了短期交付而借的長期貸款
  • 還債策略：固定約 20% 工時處理債務；以 Strangler Fig 漸進替換，避免全面重寫
13.4

七步流程與 Agent Pipeline

七個步驟可以直接拆成七個 Agent，彼此傳遞結構化資料。這是把架構流程交給 Agent 協作的具體做法。

  • 重點七步流程可以直接拆成七個 Agent 節點，以結構化 Context 串接
  • 圖表需求分析 → 領域建模 → 技術策略 → 系統設計 → 風險評估 → 技術主管 → 演進守護
  • 講者備註Agent 之間傳遞結構化資料（JSON / YAML），不傳遞自然語言

第 14 章

品質屬性與分散式設計原則

品質屬性要寫成可測試的情境，再依業務排出優先順序做取捨。

14.1

品質屬性模型

ISO/IEC 25010 提供一套完整的品質屬性清單。討論品質時使用同一套詞彙，才不會各說各話。

  • 參考標準：ISO/IEC 25010
  • Functional Suitability、Performance Efficiency、Compatibility、Usability
  • Reliability、Security、Maintainability、Portability
  • 講者備註2023 版新增 Safety，並調整部分名稱
14.2

Quality Attribute Scenario

品質要求要寫成「在什麼情況下、發生什麼事、系統怎麼回應、怎麼量測」的情境，才能拿來設計與測試。

  • 重點品質要求要寫成可測試的情境，而不是口號
  • 格式：來源 → 刺激 → 環境 → 回應 → 量測
  • 範例：午餐尖峰 5 倍流量時，推薦 API 的 P95 < 500ms
14.3

品質屬性的取捨

品質屬性之間互相牽制，不可能全部最大化。先選出對業務最重要的前三個，其餘的有意識地妥協。

  • 重點完美的系統不存在，先選出對業務最重要的前三個品質屬性
  • 提升 Security 常犧牲 Performance；提升 Consistency 常降低 Availability
14.4

CAP Theorem 與資料庫選擇

網路分區一定會發生，分散式系統只能在一致性與可用性之間取捨。交易資料選 ACID，大規模擴展選 BASE。

  • 網路分區必然發生時，只能在 CP 與 AP 之間選擇
  • ACID：交易關鍵資料（PostgreSQL、MySQL）
  • BASE：大規模擴展（Cassandra、DynamoDB）
  • Cache：Redis
14.5

分散式系統五大原則

鬆散耦合、無狀態、快取、通訊方式與可觀測性，是分散式系統穩定運作的五個基本原則。

  • Loose Coupling：避免共用資料庫與循環相依
  • Stateless：伺服器不保存 Session，才能水平擴展
  • Caching：以空間換取時間（Browser → CDN → Application → Database）
  • Communication：同步即時但耦合高；非同步可靠且能緩衝尖峰流量
  • Observability：Metrics、Logs、Traces
14.6

Four Golden Signals

延遲、流量、錯誤率與飽和度，是監控任何服務時最先要看的四個指標。

  • Latency、Traffic、Errors、Saturation

第 15 章

架構模式的選擇

架構模式是工具，預設從簡單開始，真的遇到瓶頸才升級。

15.1

Layered Architecture 與 Clean Architecture

分層架構把展示、應用、領域與基礎設施分開，所有相依都指向領域層。外層技術更換時，核心業務規則不必跟著改。

  • Presentation → Application → Domain → Infrastructure
  • 重點相依方向一律指向 Domain，核心業務規則不感知外層技術
15.2

Design Pattern 是人與 AI 的共同語言

用 Pattern 名稱下指令，例如「用 Strategy 處理不同的推薦策略」，比描述一大段行為更精準。Pattern 是人與 AI 共用的詞彙。

  • 重點以 Pattern 名稱下指令，比描述行為更精準
  • 常用：Factory、Builder、Facade、Adapter、Repository、Observer、Strategy
  • 對應9.3 提問設計
15.3

複雜度守恆

微服務等進階模式不會讓複雜度消失，只是把程式碼的複雜度換成維運的複雜度。規模還沒到之前，不必承擔這個代價。

  • 重點進階模式不會消除複雜度，只是把程式碼複雜度換成分散式維運複雜度
  • 講者備註You are not Google
15.4

架構型態決策樹

預設從 Monolith 開始，複雜了改成 Modular Monolith，需要獨立部署才拆成 Microservices。CQRS 與 Event Sourcing 只在特定需求下引入。

  • 預設：Monolith
  • 規模或複雜度上升 → Modular Monolith
  • 需要獨立部署與擴展 → Microservices（前提：快速佈建、Distributed Tracing、DevOps 文化）
  • 讀寫比例極端 → CQRS
  • 需要完整稽核與重播 → Event Sourcing

第 16 章

需求定義：PM 與 UX/UI

從老闆的一句「推薦要準」開始，產出第一份規格 PRD。

16.1

角色 R&R 與產出

PM 定義做什麼與不做什麼，UX/UI 設計使用者如何完成任務。兩者的產出是整個專案的起點。

  • PM
    • 職責：定義做什麼、為什麼做、不做什麼
    • 價值：把商業目標轉為可驗收的需求
    • 存在理由：缺少對「做對的事」負責的人，團隊會把對的東西做錯
    • 產出：PRD、User Story、優先順序、Success Metrics
  • UX/UI
    • 職責：設計使用者完成任務的路徑
    • 價值：讓需求成為可操作的流程
    • 存在理由：功能正確，使用者卻找不到或不會用
    • 產出：User Flow、Wireframe、Prototype、Design System
16.2

情境：「推薦要準」的定義

老闆只說要「更懂我」，沒有任何可以驗收的數字。這是大多數專案開始時的真實狀態。

  • 情境老闆要求「比現有外送平台更懂我」，沒有任何數字
16.3

架構演進 v1：PRD 與需求量化

把「推薦要準」換成回應時間、冷啟動與點擊率三個數字，並寫下 MVP 不做的事，這就是第一版規格。

  • 推薦結果 P95 < 500ms
  • 新使用者 Cold Start：三個問題內產生第一次推薦
  • 推薦點擊率 > 15%
  • 範圍外：MVP 不做團購、不做訂閱制
  • 對應4.2 PRD、12.1 拒絕形容詞、12.2 NFR 五大指標
16.4

AI 的角色定位

AI 能快速把訪談整理成 PRD 草稿、列出遺漏的情境，但判斷不了哪個需求最有商業價值。

  • 擅長：訪談紀錄整理成 PRD 草稿、列出遺漏情境、產生 Wireframe
  • 不擅長：判斷需求的商業價值、決定不做什麼
16.5

Orchestrator 調度方式

把訪談與競品資料交給 PM 與 UX Skill；驗收時確認每項需求都有數字，每個例外情境都有對應畫面。

  • 輸入：老闆訪談紀錄、競品截圖
  • 執行者：PM Skill 產出 PRD 與待釐清問題；UX Skill 產出 Happy Path 與 Unhappy Path
  • 驗收標準：每項需求都有數字或驗收條件；例外情境（附近無餐廳、雨天、超出預算）皆有對應畫面

第 17 章

系統分析：SA

SA 把業務語言轉成流程、規則與邊界，產出 SRS。

17.1

角色 R&R 與產出

SA 把業務語言轉成可實作的流程與規格，並畫出系統的邊界，讓每一條需求都能被實作、被測試、被追溯。

  • SA（System Analyst）
    • 職責：將業務語言轉為可實作的流程與規格；界定系統邊界
    • 價值：讓每一條需求都能被實作、被測試、被追溯
    • 存在理由：PM 講的是業務，工程師要的是規則；沒有轉譯，例外流程就由工程師自行猜測
    • 產出：SRS、Context Diagram、Use Case、Activity / Sequence Diagram、State Machine、業務規則表
17.2

SA 的三項核心工作

SA 的工作歸納成三件事：把需求拆成有編號的規格、畫出主流程與例外流程、界定系統範圍與責任歸屬。

  • 規格：把 User Story 拆成編號的 FR，並附驗收條件
  • 流程：畫出主流程與每一條例外流程
  • 邊界：界定範圍內外、外部系統與系統責任歸屬
17.3

情境：下單後店家一直不接單，怎麼辦？

PRD 只寫「可以下單」，沒寫店家不接單怎麼辦，工程師只好各自猜。例外流程沒有人定義，系統就會出現互相矛盾的行為。

  • 情境PRD 只寫「使用者可以下單」，工程師各自假設：有人等 30 分鐘、有人立刻退款
17.4

架構演進 v2：SRS——邊界、流程與規則

用 Context Diagram 畫出系統邊界，用 State Machine 定義訂單狀態與逾時規則；每條需求附驗收條件，並對應回 PRD 的目標。

  • Context Diagram：金流、地圖、LLM API 為外部系統，不在實作範圍內
  • 訂單 State Machine：已下單 → 店家接單 → 備餐中 → 已取餐 → 已送達
  • 例外規則：店家 5 分鐘未接單 → 自動改推薦同類餐廳；15 分鐘 → 取消並退款
  • FR 編號與 PRD 目標對應，建立 Traceability Matrix
  • 每條 FR 附 Given / When / Then 驗收條件
  • 圖表Context Diagram 與訂單 State Machine
  • 對應4.3 SRS、4.8 Shift Left、4.9 Traceability Matrix
17.5

AI 的角色定位

AI 很會展開 Use Case、列舉例外流程，但不知道真實的業務規則，例如店家實際多久接單、退款要符合哪些法規。

  • 擅長：由 PRD 展開 Use Case、列舉例外流程、產生 State Machine 草稿、檢查需求是否矛盾
  • 不擅長：得知真實的業務規則（店家實際接單時間、退款相關法規）
17.6

Orchestrator 調度方式

交給 SA Skill 產出 SRS；驗收時確認每條需求可追溯、有驗收條件、每個狀態都有例外路徑，業務規則由人確認。

  • 輸入：v1 PRD、訪談紀錄、店家營運資料
  • 執行者：SA Skill 依 ISO/IEC/IEEE 29148 結構產出 SRS、Use Case、State Machine
  • 驗收標準：每條 FR 都能追溯到 PRD；每條 FR 都有驗收條件；每個狀態都有例外路徑；業務規則由人確認

第 18 章

架構設計：Architect

Architect 依品質屬性做架構決策，產出 SAD 與 ADR。

18.1

角色 R&R 與產出

Architect 依品質要求決定系統的結構，並對整體品質負責。錯誤的架構決策，後面每個角色都要付出代價。

  • Architect
    • 職責：依品質要求決定系統如何切分、如何連接、故障時如何應對
    • 價值：管理整體品質，在約束條件下做出可負擔的取捨
    • 存在理由：錯誤的架構決策，後續每個角色都要付出代價
    • 產出：SAD、C4 Model、Quality Attribute Scenario、ADR、技術選型、風險清單
18.2

情境：LLM 回應需 3 秒，推薦須在 500ms 內顯示

同步呼叫 LLM 的 Demo 看起來很好，但一次回應要 3 秒，壓力測試一跑就失敗。Demo 能跑不代表能上線。

  • 情境同步呼叫 LLM 的 Demo 效果很好，壓力測試全數失敗
18.3

選定前三個品質屬性

這個專案最重要的是回應速度、尖峰時的穩定性與 AI 成本。先排出優先順序，後面的取捨才有依據。

  • Performance Efficiency：推薦 P95 < 500ms
  • Reliability：午餐尖峰下單不中斷
  • 成本（約束條件）：每筆訂單 AI 成本 < NT$0.5
  • 每項寫成 Quality Attribute Scenario
18.4

模型選型

依任務難度選模型：高頻、簡單的任務用低價模型，複雜的查詢才用旗艦模型。模型選型與資料落地位置寫成 ADR。

  • 依第 6 章比較價格、Context 與資料落地位置
  • Re-ranking 與推薦理由屬高頻、低難度任務 → 選用低價模型
  • 客服與複雜查詢 → 保留旗艦模型
  • ADR-002：模型選型與資料落地位置
  • 對應6.2 代表模型與 API 價格、6.4 台灣企業的選用考量
18.5

架構演進 v3：SAD——LLM 移出同步關鍵路徑

把 LLM 移出同步回應路徑：先用向量檢索與規則即時回應，LLM 的重排與推薦理由非同步補上，熱門推薦預先寫入快取。

  • 推薦拆為三段：Retrieval（Vector Search + 規則）→ Re-ranking → Explanation
  • Retrieval 同步回應；LLM 負責 Re-ranking 與推薦理由，非同步補上
  • 尖峰時段預先計算熱門推薦並寫入 Cache
  • 採 Modular Monolith 起步，推薦模組保留獨立拆分的邊界
  • ADR-001：不將 LLM 置於同步關鍵路徑（含被否決的方案與理由）
  • 圖表C4 Container Diagram
  • 對應4.4 SAD、14.2 Quality Attribute Scenario、14.5 Communication、15.3 複雜度守恆、15.4 架構型態決策樹、13.2 ADR
18.6

AI 的角色定位

AI 能列出候選架構、比較優缺點、找出遺漏的故障模式，但最後的決策要在預算與團隊能力之下由人做。

  • 擅長：列出候選架構、比較優缺點、繪製草圖、找出遺漏的故障模式
  • 不擅長：在預算與團隊能力下做最終決策
18.7

Orchestrator 調度方式

交給 Architect Skill 產出三個方案與比較，由人拍板並寫成 ADR，再確認每個品質情境都能在架構圖上找到對應設計。

  • 輸入：v2 SRS、NFR、約束條件（兩人、三個月、成本上限）
  • 執行者：Architect Skill 產出三個方案與取捨比較
  • 驗收標準：由人做決策並撰寫 ADR；每個 Quality Attribute Scenario 都能在架構圖上找到對應設計

第 19 章

細部設計：SD 與 DBA

SD 與 DBA 把架構拆成模組、介面與資料設計，產出 SDS。

19.1

角色 R&R 與產出

SD 把架構拆成模組與介面，讓多人或多個 Agent 能並行開發；DBA 設計資料的儲存與成長方式，因為資料是系統最難修改的部分。

  • SD（System Designer）
    • 職責：將架構拆解為可實作的模組與介面
    • 價值：讓多人或多個 Agent 並行開發而不互相衝突
    • 存在理由：架構圖的粒度太粗，無法直接實作
    • 產出：SDS、Module Diagram、API Spec（OpenAPI）、Event Schema
  • DBA
    • 職責：設計資料的儲存、查詢與成長方式
    • 價值：資料是系統中最難修改的部分
    • 存在理由：Schema 設計錯誤，修正時會波及所有程式碼
    • 產出：ER Diagram、Schema、Migration、Index 策略
19.2

情境：使用者口味資料散落各處

訂單、點擊紀錄與評分散在三個地方，推薦模組拿不到完整的使用者口味。資料流沒有設計，功能就做不出來。

  • 情境訂單、點擊紀錄、評分分散在三處，推薦模組無法取得
19.3

架構演進 v4：SDS——資料流與介面契約

定義領域實體；行為事件經由 Message Queue 更新口味向量；交易、快取與推薦各用適合的資料庫；模組之間用 OpenAPI 定義契約。

  • 領域實體：User、Restaurant、Dish、Order、Courier、Behavior Event
  • Behavior Event 經 Message Queue 更新使用者口味向量
  • PostgreSQL（交易資料）+ Redis（Cache）+ Vector DB（推薦）
  • 模組之間以 OpenAPI 定義契約
  • 圖表點擊 → Event → 口味向量 → Retrieval
  • 對應4.5 SDS、14.4 ACID 與 BASE、14.5 Loose Coupling、15.1 Clean Architecture
19.4

AI 的角色定位

AI 能從規格產生 ER 草稿、Migration 與 OpenAPI 骨架，但無法預估資料成長，也不知道哪些欄位未來會變動。

  • 擅長：由 SRS 產生 ER 草稿、撰寫 Migration、產生 OpenAPI 骨架
  • 不擅長：預估資料成長趨勢、判斷未來可能變動的欄位
19.5

Orchestrator 調度方式

交給 SD 與 DBA Skill 產出 API Spec 與 Schema；驗收時確認 Spec 通過 Lint、Migration 可以回復、每個查詢都有 Index。

  • 輸入：v3 SAD、ADR、Use Case
  • 執行者：SD Skill 產出 API Spec；DBA Skill 產出 Schema 與 Migration
  • 驗收標準：Spec 通過 Lint；Migration 可 Rollback；每個查詢都有對應 Index

第 20 章

實作與驗證：Developer 與 QA

依 V-Model 四層測試驗證實作，並為 LLM 的輸出加上 Eval 與 Guardrail。

20.1

角色 R&R 與產出

Developer 把規格變成可執行而且可維護的程式；QA 依照各層規格設計測試，因為寫程式的人最難看見自己的盲點。

  • Developer
    • 職責：將規格實作為可執行的程式
    • 價值：做得出來，而且可維護
    • 存在理由：規格不會自己執行
    • 產出：Source Code、Unit Test、Pull Request
  • QA
    • 職責：依各層規格設計測試，證明實作正確並找出錯誤
    • 價值：品質由設計決定，但需要獨立驗證
    • 存在理由：撰寫者最難看見自己的盲點
    • 產出：Test Plan、Test Case、Bug Report、Test Report
20.2

情境：測試全數通過，卻推薦牛排給素食者

推薦程式與測試都由同一個 Agent 撰寫，測試全部通過，卻把牛排推薦給素食者。自己寫的測試驗不出自己的盲點。

  • 情境推薦程式與測試都由同一個 Agent 撰寫，全部通過
20.3

V-Model 在點餐 App 的四層測試

依 V-Model 為點餐 App 設計四層測試：單一過濾函式、模組之間的介面、完整下單流程，最後用點擊率與試營運做驗收。

  • Unit Test（對應 SDS）：飲食禁忌過濾函式
  • Integration Test（對應 SAD）：訂單與支付之間的 Contract Test
  • System Test（對應 SRS）：完整下單流程、店家逾時未接單、尖峰負載測試
  • Acceptance Test（對應 PRD）：以推薦點擊率與店家試營運驗收
20.4

架構演進 v5：驗證層

用人寫的 Golden Case 為 LLM 輸出做 Eval，過敏與飲食禁忌改用硬性規則處理，測試由獨立的 Agent 依規格產生。

  • LLM Eval：人撰寫 50 筆 Golden Case，AI 擴充為 500 筆
  • Guardrail：過敏與飲食禁忌為硬性規則，不交由 LLM 判斷
  • 測試由 QA Agent 依規格獨立產生，不與實作共用 Context
  • 圖表推薦流程加入「規則過濾」與「Eval」兩道關卡
  • 對應4.6 V-Model、4.7 Verification 與 Validation、8.4 常見陷阱與防範機制
20.5

工具的選用

單一功能交給 IDE 或 CLI Agent，一次做一件事；可以獨立驗收的平行任務交給 Cloud Agent。同時留意程式碼的 AI 味。

  • 單一功能實作 → IDE 或 CLI Agent，一次一個任務
  • 可獨立驗收的平行任務（例：各模組的 Unit Test）→ Cloud Agent
  • 對應7.5 選擇工具的原則、9.6 程式碼的 AI 味
20.6

AI 的角色定位

AI 很擅長依規格實作、寫樣板測試與重構，但無法驗收自己的產出，也判斷不了業務邏輯是否正確。

  • 擅長：依規格實作、撰寫 Boilerplate 測試、Refactor、修正 Lint
  • 不擅長：驗收自己的產出、判斷業務邏輯是否正確
20.7

Orchestrator 調度方式

Developer Agent 一次只做一個小任務，QA Agent 獨立產生測試。關鍵測試由人撰寫，Eval 達標才合併。

  • 輸入：v4 SDS、SRS 驗收條件、Golden Case
  • 執行者：Developer Agent 一次一個任務、小幅度 Diff；QA Agent 依 V-Model 各層獨立產生測試
  • 驗收標準：關鍵測試由人撰寫；每個 FR 都有對應的測試案例；Eval 分數達標才 Merge

第 21 章

部署與維運：DevOps 與 SRE

上線後的重點是可觀測、可降級、可回復，以及控管 AI 成本。

21.1

角色 R&R 與產出

DevOps 與 SRE 讓系統可以部署、可以觀測、壞了能夠復原。開發環境能跑，不代表撐得住午餐尖峰。

  • DevOps / SRE
    • 職責：讓系統可部署、可觀測、可復原
    • 價值：上線不是終點，而是系統真正開始運作
    • 存在理由：開發環境可執行，不代表能承受尖峰流量
    • 產出：CI/CD Pipeline、IaC、Monitoring Dashboard、Runbook、SLO
21.2

情境：尖峰流量五倍，LLM 費用一天用掉一個月預算

每次重排都呼叫 LLM，沒有快取也沒有預算上限，尖峰一天就用掉一個月的費用。AI 成本必須和延遲一樣被監控。

  • 情境每次 Re-ranking 都呼叫 LLM，沒有 Cache，也沒有費用上限
21.3

架構演進 v6：可觀測性與降級機制

監控延遲、錯誤率與每筆訂單的 AI 成本；LLM 故障或超過預算時自動退回規則推薦；部署採灰度發布，並能一鍵回復。

  • 監控指標：Latency、Error Rate、每筆訂單 AI 成本
  • Graceful Degradation：LLM 故障或超出預算時退回規則推薦，App 不中斷
  • 成本控管：每日 LLM 預算上限、Cache Hit Rate
  • 部署流程：CI 自動測試 → Canary Release → 一鍵 Rollback
  • 圖表完整六大組成架構圖，Operations Layer 涵蓋全局
  • 對應5.2 Token 與計價、14.6 Four Golden Signals、13.1 ⑦ Evolve
21.4

AI 的角色定位

AI 能寫 Dockerfile、IaC 與 CI 設定，也能分析 Log，但不該由它決定何時部署，也不該持有正式環境的權限。

  • 擅長：撰寫 Dockerfile、IaC、CI 設定；分析 Log；起草 Runbook
  • 不擅長：判斷是否應在尖峰時段部署；承擔正式環境權限的後果
21.5

Orchestrator 調度方式

交給 DevOps Skill 產出 Pipeline、監控與 Runbook；驗收時實際演練一次回復，並確認正式環境權限不交給 Agent。

  • 輸入：v5 系統、SLO 目標
  • 執行者：DevOps Skill 產出 Pipeline、監控設定與 Runbook
  • 驗收標準：實際演練一次 Rollback；正式環境權限不交給 Agent
