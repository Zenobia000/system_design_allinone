## 1. 課程定位

| 項目 | 決定 | 備註 |
|---|---|---|
| **目標學員** | 完全的程式新手 | 連程式都還寫不太順；不假設任何後端 / 分散式 / 維運背景 |
| **終點能力** | 能畫出基本架構圖 + 能講出取捨 | 純「理解 + 推理」，**不要求動手實作** |
| **與現有課關係** | 全新獨立課 | 不假設讀者接著上現有「系統設計實戰」（那門課 L1 起跳、假設 2 年後端經驗） |

**一句話定位**：把一個完全沒碰過後端的人，帶到「看得懂架構討論、能自己畫一張架構圖、能說出為什麼這樣選」的程度。

## 2. 核心教學原則

### 2.1 不可違背的原則：先製造痛，再給解藥

系統設計的每個技術都是某個生產痛點的解藥。新手**既沒痛過、也沒詞彙**，所以直接講「快取是什麼」會沒有共鳴——這正是現有教材對新手失敗的根因。

整門課只有一個任務：**人工製造痛點**。先讓學員「想要」一個東西，再揭曉它叫什麼。順序顛倒就失敗。

### 2.2 三種教學手法的分工（A 主幹 · B 手法 · C 佐證）

- **A · 爆點敘事（主脊椎）**：跟著同一個 app 從小長大，每章開頭都是「系統爆了」，那章的技術就是解藥。負責**製造痛、長出架構圖、逼出取捨**。
- **B · 生活類比（教學手法）**：每個新技術先用學員已懂的生活場景講懂「形狀」，再揭曉技術名詞。負責**降低詞彙門檻**。
- **C · 真實佐證（收尾）**：每章點一下「IG / Uber / Netflix 也這樣做」。負責**給可信度**，並埋下「拆解真實專案」的種子。

## 3. 主角 app 與爆點章節順序

**主角：一個「線上點餐 App」**（蝦皮美食 / Uber Eats 的簡化版）。

選它的理由：天生同時具備多種張力——「訂單」是會扣錢的寫入（強一致）、「看菜單」是大量讀取（可容忍舊資料）、「食物照片」是大檔、「餐好了沒」是即時狀態、「找附近餐廳」是搜尋。同一 app 內「點餐要強一致、看菜單可最終一致」的對比，本身就是 C/A/L/Cost 框架的活教材。

| 章 | 資料夾 | 開場的痛 | 解藥（技術） | 架構圖長出什麼 |
|---|---|---|---|---|
| **0 · 世界觀** | `00-世界觀` | （還沒爆）一個 app 怎麼運作？ | client / server / DB 是什麼 | 手機 → 一台 server → 一個 DB |
| **1 · 人變多** | `01-人變多` | 中午 12 點，廚房做不過來，全部當機 | 多台 server + 負載平衡 · stateless | 加上負載平衡 + 多台 server |
| **2 · 狂看菜單** | `02-狂看菜單` | 大家一直刷菜單，DB 被問爆 | 快取（順帶建立「記憶體快、網路慢」數字直覺） | 加上快取層 |
| **3 · 資料又多又重要** | `03-資料又多又重要` | 訂單爆量，一個 DB 塞不下也讀不動 | 讀取複本（讀）+ 分片（存） | DB 變成 主庫 + 複本、分片 |
| **4 · 東西會壞** | `04-東西會壞` | 機器會掛、客人按兩次 → 重複扣款 | 容錯複本、重試、冪等 →（C/A/L/Cost 正式收斂） | 標出「會壞的點」與備援 |
| **5 · 照片與影片** | `05-照片與影片` | 上傳食物照，DB 不該塞；圖片載很慢 | Blob storage + CDN | 加上檔案儲存 + CDN |
| **6 · 即時與等待** | `06-即時與等待` | 「我的餐好了沒」狂刷新；做菜久不能卡住 | 佇列 + 非同步背景工作 + 即時通知 | 加上佇列 + worker |
| **7 · 找東西**（選配/進階） | `07-找東西` | 「附近有什麼？」找不到 | 搜尋系統入門 | 加上搜尋服務 |
| **結業 · Capstone** | `99-結業-capstone` | 給一個**新需求** | （不教新東西）自己畫架構圖 + 講取捨 | 學員自己畫一張 |

到第 6 章，架構圖已從「3 個方塊」長成一張完整的現代後端架構，而學員是**一塊一塊看著它為何長出來**的。

## 4. 每章內部結構

### 4.1 六拍節奏（每章固定，第二章起學員就摸熟套路）

| 拍 | 名稱 | 在做什麼 | 手法 |
|---|---|---|---|
| 1 | **痛點開場** | 具體場景：「中午 12 點，App 轉圈圈，客人罵翻」。先讓他痛，不給名詞。 | A |
| 2 | **生活類比** | 「這就像餐廳只有一個結帳櫃台……」用已懂場景秒懂解法形狀。 | B |
| 3 | **技術登場** | 揭曉：這叫**負載平衡 (Load Balancer)**。中英對照 + 一句白話定義。 | — |
| 4 | **架構圖長大** | 把上一章那張圖拿出來，當場加上新方塊，標「之前 vs 現在」。 | A |
| 5 | **真實世界** | 一句佐證：「Uber、蝦皮也這樣做。」 | C |
| 6 | **取捨收尾** | 得到什麼 vs 失去什麼、何時**不該**用。回到四維框架打分。 | — |

### 4.2 貫穿全課的雙螺旋（終點能達成的保證）

兩個終點目標不靠單章達成，而靠兩條從第 0 章纏到最後一章的線：

- **螺旋一 · 一直長大的架構圖**：全課只有一張圖，每章往上長一塊。每章結尾一個「**畫給我看**」練習（闔頁默畫）。到結業，學員已默畫過 7 次同一張圖的演化 → 「能畫架構圖」練了整門課。
- **螺旋二 · C/A/L/Cost 四維計分卡**：第 0 章就發給學員四個問題（一致性 / 可用性 / 延遲 / 成本各幾分）。每章第 6 拍都拿出來打分，第 4 章正式收斂成框架 → 「能解釋取捨」練了整門課。

### 4.3 兩個治新手「名詞恐懼」的小工具

- **詞彙卡**：每個新名詞首次出現，中英對照 + 一句生活版定義，絕不假設讀者知道。
- **進度條**：每章開頭顯示「我們的 App 現在服務 N 個用戶」，讓抽象的「擴展」有具體數字感。

## 5. 產出形式

**產出物**：markdown 投影片**內容設計稿**，每張投影片用 **prompt 形式**寫成——一張卡片 = 一段可直接拿去生成的規格（文字內容 + 視覺 prompt）。

**視覺風格**：LinkedIn carousel 風（專業、可滑動、一張一個重點、粗體標題壓字）。比例 **4:5（1080 × 1350 px）**。此風格自成一套，**不沿用**現有 system_design 課的暖色編輯插畫風。

### 5.1 資料夾結構

```
Handouts/system_design_101/
├── README.md                  課程總覽 + 爆點地圖 + 那張會長大的架構圖
├── 0_STYLE_GUIDE.md           LinkedIn 視覺風格 + 品牌 + 字體規格 + 卡片模板
├── 00-世界觀/
│   └── slides.md              prompt 形式投影片設計稿
├── 01-人變多/
│   └── slides.md
├── 02-狂看菜單/
├── 03-資料又多又重要/
├── 04-東西會壞/
├── 05-照片與影片/
├── 06-即時與等待/
├── 07-找東西/
└── 99-結業-capstone/
```

### 5.2 每張投影片（卡片）prompt 模板

```
### Slide N · [卡片標題]
- 節奏拍：痛點 / 類比 / 技術 / 架構圖 / 佐證 / 取捨（六拍之一）
- 卡片文字：
    - 大標：[≤ 14 中文字，粗體]
    - 內文：[≤ 3 行，每行 ≤ 18 中文字，白話]
- 視覺 prompt：[可直接生成的圖像描述，含 §6 LinkedIn 風格修飾詞 + 4:5]
- 品牌：logo 右下 64px + 頁尾「桑尼資料科學 · 版權所有 ©」
- 旁白/講者備註：（選填，給之後配音或講解用）
```

## 6. STYLE GUIDE 規格（`0_STYLE_GUIDE.md` 的核心，字體/字型/大小講究）

### 6.1 畫布

- 尺寸 **1080 × 1350 px（4:5）**
- 安全邊距 96 px（四邊）→ 內容區 **888 × 1158 px**

### 6.2 字型家族

| 用途 | 中文 | 拉丁 / 數字 | 理由 |
|---|---|---|---|
| 標題 Display | Noto Sans TC **900 Black** | Inter **800 ExtraBold** | 粗體在 feed 縮圖也讀得到 |
| 內文 Body | Noto Sans TC **500 Medium** | Inter **500** | 高易讀、專業中性 |
| 技術名詞 / 數字標註 | — | JetBrains Mono **500** | 等寬 = 「這是技術術語」信號 |

> 備援字型：中文可用思源黑體 (Source Han Sans)；拉丁可用 Helvetica Neue / system-ui。

### 6.3 字級階層（@ 1080 × 1350）

| 角色 | 字級 | 字重 | 行高 | 用途 |
|---|---|---|---|---|
| Hook 大標 H1 | **80 px** | 900 | 1.15 | 卡片主標、痛點開場 |
| 副標 H2 | **48 px** | 700 | 1.30 | 次級標題 |
| 內文 Body | **34 px** | 500 | 1.60 | 說明（每卡 ≤ 3 行） |
| 巨數字 Big Number | **160 px** | 900 | 1.00 | 用戶數進度條、強調數字 |
| 節奏標籤 Kicker | **24 px** | 700 | 1.20 | 六拍標籤，大寫 + 字距 0.12em |
| 註解 Caption | **26 px** | 400 | 1.40 | 補充、來源 |
| 頁尾品牌 | **22 px** | 500 | 1.20 | 桑尼資料科學 · 版權所有 © |

**字數上限**：大標 ≤ 14 中文字；內文每行 ≤ 18 中文字、整卡 ≤ 3 行。超過 → 拆卡，不硬塞。

### 6.4 色票（取自品牌 logo：navy 底 + teal→mint 漸層）

| 用途 | HEX | 說明 |
|---|---|---|
| 深底 | `#152238` | logo 海軍藍，深色卡片主底 |
| 淺底 | `#F4F1EA` | 暖白，淺色卡片底（不用純白） |
| 主強調 | `#2E7D86` | deep teal（漸層暗端） |
| 次強調 / 亮點 | `#97E8D6` | mint（漸層亮端）；箭頭、highlight |
| 白點 | `#FFFFFF` | logo 眼睛白，小面積點綴 |
| 深底上文字 | `#F4F1EA` | |
| 淺底上文字 | `#152238` | |
| 警告 / 痛點 | `#E8634F` | soft red |
| 成功 / 解藥 | `#5B9770` | moss green |

**禁用**：純白 `#FFFFFF` 當大面積背景、純黑 `#000000`、霓虹、3D 反射、雜亂裝飾。

### 6.5 品牌配置（每張卡片必備）

- **Logo**：深底卡用 `logo-light.png`；淺底卡用 `logo-dark.png` 或 `logo-main.png`。位置右下角，高度 64 px。
  - 來源：`Handouts/system_design/openslide/assets/branding/`
- **頁尾**：「桑尼資料科學 · 版權所有 ©」，22 px，置中或置左，當前底色文字 50% 透明。

### 6.6 六拍視覺編碼（讓學員一眼認出在哪一拍）

| 拍 | 角標色 |
|---|---|
| 痛點 | 警告紅 `#E8634F` |
| 類比 | mint `#97E8D6` |
| 技術 | deep teal `#2E7D86` |
| 架構圖 | navy `#152238` |
| 佐證 | 成功綠 `#5B9770` |
| 取捨 | 雙色（teal vs red 並陳） |

## 7. 驗收標準（課程成功的定義）

1. 一個完全沒碰過後端的人讀完，能在白紙上**默畫出點餐 App 的演化架構圖**（至少到第 4 章的程度）。
2. 給一個新需求（如「設計一個線上投票」），學員能說出**至少 2 個技術選項**並用 C/A/L/Cost 講出取捨。
3. 全程沒有任何一個技術名詞是「沒先製造痛、直接丟定義」出現的。
4. 每張卡片符合 §6 字體 / 色票 / 品牌規格，4:5，可直接生成。

## 8. 範圍界線（非目標 · YAGNI）

- **不教**動手寫程式、framework、雲端設定、面試技巧。
- **不涵蓋**現有「系統設計實戰」的進階深度（Paxos 證明、PACELC 細節等）。
- **不做**實際 React/Marp 渲染——本課產出是 prompt 形式設計稿；渲染是後續獨立工作。
- 第 7 章（搜尋）標**選配**，可後做或砍掉，不阻塞前 7 章完成。
