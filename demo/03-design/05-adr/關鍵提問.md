# 05 ADR · 關鍵提問（Architect 必問）

> 本場會議 60 分鐘，Architect 只要把這 6 題 + 1 題送命題問完、問對，會議就成功了。
> 不要問「大家想用什麼？」這種開放題——問題要**逼出 trade-off**，不是逼出偏好。

---

## Q1. 「這個決策**影響到哪些 NFR**？列出至少 3 個會被它綁住的非功能需求。」

- **為什麼問這個**：很多人挑技術只看 functional（「會不會做」），忘了 NFR 才是 ADR 的真正戰場。
  ADR 的價值是**逼大家看見 trade-off**，而 trade-off 永遠發生在 NFR 層——performance、reliability、
  maintainability、security、cost、portability。沒列 NFR，等於沒在做架構決策，只是在挑工具。
- **好答案長什麼樣**：「儲存層決策影響 (a) **portability**（V1 要不要同步到雲）(b) **performance**
  （讀取延遲 < 100ms 才能維持 3 分鐘 UX）(c) **cost**（localStorage 零成本 vs server $50/mo）
  (d) **data durability**（使用者清 cache 資料就沒了）」——4 個 NFR 各對應**具體量測**。
- **壞答案長什麼樣**：「會影響使用者體驗」「會影響效能」——沒指明哪個 NFR、沒數字。
- **別人會 push back 什麼**：Dev 會說「現在還沒實作哪知道效能多少」。回應：
  「不是要你給實測值，是要你給**門檻假設**——譬如『讀取 < 100ms 才能維持目標 UX』，
  之後實作驗證沒達標就觸發 review。」

## Q2. 「這個決策**可逆嗎**？要換掉的話成本是多少？標 Easy / Hard / One-way Door。」

- **為什麼問這個**：可逆性決定**討論深度**。Easy decision（譬如選哪個 UI library）討論 10 分鐘就夠，
  Hard decision（譬如 ORM 選型）要討論 60 分鐘，One-way Door（譬如資料庫從 SQL 換 NoSQL）
  要討論 3 場會議外加 spike。把可逆性先標出來，會議才知道該花多少力氣。
- **好答案長什麼樣**：「localStorage → server-side 是 **Hard**——要 (a) 寫 migration endpoint
  (b) 設計衝突解決（離線資料 vs 雲端）(c) 給使用者 opt-in flow。預估 2 週工作量。**不是 One-way Door**
  因為 server-side 還能讀回 localStorage 格式（schema 設計時保留兼容）。」
- **壞答案長什麼樣**：「應該可以換吧」「之後再說」——沒估工作量、沒列 migration 步驟。
- **別人會 push back 什麼**：PO 會說「現在想這個太早了」。回應：「One-way Door 不在現在想，未來就不能換。
  ADR 的存在就是替未來決策標路標。**現在花 10 分鐘標清楚可逆性，未來省 2 個月的悔恨**。」

## Q3. 「至少列出 **3 個 rejected options**，每個寫具體的拒絕理由（不准用『不夠好』）。」

- **為什麼問這個**：少於 3 個 rejected options 的 ADR 是**沒做功課**——代表只考慮了一條路就決定，
  根本沒做 trade-off。拒絕理由要寫**本專案的具體理由**（譬如「IndexedDB 對 PWA service worker
  的相容性在 Safari 14 以下有 bug，我們目標族群 30% 用 iPhone」），不是抽象的「不夠好」。
- **好答案長什麼樣**：
  - Rejected: **IndexedDB**。拒絕理由：「(1) API 比 localStorage 複雜 3 倍，4 週 MVP 沒時間寫 wrapper
    (2) 主要需求是『存 3–10 個行程 JSON、< 100KB』，根本沒用到 IndexedDB 的 transaction/index 能力
    (3) 給 V1 真的需要大量資料時再升級。」
  - Rejected: **Firebase Firestore（server-side）**。拒絕理由：「(1) 違反 brief「免登入即開即用」
    (2) 月成本 ~$25 USD（驗證期沒商業模式不該燒）(3) 4 週驗證窗失敗的話這個依賴等於白接。」
- **壞答案長什麼樣**：「IndexedDB 太複雜」「Firebase 不適合」——沒給數字、沒列具體缺點。
- **別人會 push back 什麼**：Dev 會說「拒絕的東西寫這麼詳細幹嘛？」。回應：「3 個月後有人提
  『我們為什麼不用 IndexedDB』，沒寫拒絕理由你就要重開一場會。寫一次省十次。」

## Q4. 「6 個月後**會後悔這個決策的情境**是什麼？預先寫 review trigger。」

- **為什麼問這個**：ADR 不是「決定完就鎖死永遠不動」，而是「決定 + 預設未來重審條件」。
  寫下 review trigger（什麼指標達標時要重審）才是成熟架構，否則 ADR 變成「祖傳憲法」沒人敢動。
- **好答案長什麼樣**：「Review trigger：(a) **DAU > 10K** 時重審（localStorage 規模上限）
  (b) **使用者出現『換手機資料就沒了』客訴 > 5 件/週** 時重審 (c) **V1 帳號功能進入 roadmap**
  時觸發 ADR-002（雲端同步策略）。」
- **壞答案長什麼樣**：「不會後悔」「之後再看」——典型的「ADR 變祖傳憲法」失敗模式。
- **別人會 push back 什麼**：Architect 自己最容易跳過這題。回應：寫下 review trigger 才是 ADR，
  沒寫的 ADR 是「會議紀錄」。**這條沒寫，下游 12-release-plan 無法判斷何時要排 migration sprint**。

## Q5. 「這個決策**綁住了哪些下游卡**？具體說明流向 06/07/08 哪一個欄位。」

- **為什麼問這個**：ADR 不是孤島，每條決策都會在下游卡變成**具體欄位**。Architect 要明示
  「我這條決策決定了 06-c4-diagram 的 storage container 類型」、「決定了 07-api-spec
  是 HTTP 還是 local function」、「決定了 08-data-model 是否需要 schema migration 機制」。
  下游沒對齊，ADR 等於白寫。
- **好答案長什麼樣**：「ADR-001（localStorage）→ (a) **06-c4** 的 storage 標『browser-local』
  不是『external service』(b) **07-api-spec** 的 endpoint 是 `storage.save()` 不是
  `POST /trips`（local function 契約）(c) **08-data-model** 不需要 ID generation strategy
  （client-side UUID 即可，無 server 衝突問題）。」
- **壞答案長什麼樣**：「下游自己看著辦」——下游無錨點就會自己腦補，3 卡之後對不上。
- **別人會 push back 什麼**：Dev 會說「下游卡還沒寫，怎麼引用？」回應：「現在不是引用，是**標欄位流向**。
  之後 06 卡開會時，主席會看 ADR 這段確認方向，不是重新討論。」

## Q6. 「**沉沒成本**有多少？團隊熟悉度 vs 學習曲線怎麼權衡？」

- **為什麼問這個**：技術選型不能只看「客觀最佳」，要看「**我們團隊**做不做得出來」。
  一個理論上最棒但全團隊都沒碰過的選擇，學習曲線會把 4 週 MVP 燒掉一半。沉沒成本（已有 code、
  已有 infra、已有經驗）與學習曲線是**真實成本**，不寫進 ADR 就是自欺欺人。
- **好答案長什麼樣**：「FE 2 人都做過 React + localStorage 專案 → **學習曲線 = 0**；
  vs Firebase 沒人碰過 → 預估 1 週 onboarding + 1 週踩雷 = 2 週成本，等於 MVP 50% 時間。
  沉沒成本：目前產品已用 localStorage 上線，換 Firebase 要重寫 6 個檔案。」
- **壞答案長什麼樣**：「團隊應該學得會」「Firebase 文件很完整」——沒估時間、沒列既有資產。
- **別人會 push back 什麼**：Architect 自己會想用「正確的技術」否定團隊熟悉度。回應：
  「『正確的技術』是上下文相依的。4 週 MVP 的『正確』就是『團隊能 ship 的』。
  學習曲線是 trade-off 的一部分，不是『不夠專業』。」

## 送命題清單

這 1 題不問，3 個月後新人 onboard 會看不懂為什麼這樣選：

1. **「假設 V1 我們真的要做帳號同步，**現在的決策**會綁死什麼**？預先列 migration 路徑。」

   ADR 不只是「現在選什麼」，是「**現在的選擇對未來開出什麼後門**」。
   localStorage → server-side 的 migration path 要在 ADR-001 寫清楚：
   (a) schema 預留 `userId` 欄位（即使 MVP 不用）
   (b) 序列化格式用標準 JSON 不要塞 Date object（避免 deserialize 不一致）
   (c) 預留 `lastModified` timestamp（未來衝突解決需要）。

   **不寫，6 個月後做 V1 才發現要花 4 週重構**——這就是技術債。ADR 的價值是**現在花 10 分鐘
   開後門，未來省 4 週重構**。
