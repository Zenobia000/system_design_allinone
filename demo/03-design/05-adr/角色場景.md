# 05 ADR · 角色場景

## 這場會議在做什麼

PRD 與 AC 都已凍結，現在要正式回答「**為什麼選 A 不選 B**」。
本場會議專門對**單一架構決策**展開：列 ≥3 個候選選項、寫各自 pros/cons、
給出 rejected option 的拒絕理由、寫下 consequences 與可逆性。

**不是**選 best technology 的會議，**不是**炫技會，**不是**寫實作的會議。
目的只有一個：把這個決策**寫進 ADR 文件**，三個月後新人 onboard 看了能秒懂「為什麼當初這樣選」。

> **一場會議只討論一個 ADR**。SmartTrip MVP 預計累積 6–10 條 ADR
> （儲存層、FX 資料源、PWA vs SPA、狀態管理、燈號演算法、分析工具⋯⋯），
> 每條獨立開一場 60 分鐘會議。本場示範第一條：**儲存層選型**。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Architect（主責，你）** | PRD §8 技術約束、團隊技能盤點、6 個月 roadmap 視角 | 簽核的 ADR 文件 + decision log |
| **Dev**（FE 1–2 人） | 實作可行性、library 熟悉度、踩雷經驗 | 知道「6 週後寫 code 時不會被卡死」的選項 |
| **SA**（System Analyst） | 跨系統依賴、外部 API 穩定性、容量估算 | 確認決策不會破壞既有 integration |

## 你扮演的角色（Architect）

你是「**未來債清算員**」。本場會議你要做三件事：

1. 強迫團隊至少列 **3 個候選選項**——少於 3 個代表沒做功課，會議休會去補
2. 對每個 rejected option 寫**具體**的拒絕理由（不准寫「不夠好」「太複雜」這種模糊話）
3. 給最終決策標**可逆性等級**（Easy / Hard / One-way Door）+ **量測軸**（之後怎麼知道這決策對不對）

**禁忌動作**：本場會議**禁止**講這幾種話，講了就要重來：

- ❌「**業界都用 X**」「**大廠都這樣做**」——本專案的約束跟大廠不同，引用無效
- ❌「**新技術比較好**」「**OOO 已經過時**」——技術新舊不是 trade-off，是品味
- ❌「**之後再說**」「**先做了再看**」——這場會議的存在就是為了避免「再說」
- ❌**沒寫 rejected options 直接決定**——這叫「會議紀錄」不叫 ADR

## 會議結束時，桌上要有什麼

一份完整的 ADR 文件，含以下 6 段（缺一段不算過）：

1. **Context**：為什麼現在要做這個決策？觸發事件是什麼？（引用 PRD §X / AC §Y）
2. **Decision**：一句話結論。「我們選 X」。
3. **Options Considered**：≥3 個選項，每個含 pros / cons / rejection reason
4. **Consequences**：positive 與 negative 各列 2–3 條（誠實寫負面）
5. **Reversibility**：Easy（程式改一改）/ Hard（要 migration script）/ One-way Door（換不回來）
6. **Review Trigger**：什麼條件觸發本決策需重審（例：DAU > 10K、出 V1 帳號功能時）

附加產出：

- Decision log 條目（短摘要 + 連到本 ADR 全文）
- 給 06-c4-diagram 的「container 邊界提示」（這個決策框住了 container 怎麼切）
- 給 08-data-model 的「資料生命週期假設」（資料活在哪、活多久）

## 為什麼這場會議重要

ADR 是整條 SDLC 的**設計憲法**。下游每張卡都引用它：

- **06-c4-diagram**：container 邊界依賴 ADR「storage 在哪一層」這類決策
- **08-data-model**：欄位設計取決於 ADR「資料用 NoSQL 還是關聯式」
- **07-api-spec**：endpoint 是 HTTP 還是 local function 取決於 ADR「PWA vs server」
- **11-unit-test**：mock 策略取決於 ADR「外部依賴怎麼隔離」
- **12-release-plan**：是否需要 migration window 取決於 ADR「可逆性」
- **15-postmortem**：事故發生時回頭看 ADR，判斷是「決策錯」還是「執行錯」

**跳過 ADR 的代價**：6 週後 Dev 寫 code 時憑感覺挑 library，3 個月後新人接手問「為什麼用 X」沒人答得出來，
6 個月後想換掉發現綁太深——這就是**技術債的源頭**。ADR 不是文件工作，是**未來債的保險單**。

## 本場示範主題

**ADR-001：localStorage vs IndexedDB vs server-side persistence（MVP 儲存層選型）**

- **為什麼選這題示範**：種子簡報明示「MVP 用 localStorage、不做帳號雲端同步」，看似決定好了，
  但**沒走 trade-off 流程的決定不是 ADR**——本場會議要把「為什麼這個看似顯而易見的決定其實有 3 個選項」攤開。
- **教學意義**：學員會學到「即使最終決策不變，走完 ADR 流程的價值在於 consequences 與 reversibility 被寫清楚」。
  V1 要加帳號時，下一任 Architect 看這份 ADR 才知道「當初為什麼這樣選、需要做什麼 migration」。
