## 教學要點（看完 AI 輸出後讀這段）

### 1. ADR vs PRD decision_log：為什麼同一個決策要寫兩次？

PRD 的 `decision_log` 只記「PM 視角為何選 A」——對 PM/PO 夠用。
ADR 是**架構視角**的展開，必須回答：
- 5 象限 decision_drivers 怎麼權衡（PRD 不寫）
- 每個 rejected option 的 cost / risk / 隱含合規問題（PRD 不寫）
- consequences.negative + follow_up（PRD 不寫）

兩者不是重複，而是**不同抽象層級**的決策紀錄。半年後新人問「為何不用 Firebase？」時，PRD 答不出來，ADR 答得出。

### 2. 為什麼必須列至少 3 個 options，且要包含「不做」選項？

本卡列了 4 個 options，其中 **Option D（in-memory 不持久化）是刻意放的「下界對照」**。
就算明顯不會選，列出來能：
- 強迫團隊明確說出 P0 FR-006（行程儲存）為何不能砍
- 防止半年後有人質疑「為何不用最簡單的 in-memory」時找不到歷史紀錄
- 對照之下 Option A 的真實 trade-off 更清楚

學生最常犯的錯：只列 chosen + 1–2 個 strawman option，看不出真實取捨。

### 3. `decision_drivers` 5 象限為何要顯式 weight？

不寫 weight，rejected_reason 會變成主觀感覺。
本卡 Option B 被拒，是因為 weight 是 `time_to_market: critical`、`cost: high`、`operability: high`、`reliability: medium`——
在這個 weight 排序下 Option B 在 operability + 合規成本上失分，Option A 勝出。
若 weight 改成 `reliability: critical`，結論可能會反過來。
**ADR 的價值不是結論，而是「給定這個 weight 才有此結論」的可審計脈絡**。

### 4. `status` 與 `superseded_by` 為什麼重要？

ADR-001 標 `accepted` + `review_date: 2026-06-23`（4 週驗證窗結束）——
這是 ADR 紀律最容易被忽略的部分：**決策有時效性**。
若 4 週驗證通過、要做 V1 雲端同步時，須開 ADR-005，並把 ADR-001 標 `superseded_by: ADR-005`。
不標的話，新人 onboarding 會看到「localStorage」結論誤以為現在還適用。
學生產出 ADR 後常忘了維護 status，等於白寫。

### 5. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `chosen_and_scope` | `06-c4-diagram/` Container 層標示 client-side storage |
| `consequences.follow_up` 第 3 條 | 回頭補 `04-acceptance-criteria/` AC-008 一條 NFR AC |
| `decision_drivers` 5 象限 + weight | `09-non-functional-reqs/` 的優先級排序 |
| `out_of_scope` 第 1 條（即時匯率快取） | 觸發開 ADR-002 |
| `consequences.follow_up` 第 1 條 | 預埋 V1 規劃時的 ADR-005（遷移策略） |
| `status.review_date` | 加入團隊 calendar 提醒 |

### 6. ADR 不寫 how，只寫「為何這樣選」

本卡輸出**沒有**：
- localStorage 的 key/value schema 設計
- 序列化格式（JSON vs IndexedDB）
- 加密策略

這些屬於 Dev Lead 的實作層，不該進 ADR。
ADR 只到「用 localStorage」這層——再深就是 how，違反規則 7 暗示（ADR 是 trade-off 紀錄不是技術說明書）。

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 只列 chosen + 1 個 strawman option（湊數） | 規則 7 | 至少 3 個 options（含「不做」），每個都要 pros/cons/cost/risk |
| `consequences` 只寫 positive，沒寫 negative | 規則 2 | negative 必填——選了 A 一定犧牲什麼，誠實寫出來 |
| `decision_drivers` 只寫權重高的，省略不適用的象限 | 規則 4 | 5 象限都要寫；不適用須寫「為何不適用」 |
| `status` 寫 accepted 但不寫 `review_date` | 規則暗示（決策有時效） | 標記下次審視日期，特別是綁時間盒（如 4 週驗證窗）的決策 |
| ADR 內含 schema / class 設計 / API spec | 規則 7（PRD 規則挪用） | ADR 只寫 what & why，how 屬於 Dev / API contract |
| rejected_reason 寫「不適合」「不夠好」 | 規則 2 + 思考步驟 5 | 必須對應到具體 decision_driver 象限（例：「operability driver: 需要 24x7 on-call」） |

## 交件 checklist

- [ ] `options_considered` ≥ 3 個（含「不做」或「現狀」），每個都有 pros/cons/cost/risk
- [ ] `decision_drivers` 5 象限都有 weight + rationale，不適用要寫明
- [ ] `consequences.negative` 至少 2 條（必填）
- [ ] `consequences.follow_up` 至少 1 條，且對應到下游卡的具體動作
- [ ] `status.current` + 若是 accepted 要寫 `review_date`
- [ ] `out_of_scope` 至少 3 條（避免越權，且預告會有 ADR-002/003/...）
- [ ] `rejected_reason` 對應到 `decision_drivers` 中的具體象限（不寫「不適合」）
- [ ] `self_review.lowest_confidence` 對應到每個 M/L 標註的補洞計畫
