## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 SmartTrip FX 的 data model 看起來不像「真的 schema」？

很多學生第一次看到「localStorage 的 data model」會覺得：「這不是用 JSON 嗎？要 model 幹嘛？」

錯。**只要有「跨時間的資料一致性需求」就需要 model**：

- schema version 不寫，半年後改 enum 值會炸開所有舊資料
- audit 欄位不寫，使用者反映「我的行程消失了」你查不到何時被改
- soft delete 不寫，「最近刪除」UI 沒法做

把 localStorage 當 DB 來建模，是工程紀律的體現。

### 2. 為什麼 ItineraryItem 用 denorm 嵌入 Trip，但 Expense 拆獨立 key？

`decision_log` 寫得很清楚 — **看 query pattern 與寫入頻率決定，不是抄 SQL 範式**：

| Entity | 讀模式 | 寫頻率 | 決策 |
|---|---|---|---|
| ItineraryItem | 「打開整個 Trip」一起讀 | 一次性建立後少改 | denorm 嵌入 Trip |
| Expense | 跨 expense 算總額 | 旅途中頻繁新增 | 獨立 key |

學生若無腦套用「3NF → 全部拆表」，會把 ItineraryItem 拆出來，結果 localStorage 無 JOIN，要做 N+1 次 getItem。**規範化的目的服務 query pattern，不是反過來**。

### 3. 為什麼「無 PII」也要做 data classification？

種子簡報沒有姓名 / email / 信用卡，但仍標出 `session_sensitive`：

- destination + dates 是「行為資料」，被偷看可知道使用者何時不在家
- expense.note 可能含「給男友的生日禮物」這種隱私敘事

GDPR right-to-erasure 在本案等價於「清空所有資料」按鈕。如果學生只寫「無 PII → 不需要 classification」就漏掉一整層風險。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `entities` 所有 schema | `10-code-review-checklist/` schema validation 維度 + 單元測試 |
| `data_classification.erasure` 「清空所有資料」按鈕 | UX flow + `09-non-functional-reqs/` privacy SLI |
| `migration_strategy.versioning` | `10-code-review-checklist/` schema migration review 規則 |
| `FXRateCache` 與 `07-api-spec` 的 FxRateResponse | 同步維持兩者一致 |
| `relationships.on_delete` 行為 | StorageAdapter 實作 + 單元測試 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 用 SQL FK 描述 localStorage 關聯，寫 `FOREIGN KEY (trip_id) REFERENCES Trip(id)` | localStorage 沒有 FK | 寫「logical FK, application-enforced」並指明哪個 component 負責 enforce |
| 漏寫 `schema_version` 欄位 | 規則 7（audit 欄位） | 每個 entity 都要有 schema_version + created_at + updated_at + deleted_at |
| Trip 嵌 ItineraryItem 又拆獨立 key，沒在 decision_log 解釋 | 規則 2（trade-off） | 至少寫一條 `decision_log`，列 options + 為何選此 normalization |
| 寫「無 PII 故無需 retention」 | 規則 4 | session-sensitive 資料仍需 retention + erasure 策略（GDPR right-to-erasure 等價） |
| ERD 用 SQL 工具的語法，沒用 Mermaid | 輸出格式要求 | 用 `erDiagram` Mermaid 語法，能在 GitHub / Notion 直接渲染 |

## 交件 checklist

- [ ] 每個 entity 都有 `schema_version` + `created_at` + `updated_at` + `deleted_at`
- [ ] 每個關聯標 cardinality + on_delete + rationale（含 application-enforced 的說明）
- [ ] `normalization_level` 明寫 denorm vs normalize 的 trade_off
- [ ] `migration_strategy.versioning` 寫明 migration table 結構 + rollback 策略
- [ ] 每個 session_sensitive 欄位都有 retention + erasure 政策
- [ ] Mermaid ERD 涵蓋所有 entity + 主要關係
- [ ] `out_of_scope` 至少 3 條（雲端同步、analytic、多人分帳）
- [ ] 每個 `confidence: M/L` 對應 `self_review.lowest_confidence` 一條補洞計畫
