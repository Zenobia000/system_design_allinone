# 08 Data Model · 關鍵提問（Dev 必問）

> 本場會議 60 分鐘，Dev 只要把這 6 題問完、問對，會議就成功了。
> 不要問「大家覺得這個欄位怎麼設？」這種開放題——問題要**逼出選擇**，不是逼出意見。
> 每個欄位的命運要在這場會議裡定下來。

---

## Q1. 「這個欄位的 type / nullable / default 是什麼？沒答出三個值的不准進 schema。」

- **為什麼問這個**：data model 最常見的爆炸是「欄位定義模糊」。`amount` 是 number 還是 string？nullable 嗎？沒填預設 0 還是 null？三個值任一不確定，半年後 prod 就會有一筆資料把你的 component 炸掉。Dev 心智：你不是在「設計欄位」，你是在「替三個月後讀資料的自己寫合約」。
- **好答案長什麼樣**：「`Expense.amount`：number（IEEE 754 double，前端 toFixed 處理顯示精度）、not null、no default（必填）、約束 >= 0；理由：PRD P0-7 開支必填金額，0 與 null 在報表上行為不同（0 = 真的免費，null = 還沒填），不能讓 null 出現。」
- **壞答案長什麼樣**：「就是金額啊」「先 nullable 之後看狀況」「default 0 就好不用想」——三個都是定時炸彈。
- **別人會 push back 什麼**：Architect 可能說「這太細了吧，寫 code 時再說」。回應：「寫 code 時定 = 每個 Dev 自己定 = 三處不一致。現在 30 分鐘定完，省下未來 3 個 sprint 的 bug。」

## Q2. 「這個欄位是 PII、session_sensitive 還是 public？保留多久？怎麼 erasure？」

- **為什麼問這個**：MVP「無帳號 = 無 PII」是錯誤直覺。Trip.destination + start_date 合在一起，等於「告訴你我何時不在家」；Expense.note 可能寫「給女友的生日禮物」這種敘事資料。GDPR Article 17（right-to-erasure）對「能識別自然人的資料」全部適用，不只姓名身分證。**不在這場定，下游 NFR 卡（09）寫不出 retention SLO，runbook（14）寫不出「使用者要求刪除資料」流程。**
- **好答案長什麼樣**：「`Trip.destination`：session_sensitive；retention = 隨 Trip 一起 GC；erasure = 設定頁『清空所有資料』按鈕清掉 `smarttrip:trip:*` 全部 key（GDPR Art.17 等價）。」
- **壞答案長什麼樣**：「我們沒有 PII 所以不用標」——99% 是錯的，行為與敘事資料都需要 classification。
- **別人會 push back 什麼**：Architect 可能說「MVP 階段不用顧 GDPR 吧」。回應：「不顧 = release 前法務退件 = 整批 schema 重做。現在定 5 分鐘，省下 release 前一週的痛苦。」

## Q3. 「這個關聯是 1:1 / 1:N / N:M？on_delete 怎麼處理？」

- **為什麼問這個**：localStorage 沒有 FK 強制、沒有 ON DELETE CASCADE，**所有關聯都靠 application-enforced**。如果沒明寫「刪 Trip 時 Expense 怎麼辦」，會出現「行程刪了但開支還在」的孤兒記錄，使用者下次打開「我的行程」清單看到一堆數字對不上的資料。寫程式的人是 Dev，被客訴炸的也是 Dev，必須當場敲死。
- **好答案長什麼樣**：「`Trip 1:N Expense`，logical FK = `Expense.trip_id`；on_delete = cascade（刪 Trip 時 StorageAdapter 掃 `smarttrip:expense:{tripId}:*` 全部 purge）；若 purge 失敗，孤兒記錄不影響功能，下次 list 時 GC。」
- **壞答案長什麼樣**：「就 1:N 啊」（沒講 on_delete）、「應該不會有人刪行程吧」（就會有）。
- **別人會 push back 什麼**：Architect 可能說「localStorage 沒 FK，這些都是 app 邏輯，不用寫進 schema」。回應：「不寫進 schema = 每個寫 delete 的 Dev 各自實作 = 三處不一致。schema 是『行為規範』，不只是『欄位清單』。」

## Q4. 「這個 entity 走 denormalize（嵌入）還是 normalize（拆獨立 key）？trade-off 是什麼？」

- **為什麼問這個**：localStorage 不是 RDBMS，**3NF 教條在這裡是錯的**。決策維度是「query pattern × 寫入頻率 × 寫入阻塞容忍度」，不是「資料庫範式」。`ItineraryItem` 跟著 Trip 一起讀 → 嵌入；`Expense` 旅途中頻繁新增 → 獨立 key（否則每次新增都要整包 Trip 重寫，main thread 阻塞）。沒挑明，會被「習慣 SQL 的 Dev」自動全部拆表，造出 N+1 getItem 慘案。
- **好答案長什麼樣**：「ItineraryItem 嵌入 Trip（denorm），因為 query pattern 是『打開整個 Trip』整包讀寫最快、N < 30 可接受；Expense 拆獨立 key `smarttrip:expense:{tripId}:{expenseId}`，因為新增頻繁、寫入熱點，獨立才不會阻塞 main thread。」
- **壞答案長什麼樣**：「先全部拆獨立 key 比較規範」「先全部嵌入比較簡單」——沒看 query pattern。
- **別人會 push back 什麼**：Architect 可能說「混用兩種策略很怪」。回應：「混用是因為兩個 entity 的寫入模式不同。一致性服務於使用者體驗，不是反過來。寫進 decision_log。」

## Q5. 「這個欄位需要 index 嗎？localStorage 上限 5MB，index 加多少不會爆？」

- **為什麼問這個**：localStorage 沒有原生 index，所有「快速查找」都要自己維護一個 index key（例如 `smarttrip:trips_index` 存 `[{id, created_at, destination, deleted_at}]`）。但 index 也佔空間、也要在新增/刪除時同步更新，不是免費的。**Dev 必須當場決定哪些 query 值得犧牲 5MB 配額來加 index，哪些 query 可以接受 O(N) 掃描。**
- **好答案長什麼樣**：「`trips_master_index` 只存 [id, created_at, destination, deleted_at] 四欄，覆蓋『我的行程清單依時間排序』query；N < 50 估算 < 2KB，配額影響可忽略。Expense 不另建 index，靠 `smarttrip:expense:{tripId}:` key prefix scan，每 trip M < 200，可接受。」
- **壞答案長什麼樣**：「都加 index 比較快」「都不加 index 比較簡單」——沒看 query pattern + 配額限制。
- **別人會 push back 什麼**：Architect 可能說「以後資料量大了再加」。回應：「以後 = migration 一波。現在定 + 寫進 schema_version，未來改 index 結構走正規 migration 流程。」

## Q6. 「schema_version 怎麼帶？舊版資料怎麼 on-the-fly 升級？升不上去時怎麼提示使用者？」

- **為什麼問這個**：PRD 已註明多數功能上線，**已有 prod 使用者的 localStorage 裝著 v1 資料**。下次 release 改 schema（譬如 ItineraryItem 加 `category` enum），舊資料讀進來會炸。沒有 migration 策略 = 整批使用者資料消失 = 客訴爆。必須在 schema 階段就寫清楚 migration table 結構、rollback 行為、不能升級時的 UX。Dev 心智：純前端意味著**沒有 server-side migration window**，使用者打開 App 那一刻必須 on-the-fly 完成升級。
- **好答案長什麼樣**：「每筆記錄帶 `schema_version` 欄位；StorageAdapter 在 read 時偵測舊版並升級，migration table 為 `[{ from: 1, to: 2, transform: (record) => ... }]`。若新版有 bug，回退 client code 即可（舊 code 讀到 `schema_version > 自己支援上限` 時提示『請更新 App』，不破壞舊資料）。」
- **壞答案長什麼樣**：「應該不會改 schema 啦」「以後遇到再說」——這兩句是 data loss 的開場白。
- **別人會 push back 什麼**：Architect 可能說「pure-frontend 沒 server 哪有 migration」。回應：「migration 是『讀寫資料的契約變了』，不是『DB 操作』。前端有，後端也有。沒寫 = 第一次 release 翻車。」

## 送命題清單

這 3 題不問，三個月後維運會回來找你算帳：

1. **「localStorage 配額爆掉時，App 怎麼降級？」**
   瀏覽器 quota 預設 5MB，活躍使用者存 30 個 Trip + 1000 筆 Expense 就可能逼近。沒寫降級策略 = `QuotaExceededError` 直接讓存檔功能崩潰。最少要決定：(a) 自動 GC 最舊的 soft-deleted trip (b) 提示使用者「清空 30 天前的資料」(c) 直接拒絕新存檔。**這條會被 09-NFR 的 reliability SLI 引用。**

2. **「FxRate cache 的 TTL 多長？過期但 API 又掛掉時用哪個值？」**
   FxRate 不是 user data，是 cache。TTL 太短 → API 配額爆 + 成本失控；太長 → 燈號失準。必須明寫 `cached_until = as_of + 5min`，且過期 + API failure 時 fallback 到上次成功值並標 `data_source: simulated`（與 PRD P0-8「失敗時明確標示模擬」對齊）。**這條會被 14-runbook「FX provider 不可用」流程引用。**

3. **「fabricated assumption 有哪些？」**
   schema 上每個沒被 PRD/ADR 明寫、是 Dev 自己腦補的部分要標 `confidence: L` + 寫進 `self_review.lowest_confidence`。常見假設：「Expense.note 真的會有人用」「ItineraryItem.category 的 enum 值是 ATTRACTION/FOOD/TRANSPORT」「party_size 是 integer 不允許 2 大 1 小」。不標，三個月後團隊把它當事實引用，發現是空中樓閣時已經寫完 code。
