# 08 Data Model · 角色場景

## 這場會議在做什麼

ADR 拍板「localStorage-first、暫不接後端 DB」、API spec 把 `GET /api/v1/fx/rate` 與 `POST /api/v1/itinerary/generate` 的 request/response 定下來之後，
Dev 把後端與前端要持久化／快取的所有資料**一張一張畫成 entity**，把每個欄位的
**type / nullable / default / 索引 / PII 標記 / 保留政策**當場敲死。

**不是**架構選型會（那是 05-ADR），**不是**API 合約會（那是 07-API），
**不是**「之後寫 code 再決定」會。目的只有一個：
讓三個月後凌晨被 page 起來的 Dev（很可能就是你自己），能對著 ERD 找到
「為什麼這個欄位是 nullable」「為什麼這條保留 30 天」的決策依據。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Dev（主責，你）** | 07-API 的 response schema、實際 query pattern、過去踩過的 schema 雷 | 完整 ERD、每欄位含 type/null/default/index、migration 策略、保留政策 |
| **Architect** | 05-ADR 決策（為何 localStorage、為何不 IndexedDB）、上下游系統邊界 | 確認資料模型沒有違反架構約束（例如不能讓前端直接寫 DB） |

> **為什麼 Dev 主責、不是 Architect？**
> Architect 決定「資料住哪裡」，Dev 決定「資料長什麼樣」。
> 欄位 nullable / default / 索引這些決策的「會痛的人」是 Dev — 寫 code 的人、debug 的人、半夜 on-call 的人都是 Dev。
> Architect 在場是「確認沒越界」，不是主導。整個 03-design 階段如果 Architect 都當主責，
> Dev 會在 build 階段才第一次認真看 schema，那時改已經晚了。

## 你扮演的角色（Dev）

你不是「畫 ERD 給人看」，你是**未來查問題的人**。本場會議你要做三件事：

1. **每個欄位都問四件事**：type 是什麼？nullable 嗎？default 是什麼？要不要加 index？
   一個都不能跳過，跳過的那個欄位就是三個月後的 production NULL bug。
2. **每個關聯都標 cardinality + on_delete 行為**：1:N 還是 N:M？刪 Trip 時 Expense 怎麼辦？
3. **每個欄位都標 classification**：public / session_sensitive / PII，並且寫「retention 多久 / erasure 怎麼做」。
   就算 MVP 不存 email 也要做這件事 — destination + date 是行為資料，仍是隱私。

**禁忌動作**：本場會議不能講「**之後再說**」「**先這樣**」「**我們不會有問題**」這三句話。
一講就罰自己 100 元。理由：

- 「之後再說」= migration 來不及 + 沒人記得當初為何這樣寫
- 「先這樣」= 沒有 default 值 / nullable 沒想清楚 → prod NULL exception
- 「我們不會有問題」= 違反規則 4（破壞性分析） → 三個月後就會有問題

## 會議結束時，桌上要有什麼

- **完整 entity 清單**（SmartTrip MVP 預期 5 個：Trip / Day / Expense / FxRate / Recommendation），每個 entity 含：
  - 完整欄位清單，每欄位有 `type / nullable / default / constraints / classification / index?`
  - 主鍵與外鍵（即使是 logical FK 也要標明）
- **ER 圖**（Mermaid `erDiagram` 語法即可，能在 GitHub / Notion 直接渲染）
- **Normalization 決策表**：哪個 entity 走 denorm（嵌入）、哪個拆獨立 key、trade-off 是什麼
- **Migration 策略**：schema_version 怎麼帶、舊版資料怎麼 on-the-fly 升級、無法升級時怎麼提示使用者
- **Retention / Erasure 政策**：每個 session_sensitive 欄位多久 GC、「清空所有資料」按鈕清哪些 key
- **Decision log**：至少 3 條（denorm vs normalize、soft vs hard delete、index 加在哪裡）
- **自我審查清單**：列出 confidence `M/L` 的欄位 + 補洞計畫（誰、何時補）

## 為什麼這場會議重要

Data model 是整條 build 階段的**契約根節點**。下游每張卡都引用它：

- **11-unit-test**：每個 entity 的 schema validation test、每條關聯的 on_delete 測試、每個 migration 的「v1 → v2」測試都從這裡長出來
- **14-runbook**：「使用者反映行程消失」「localStorage 配額爆掉」「FX rate cache 髒資料」三類客訴的 runbook，第一步都是「對照 data model 找對應的 key pattern」
- **10-code-review-checklist**：schema migration review、PII 標記 review、index 必要性 review，這三條規則都是 data model 的延伸
- **12-release-plan**：含 schema 變更的版本，release 流程多一道「migration dry-run」關卡

跳過這場會議的代價：每個 Dev 自己腦補 schema → 同一個欄位三處不一致 →
某次 release 把 `amount` 從 number 改成 string，前端沒改，prod 三天後資料無法讀。
這不是「未來才會發生」，是「我們已經發生過」。

## SmartTrip FX 在本場會議的特殊點

| 特殊點 | 對會議的影響 |
|---|---|
| **localStorage 不是 RDBMS** | 沒有 FK 強制、沒有 transaction、沒有 prefix scan API → 所有「關聯」「索引」都是 application-enforced，需在 schema 上明寫由哪個 component 負責 enforce |
| **無帳號設計（PRD Non-Goals）** | 表面上「無 PII」，但 destination + date + mood + expense.note 仍是 session_sensitive — 不能因此跳過 classification |
| **schema 已上線**（PRD 註明多數功能已部署） | 任何 schema 改動都是 migration，不是 fresh start → migration_strategy 是硬需求，不是 nice-to-have |
| **FX rate 來自外部 API**（07-API spec 已定義） | FxRate entity 的 schema 必須與 API response 100% 對齊，否則前後不一致 |

跳過這場會議，等於把上面四個風險推給「下次 release 時的自己」— 而下次 release 的自己會非常恨現在的自己。
