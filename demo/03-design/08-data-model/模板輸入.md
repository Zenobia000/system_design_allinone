## ⚠️ 本卡注意事項（進 Claude 前先讀）

- **每個 entity 必含 audit 欄位**：`schema_version` + `created_at` + `updated_at` + `deleted_at`。即使在 localStorage 也不可省略 — schema migration 與 debug 都靠這幾個欄位。
- **localStorage 沒有 FK，但 logical FK 必須寫**。在 §Relationships 段標 `application-enforced`，並指明哪個 component 負責 enforce（如 StorageAdapter）。
- **normalization 決策看 query pattern + 寫入頻率，不是抄 3NF**。本案 ItineraryItem 嵌入 Trip（一起讀）、Expense 拆獨立 key（高頻寫），§Decision Log 要寫明這個 trade-off。
- **「無 PII」≠「不需要 data classification」**。session_id + 行程內容仍是 `session_sensitive`（被偷看可知何時不在家），仍需 retention + erasure 政策（GDPR right-to-erasure 等價於「清空所有資料」按鈕）。
- **ERD 用 Mermaid `erDiagram` 語法**，能在 GitHub / Notion 直接渲染；不要用 SQL 工具截圖。
- **§Migration Strategy 要寫死 migration table 結構**（如 `[{ from: 1, to: 2, transform: ... }]`）+ rollback 策略，否則半年後 enum 值改一改全炸。

### SRS / 功能規格

從 PRD User Stories 抓出的核心資料對象：

1. **Trip** — 一趟完整旅程方案（含目的地、日期、預算、選定的 Low/Mid/High tier、建議換匯額）
2. **ItineraryItem** — 行程中的單一項目（景點/餐廳/活動，標 cash/card + 預估金額）
3. **Expense** — 旅途中實際開支（cash/card + 金額 + 對應的 ItineraryItem 或自由項）
4. **FXRateCache** — FX rate 與 MA30 的客戶端快取（5 分鐘 TTL）

### Business rules

- 建議換匯額 = cash_only ItineraryItem 總額 × 1.1，依幣別進位（PRD P0-4）
- 三方案 tier 總額遞增，且各自 ≤ 該級距預算上限（PRD P0-2）
- 「換匯準確度」計算：實際現金 / 建議換匯，需在開支紀錄中累計（PRD §8）
- 法務：FX 燈號需「非投資理財建議」免責聲明
- **無使用者帳號 → 無真正的 PII**；但 session_id 與行程內容仍應視為「使用者敏感資料」
- Retention：localStorage 預設無上限；本案需主動定義「行程封存」策略以免配額爆掉

### 既有 ER / 資料分類政策 / 主要 query pattern

- 主要 query pattern：
  1. 列出「我的行程」清單（依 created_at desc，最多 50 筆）
  2. 打開單一 Trip 看完整 itinerary + expense
  3. 算「該 Trip 的實際現金 vs 建議換匯」誤差比
- 無跨 Trip 查詢、無聚合分析（屬 V2 個人化推薦）

### 上游卡輸出（API spec 摘要）

`07-api-spec` 已定 `FxRateResponse` schema：
- `{ base, quote, rate, ma30, deviation_pct, signal, as_of, cached_until, data_source, disclaimer }`
- 此 schema 是 FXRateCache entity 的 server-side 對應；本卡需確保兩者一致

### 上游卡輸出（C4 摘要）

`06-c4-diagram` 已定 C-3 `Browser LocalStorage` 容器，儲存 Trip / Expense / FXRateCache 三類資料。
本卡的任務是把這三類資料的 schema、關係、constraint 寫清楚。

## 替換成自己專案的方法

如果你不是要做 SmartTrip FX：

1. 跑 [`/start/`](http://localhost:3000/start/) 問卷 → 下載你自己的 `project-brief.md`，並跑完 [`03-prd/`](../../02-define/03-prd/模板輸入.md) + [`06-c4-diagram/`](../06-c4-diagram/模板輸入.md) + [`07-api-spec/`](../07-api-spec/模板輸入.md) 拿到上游輸出
2. 步驟 1（複製站上「完整範本」tab）**完全不動**
3. 步驟 2 的 trigger 結構不動；**只替換 `⏫` 上方的「上游文件」貼位區**（把 SRS / Business rules / Query pattern / API spec 摘要 / C4 摘要 5 個小節換成你自己的對應內容）
4. 如果你有真的 RDBMS（Postgres / MySQL），在「上游文件」段註明 storage layer 是 `table` / `materialized_view` 而非 `localStorage_key`，AI 會自動把章節結構調整為 RDBMS-friendly（含 DDL 草稿）
5. 貼到 Claude → 對比你拿到的結果與 [`實際結果.md`](./實際結果.md) 的「教學要點」與「常見錯誤」

> **為什麼步驟 1 不動？** 因為站上模板就是 single source of truth。版本升級（規則修訂、章節增刪）會自動同步到所有學生的下次產出，不需要去改舊的 demo 檔。
