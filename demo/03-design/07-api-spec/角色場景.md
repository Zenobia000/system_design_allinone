# 07 API Spec · 角色場景

## 這場會議在做什麼

C4 圖畫好後，每條跨 container 的線都需要一份**契約**——method 名、input schema、
output schema、錯誤碼、併發語意、版本策略，全部寫死。本場會議 60 分鐘，產出
**OpenAPI 3.x 風格的 API spec 文件**（即便 MVP 是 PWA 沒有 HTTP，也用同樣嚴謹度寫
local function 契約）。

**不是**寫實作會，**不是**討論 HTTP 還是 gRPC 的會，**不是**列功能清單會。
目的只有一個：**鎖死契約，讓 FE / BE / QA / Mobile 各自能獨立開發**——
契約一寫死，誰先寫完誰先測，不再需要「等對方做完」的相互阻塞。

> **API spec 的價值不在「文件齊全」，在「契約讓並行開發成為可能」**。
> 一份模糊的 spec 等於沒寫，並行開發退回串行，整個 sprint 慢一倍。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Architect（主責，你）** | 06-C4 圖、ADR 全套、08-data-model 草稿 | 一份簽核的 API spec + version 策略 + deprecation 流程 |
| **Dev（FE 1 人 + BE/Service 1 人）** | 實作經驗、SDK 偏好、debug 痛點 | 各自能獨立開發的 mock data + contract test 範本 |

> SmartTrip MVP 是純 PWA（無 server），所以本場「BE」由「行程規劃引擎 / FX Adapter / Storage
> Adapter 三個 logical container 的主責 Dev」代替。**契約嚴謹度不因『沒有 HTTP』而降低**。

## 你扮演的角色（Architect）

你是「**契約律師**」。本場會議你要做四件事：

1. 每個 endpoint / function call，**強迫團隊回答**併發行為（兩個 client 同時 call 怎麼辦？）
2. 每個寫操作，**強迫團隊回答**冪等性（重複 call 結果一樣嗎？）
3. 每個錯誤，**強迫團隊定義業務語意 code**（不准只寫 400/500，要分 400_INVALID_INPUT /
   422_BUSINESS_RULE_VIOLATION / 409_CONFLICT 等）
4. 強制定義**版本策略**與**deprecation 流程**——契約是會改的，但改的方式要事先約好

**禁忌動作**：本場會議**禁止**這幾種寫法，寫了就要重來：

- ❌ **「依需求調整」「之後再說」**——契約必須現在寫死，不准未來定
- ❌ **錯誤碼只有 200/500**——沒有業務語意 code 的 spec 是廢 spec
- ❌ **payload 寫「object」沒列欄位**——欄位 / 型別 / required 必須逐一列
- ❌ **沒寫 versioning 策略**——URL 版本（`/v1/`）vs Header 版本必選一條
- ❌ **沒寫 deprecation 流程**——未來改契約怎麼通知 client、給多久 grace period 要寫
- ❌ **沒寫併發 / 冪等性**——這兩條不寫，client 寫 retry 邏輯時會猜

## 會議結束時，桌上要有什麼

### API Spec 文件（必交）

每個 endpoint / function 至少含：

| 欄位 | 範例 |
|---|---|
| **Operation ID** | `trips.generate` |
| **Method / Path** | `POST /trips/generate`（或 local function `tripPlanner.generate()`） |
| **Description** | 一句話 |
| **Request schema** | 完整欄位列表 + 型別 + required + validation rule |
| **Response schema** | 完整欄位列表 + 型別 + nullable 標註 |
| **Error codes** | 業務語意 code 表（不只 HTTP status） |
| **Idempotency** | Yes / No + 若 Yes 用什麼 key |
| **Concurrency** | 同 user 多 tab 同時 call 怎麼辦？race condition 處理？ |
| **Version** | 屬於 v1 / v2 / unversioned-local |
| **Auth** | 需要什麼 credential？MVP 階段為 none |
| **Rate limit** | RPS / RPM 上限（即便 local 也建議標：避免 UI bug 無限迴圈打爆） |

### 全域策略（必交）

- **Versioning 策略**：URL 版本 vs Header 版本 vs Content negotiation，三選一
- **Deprecation 流程**：宣告 → grace period 長度 → sunset date → 強制下線，4 階段時程
- **錯誤碼字典**：所有業務 code 的完整列表（譬如 `FX_RATE_UNAVAILABLE`、
  `STORAGE_QUOTA_EXCEEDED`、`INVALID_CURRENCY_PAIR`⋯⋯）
- **Payload 向後相容規範**：加欄位 OK、刪欄位禁、改型別禁、加 enum 值要 client 容錯

### 附加產出

- **Mock data set**（給 FE 獨立開發用）
- **Contract test 範本**（給 11-unit-test 卡使用）
- 給 08-data-model 的「schema 對應表」（API schema vs DB/storage schema 的轉換規則）

## 為什麼這場會議重要

API spec 是整條 SDLC 的**並行開發解鎖鑰匙**。下游每張卡都靠它：

- **08-data-model**：schema 細節從 API spec 推導（API field → storage field 對應）
- **11-unit-test**：mock 從 spec 自動生成；contract test 用 spec 驗證
- **12-release-plan**：deprecation 流程決定 release window
- **13-deployment**：版本切換策略決定 rollback 機制
- **14-monitoring**：每個 endpoint 的 latency / error rate metric 從 spec 列
- **15-postmortem**：事故發生時看 spec 判定「是契約問題還是實作問題」

**跳過 API spec 的代價**：FE 跟 BE 互相問「你給我什麼」「我要送什麼」三個 sprint 走不完一個 feature。
更糟的是上線後客戶接 API 發現欄位跟文件不符，客戶整合工作量爆炸——這就是「契約律師」沒到場的代價。

## 本場示範主題

**SmartTrip FX MVP 的 5 個核心 endpoint（local function 契約）**：

1. `POST /trips/generate` — 行程生成（最複雜，含三方案計算）
2. `GET /fx/recommendation` — 換匯建議（依目的地與預算給金額）
3. `GET /fx/signal` — FX 燈號（STRONG_BUY / BUY / HOLD）
4. `POST /expenses` — 新增開支紀錄
5. `GET /trips/:id` — 讀取行程

**關鍵教學點**：MVP 是 **PWA + localStorage**，所以這 5 個「endpoint」其實是 **local function
契約**（譬如 `tripPlanner.generate(req)` 而非 `POST /trips/generate`）。本場示範會說明
**為什麼即便沒有 HTTP，仍要用 HTTP-style spec 寫**——為的是 V1 雲端化時的相容性，
也為的是強迫團隊用「契約思維」設計 interface，而非「函式呼叫思維」。
