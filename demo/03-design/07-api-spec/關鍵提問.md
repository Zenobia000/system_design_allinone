# 07 API Spec · 關鍵提問（Architect 必問）

> 本場會議 60 分鐘，Architect 只要把這 6 題 + 1 題送命題問完、問對，5 個 endpoint 就會被釘死。
> 不要問「大家覺得這 API 怎麼設計？」這種開放題——問題要**逼出契約細節**，不是逼出風格偏好。

---

## Q1. 「這個 endpoint 的**併發行為**是什麼？同 user 多 tab 同時 call，會發生什麼？」

- **為什麼問這個**：併發是 API 最容易踩雷的地方——使用者在兩個 tab 同時點「儲存」，
  結果哪個版本贏？兩個請求同時 call `POST /trips/generate`，會不會生出兩筆但 ID 衝突？
  這些**現場可重現**的 bug 必須在 spec 階段就回答，不能等出 incident 才補。
- **好答案長什麼樣**：
  - `POST /trips/generate`：**no concurrency conflict**（讀-生成-回傳，不寫 storage；
    寫由 client 另呼叫 `POST /trips/save` 完成）
  - `POST /trips/save`：**last-write-wins**（同 ID 後 call 覆蓋前 call；MVP localStorage 同步，
    瀏覽器同 tab 不會 race；多 tab 用 `lastModified` timestamp 比較，後者贏）
  - `POST /expenses`：**append-only**（每筆 expense 獨立 ID，無 conflict；併發新增兩筆等於兩筆）
- **壞答案長什麼樣**：「應該沒問題吧」「localStorage 是同步的不會 race」——多 tab 場景沒考慮。
- **別人會 push back 什麼**：Dev 會說「MVP 哪有人同時開兩個 tab 操作」。回應：
  「**有**。我們的目標族群 25–40 歲熟 web，比較行程／看燈號／記開支同時開三個 tab 是常見行為。
  你不在 spec 裡寫，FE 寫 retry 邏輯時會猜，QA 也不知道測什麼。**現在花 3 分鐘寫，未來省 incident**。」

## Q2. 「**冪等性**怎麼處理？同一個 request 重送，結果一樣嗎？要不要 idempotency key？」

- **為什麼問這個**：網路會丟包，client 會 retry。沒寫冪等性 = client 不敢 retry = 使用者看到
  「載入失敗」就放棄。讀操作天然冪等（GET），但寫操作（POST / PUT / DELETE）必須明示
  冪等性策略：(a) 天然冪等（譬如「設定欄位 X = Y」）(b) 需要 idempotency key（譬如建立資源）
  (c) 不冪等（譬如「累加 counter」）。
- **好答案長什麼樣**：
  - `POST /trips/generate`：**天然冪等**（純計算，同 input → 同 output）。**但有副作用**：
    會送 analytics event；可加 `clientGenerationId` UUID 去重，30 秒內重複請求不重複計 metric
  - `POST /trips/save`：**用 trip.id 為冪等 key**（client 生成 UUID）。同 ID 重送 = 覆蓋（idempotent）
  - `POST /expenses`：**用 `expense.id`（client UUID）為冪等 key**。同 ID 重送 = noop，不重複新增
- **壞答案長什麼樣**：「retry 失敗顯示錯誤就好」——使用者體驗砍半。
- **別人會 push back 什麼**：Dev 會說「localStorage 不會 timeout，幹嘛搞冪等？」回應：
  「**為 V1 開後門**。MVP local function 確實不需要，但 V1 變 HTTP endpoint 就需要。
  契約現在就寫『接受 idempotency key』，V1 上線無痛切換。」

## Q3. 「**錯誤碼**怎麼分？400 / 422 / 409 / 503 各代表什麼業務語意？必須有 code 字典。」

- **為什麼問這個**：HTTP status code 只是「class」，業務 code 才是「diagnosis」。
  400 = client 送錯（typo），422 = client 送對但違反業務規則（餘額不足），409 = conflict
  （重複 ID），503 = 系統暫時不可用。client 寫錯誤處理 UI 時需要知道**該對使用者說什麼**——
  「您輸入的內容有誤」（400）vs「您的預算不足」（422）vs「請稍後再試」（503）。
  沒有 code 字典 = UI 寫死「發生錯誤」一句話，使用者罵到爆。
- **好答案長什麼樣**：
  - **400 INVALID_INPUT**：欄位 typo / 型別錯（譬如 `budget` 送字串）
  - **400 MISSING_REQUIRED_FIELD**：缺必填（譬如沒送 `destination`）
  - **422 INVALID_CURRENCY_PAIR**：幣別合法但組合不支援（譬如 USD → 古巴幣）
  - **422 BUDGET_OUT_OF_RANGE**：預算 < 1000 或 > 1000000（業務規則）
  - **409 TRIP_ID_CONFLICT**：trip.id 已存在但內容不一致（非 idempotent 重送）
  - **503 FX_RATE_UNAVAILABLE**：FX provider 三家都失敗、cache 也過期
  - **507 STORAGE_QUOTA_EXCEEDED**：localStorage 5MB 滿了
- **壞答案長什麼樣**：「成功 200、失敗 500」——client 無法針對性處理。
- **別人會 push back 什麼**：Dev 會說「分這麼細，code 寫起來很煩」。回應：
  「**code 是 server 寫一次，client UI 受益 N 次**。每個業務 code 對應一段使用者語言訊息，
  使用者體驗差別在這。**這是 ADR-001『非投資理財建議』之類法規邊界的延伸——錯誤訊息精準才不會誤導**。」

## Q4. 「**版本策略**是 URL 版本（`/v1/`）還是 Header 版本？deprecation 流程怎麼走？」

- **為什麼問這個**：API 一定會改。問題是「改的時候 client 怎麼辦」。URL 版本（`/v1/trips` →
  `/v2/trips`）優點是直觀、可同時共存；Header 版本（`Accept: application/vnd.smarttrip.v2+json`）
  優點是 URL 乾淨、容易做漸進升級。**選哪個次要，重點是選一個並寫進去**。沒寫 = 第一次要改
  API 時就吵架。**Deprecation 流程**更重要：宣告 → grace period → sunset → 強制下線，每個
  階段給多久？通知 client 的方式是什麼？
- **好答案長什麼樣**：
  - **版本策略**：**URL 版本**（`/v1/`）。理由：(1) 對未來 OpenAPI 工具相容 (2) 直觀
    (3) client 切版本就改 URL，不需改 SDK
  - **Deprecation 流程**：
    1. **Announce**（T-90 天）：在 docs 標 `deprecated`，response 加 `Sunset` header
    2. **Grace period**（T-90 ~ T-0）：舊 endpoint 仍可用，但 response 加警告
    3. **Sunset date**（T+0）：舊 endpoint 回傳 410 Gone + 指引新 endpoint
    4. **強制下線**：30 天後完全移除
  - **MVP 階段**：所有 endpoint 標 `v1`，即便目前是 local function。V1 雲端化時轉成 HTTP `/v1/...`，
    版本不變—— 因為 schema 在 ADR-001 已預留兼容欄位
- **壞答案長什麼樣**：「先不分版本，之後再說」——之後沒人記得約定。
- **別人會 push back 什麼**：Dev 會說「MVP 是 local function 哪需要版本？」回應：
  「**spec 上要標**。local function 也有版本——`storageAdapter.saveTrip` 的 input schema 升級了，
  舊版怎麼辦？localStorage 裡存的是哪個版本的 schema？這就是 ADR-001 預留的 `schemaVersion` 欄位
  的用途。」

## Q5. 「**Payload 向後相容**規範是什麼？哪些改動允許、哪些禁止？」

- **為什麼問這個**：契約一旦寫死，每次改動要先問「會不會破壞既有 client」。**加欄位**通常 OK
  （舊 client 忽略新欄位）；**刪欄位**或**改型別**通常**禁止**（舊 client 拿不到欄位或解析失敗）；
  **加 enum 值**要小心（舊 client 若沒寫 default case 會炸）。這套規範要寫在全域，每個 spec
  改動都依據它判斷。
- **好答案長什麼樣**：
  - ✅ **加欄位**：OK（必須是 optional，舊 client 忽略）
  - ✅ **加 endpoint**：OK（新 client 用，舊 client 不知道）
  - ❌ **刪欄位**：禁止（需走完整 deprecation 流程才能刪）
  - ❌ **改欄位型別**：禁止（譬如 `budget: number` → `budget: string` 直接炸）
  - ⚠️ **加 enum 值**：需事前公告，client 必須寫 default case 容錯
  - ❌ **改 required**：optional → required 禁止（舊 client 沒送會被擋）
  - ✅ **required → optional**：OK（鬆綁不破壞）
  - ❌ **改 endpoint URL**：禁止（用 deprecation 流程做新 endpoint，舊的保留）
- **壞答案長什麼樣**：「需要改就改」——上線後客訴爆炸。
- **別人會 push back 什麼**：Dev 會說「MVP 階段反正沒外部 client，隨便改」。回應：
  「**MVP 也有 client——就是你自己的 PWA Shell 跟 storage 裡的舊資料**。改 schema 沒 migrate
  資料，使用者打開 app 看到行程消失，這就是 V1 雲端化的預演。**現在養成習慣，未來省 incident**。」

## Q6. 「每個 endpoint 的 **rate limit / quota** 是多少？即便 local function 也要標。」

- **為什麼問這個**：rate limit 不只是「防 DDoS」，更是「防自己」——UI bug 寫成無限迴圈打爆
  backend、或無限 fetch 打爆外部 API quota，這些都是 spec 應該保護的場景。即便 local function
  也應該標（譬如 `tripPlanner.generate` 每秒最多被 call 5 次，防 React 重渲染風暴）。
- **好答案長什麼樣**：
  - `POST /trips/generate`：**5 RPS per session**（防 UI bug 重渲染風暴）
  - `GET /fx/recommendation`：**10 RPS per session**（FX cache 內可高頻；穿透 cache → adapter
    層限 1 RPS to provider）
  - `GET /fx/signal`：**同上**
  - `POST /expenses`：**20 RPS per session**（允許批次新增）
  - `GET /trips/:id`：**unlimited**（純讀本地）
  - **External quota（給 FX Adapter）**：Wise API 1000 req/day（免費 tier）→ adapter cache 24h
    可降到 ~50 req/day
- **壞答案長什麼樣**：「沒 rate limit」——UI bug 一上線就燒 API quota。
- **別人會 push back 什麼**：Dev 會說「PWA 怎麼可能打爆？」回應：
  「**React 18 的 strict mode 會 double render；useEffect 依賴錯就無限迴圈**。spec 寫 rate limit
  不是怕惡意攻擊，是怕自己手滑。external quota 那條更重要——Wise 免費 tier 用爆要付錢。」

## 送命題清單

這 1 題不問，3 個月後上線發生 incident 時找不到根因：

1. **「每個 endpoint 的 mock data 在哪？FE 能不能**今天下午就**用 mock 開始寫畫面？」**

   API spec 的終極驗證是「FE 拿著 spec 能不能獨立開發」。如果不行，spec 不夠完整。
   每個 endpoint 應附 **2–3 組 mock response**：(1) 成功 happy path (2) 業務錯誤
   （譬如 `BUDGET_OUT_OF_RANGE`）(3) 系統錯誤（譬如 `FX_RATE_UNAVAILABLE`）。
   附在 spec 文件裡，FE 拿到就能 `npm install msw` 跑起來，**串接前完成 80% UI**。

   **判準**：FE 在會議結束後 2 小時內，能 commit 第一個 mock-based PR。做不到 = spec 不完整。

   **常見漏項**：(a) 錯誤狀態的 response shape 沒定義（FE 不知道 error 物件長怎樣）
   (b) 列表型 API 沒定義 empty / pagination 邊界 (c) optional 欄位沒給 `null` 與 `missing`
   兩種 mock。
