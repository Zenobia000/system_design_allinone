# 09 Non-Functional Requirements · 關鍵提問（DevOps 必問）

> 本場會議 60 分鐘，DevOps 只要把這 6 題問完、問對，會議就成功了。
> 不要問「大家覺得幾個 9 比較好？」這種開放題——問題要**逼出數字**，不是逼出意見。
> 每個 NFR 的目標值、量測方式、alert 閾值、降級行為都要在這場會議裡定下來。

---

## Q1. 「這條 NFR 的 SLO 目標是多少？怎麼從業務目標推導出這個數字？」

- **為什麼問這個**：NFR 最常見的爆炸是「目標數字憑感覺」。寫「response time < 1s」沒分 p50/p75/p95；寫「99.9% uptime」因為「大家都這樣寫」；寫「成本越低越好」。這些都是廢話 — 上線後沒人會用這些「目標」做決策。DevOps 心智：**每個數字要能對外回答「為什麼是 2.5s 不是 3s、不是 1s」**。種子簡報「3 分鐘」是業務目標，拆成「LCP < 2.5s + 表單填寫 90s + 讀結果 60s + 保存決策 30s」才是 SLO。
- **好答案長什麼樣**：「`page_load_lcp_p75 < 2.5s`，依據：種子簡報期望成果『3 分鐘內拿到結果』拆解 — 假設 /start 表單 90s、讀三方案 60s、保存 30s，前端可用 LCP 預算為 ≤ 2.5s × 多次頁面切換。」
- **壞答案長什麼樣**：「越快越好」「< 1s 比較專業」「大家都寫 99.9% 我們也跟」——三個都是定時炸彈。
- **別人會 push back 什麼**：Architect 可能說「我們 MVP 4 週驗證窗，這麼細沒必要」。回應：「現在不細，release 時對 LCP 退化沒共識 → 沒人攔得住 → 使用者抱怨 → 4 週驗證白做。每條 SLO 都要對應一個 release gate。」

---

## Q2. 「這條 SLO 怎麼量測？取樣窗口多長？工具是什麼？」

- **為什麼問這個**：SLO 沒有 SLI 是廢話。寫「99.9% availability」沒寫「以什麼 probe、什麼間隔、什麼 endpoint」就無法判斷 incident 發生時系統「合不合 SLO」。**沒量測 = 沒問責**。SmartTrip MVP 是 PWA，傳統 server-side monitoring 工具大半不適用 — 必須用 RUM（Real User Monitoring）+ synthetic probe 雙軌。
- **好答案長什麼樣**：「SLI = `page_load_lcp_p75`；工具 = Vercel Speed Insights（RUM 自動收 web vitals）+ Lighthouse CI（每 PR 跑 mobile profile + slow-4G）；窗口 = 28 天 rolling（Google Core Web Vitals 對齊）。」
- **壞答案長什麼樣**：「Grafana 看一下就好」「monitoring 之後接」——沒寫工具名、沒寫取樣窗口、沒寫 percentile。
- **別人會 push back 什麼**：Architect 可能說「Vercel 自帶報表就夠了吧」。回應：「自帶報表 ≠ alert。我們要的是『LCP 退化』能在 alert channel 喊出來，不是『要看時去 dashboard 翻』。寫死工具 + 窗口 + 觸發條件。」

---

## Q3. 「破了 SLO 的閾值是多少？發 alert 給誰？怎麼降級？」

- **為什麼問這個**：SLO 與 alert threshold 是兩件事。SLO 是「目標達成度」，alert threshold 是「破到什麼程度該爬起來」。沒有 alert threshold 的 SLO 是 dashboard 裝飾品 — 不會有人去看。**每條 SLO 都要對應「破閾值之後該做什麼」的劇本**，否則 alert 響了第一次大家研究，響第二次大家麻木，響第三次 mute 通知。
- **好答案長什麼樣**：「`fx_endpoint_success_rate < 99% in last 1h` → Slack #alerts → on-call 開 14-runbook『FX provider 不可用』；如 source = simulated 比例 > 10%，視為早期警告 → Slack #perf（不 page）。」
- **壞答案長什麼樣**：「破了就 email」「Slack 設一個 channel 收就好」——沒寫 routing、沒寫降級行為、沒寫嚴重度區分。
- **別人會 push back 什麼**：Architect 可能說「MVP 階段沒 24x7 on-call，alert 給誰？」回應：「best-effort 也要寫 routing。寫『個人專案 → 寄 PM 信箱 → 24h 內回應』也算 SOP；沒寫 = 真出事誰都沒責任。」

## Q4. 「這個 NFR 的『不可用』降級行為是什麼？fallback 到哪個狀態？」

- **為什麼問這個**：MVP 不可能保證每個依賴都 100% 可用 — FX provider 會掛、Vercel 會偶發 5xx、analytics vendor 會 rate-limit。**沒寫 fallback = 預設行為 = 全掉**。SmartTrip 的 FX 燈號完全依賴上游 API，若 API 掛而沒 fallback，整個「省錢」護城河斷掉。DevOps 心智：「good failure mode」是把 incident 從「全停」變成「部分降級」，使用者拿到 actionable response 比例不掉。**graceful degradation 是 PRD P0-8 驗收標準，不是 nice-to-have**。
- **好答案長什麼樣**：「FX provider 全掛時，FxRate.source = simulated（用上次成功值 + 標明『模擬』），UI 強制顯示『目前匯率資料暫時不可用』+ 維持原免責聲明；此時 `fx_endpoint_success_rate` SLI 不扣分（fallback 是『good failure mode』）。」
- **壞答案長什麼樣**：「FX API 掛了就顯示錯誤頁」「使用者重試吧」——使用者出國前 24 小時看到錯誤頁，這個 App 就死了。
- **別人會 push back 什麼**：SA 可能說「fallback 用快取值算不算金融建議？法務有疑慮。」回應：「就是因為有疑慮才要強制顯示『模擬』標籤 + 維持免責聲明。寫進法規 NFR 段。」

## Q5. 「Monthly cost 上限是多少？哪個 metric 驅動成本？超了怎麼辦？」

- **為什麼問這個**：MVP 不設 cost ceiling = 4 週驗證後收到帳單嚇死 = 整個 V1 規劃被「先還債」打斷。種子簡報沒明寫財務上限，但**個人專案 + 4 週驗證窗的合理推論是 < NT$2,000/月**。沒寫，FX provider 從 free tier 升到 paid tier 沒人攔；CDN 流量爆但 alert 沒掛；Plausible 事件數爆但沒 vendor 切換劇本。**cost 是 NFR 的硬指標**，不是「會計部問再說」。
- **好答案長什麼樣**：「Monthly cost ceiling = NT$2,000；driver metrics = (a) FX provider monthly request count（free tier 上限 1000/day）(b) Vercel bandwidth（100GB free tier）(c) Plausible events count；超 ceiling 80% 警示 → 評估 vendor 切換；超 100% → 強制切 free tier 替代品或暫停 service。」
- **壞答案長什麼樣**：「先用 free tier 啊不用想」——free tier 爆了就會自動升 paid，悄悄扣信用卡。
- **別人會 push back 什麼**：Architect 可能說「個人專案哪有預算」。回應：「正因為個人專案，超預算 = 真實扣自己錢。比企業案還需要 ceiling。」

## Q6. 「合規與法規清單是什麼？哪些『不適用』也要寫原因？」

- **為什麼問這個**：種子簡報明寫「FX 換匯燈號需要『非投資理財建議』免責聲明」— 這是**硬要求**，不寫 = release 退件。除此之外 GDPR / 個資法 / PCI / PWA 權限說明等項目，**每個都必須標『適用 + 控制 / N/A + 原因』**。寫「N/A」沒寫原因，下次法務問起來啞口無言；漏列任一條，release 前才被 SA 退件。DevOps 心智：合規是「release gate」，不是「合規部的事」。
- **好答案長什麼樣**：
  - **GDPR Art.17**: 適用；對應控制 = 設定頁「清空所有資料」按鈕（08-data-model erasure 段）
  - **金融商品免責**: 適用；對應控制 = `Recommendation.disclaimer_shown` 強制 true 才能 render 燈號 component
  - **PCI**: N/A；原因 = 不處理任何信用卡資料（PRD Non-Goals 延伸）
  - **PWA 離線權限說明**: 適用；對應控制 = manifest.json + 首次使用引導頁說明 localStorage 用途
- **壞答案長什麼樣**：「合規讓法務看吧」「全寫 N/A 比較快」——前者是甩鍋，後者是裝睡。
- **別人會 push back 什麼**：SA 可能說「免責聲明加上去使用者體驗變差」。回應：「燈號顯示 + 免責是 PRD P0-5 與種子簡報明示的硬要求。可以調 UI 樣式，不能拿掉。寫進 a11y + 法規 NFR。」

## 送命題清單

這 3 題不問，上線後第一個月會回來找你算帳：

1. **「FX provider 全掛 1 小時，algorithm 怎麼判斷『要不要扣 error budget』？」**
   這是 SRE 哲學的核心。若計入 = 一次小事件就燒光 monthly error budget；若不計入 = SLO 變裝飾品。正解：**fallback 機制能正常運作就算 success**（user-centric SLI），上游成功率另外用獨立 SLI `fx_provider_upstream_success` 追蹤（不掛 alert，純觀察）。**這條會被 12-release-plan 引用為「success SLI 不能用上游成功率」的決策依據。**

2. **「無帳號 = 沒 auth 漏洞？那 XSS、CSP、API key 外洩怎麼防？」**
   無帳號**只是降低 auth attack surface**，不等於零安全風險。SmartTrip 的攻擊面：(a) Expense.note 自由文字 → XSS（必須前端 sanitize + CSP header）(b) FX provider API key 不能寫在 client（必須走 Vercel env var + server function proxy）(c) Plausible 雖匿名但事件污染 → rate limit。沒寫，第一次 OWASP scan 就會收到 H 級 finding。**這條對應 10-code-review-checklist「security」維度。**

3. **「fabricated assumption 有哪些？」**
   NFR 上每個沒被 PRD / 種子簡報 / 實測支持的數字，是 DevOps 自己腦補的部分要標 `confidence: L` + 寫進 `self_review.lowest_confidence`。常見假設：「100 DAU baseline」（PRD §9 Open Question 第 5 條明寫無歷史基準）、「FX provider p95 < 300ms」（vendor 未拍板）、「monthly cost < NT$2,000」（個人專案推論）、「mobile 4G 是 baseline」（PRD 未明說）。不標，下次 incident 發生時對著一個錯誤 baseline 比較會做出錯誤決策。
