# 09 Non-Functional Requirements · 角色場景

## 這場會議在做什麼

PRD 已寫完 P0-P2 功能、08-data-model 已敲定 schema 之後，DevOps 召集 Architect 與 SA
把所有「**非功能**」需求一次釘死：**性能、可用性、安全、成本、合規、法規** —
每一條都帶 SLO 目標 + SLI 量測指標 + 觸發 alert 的閾值 + 降級行為。

**不是**架構設計會（那是 05-ADR），**不是**功能需求會（那是 03-PRD），
**不是**「先上線再說，NFR 之後補」會。目的只有一個：
讓凌晨 3 點被 alert 叫醒的 DevOps（很可能就是你自己），對著文件能立刻判斷
「這個指標跨閾值該不該真的爬起來處理」「沒爬起來會被誰罵」。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **DevOps（主責，你）** | 過去 on-call 痛經歷、雲服務帳單、監控工具能力清單、降級操作手冊雛形 | 完整 NFR 清單、每條含 SLO + SLI + threshold + alert routing、cost ceiling、降級劇本 |
| **Architect** | 05-ADR 決策（為何 localStorage、為何選 Vercel）、上下游依賴 SLA、容量假設 | 確認 NFR 與架構選型一致（譬如 99.9% 對 Vercel free tier 是否現實） |
| **SA** | 種子簡報「主要約束」、PRD §9 Open Question、法務／個資疑慮整理 | 把「免責聲明」「PWA 權限」這類軟需求轉成可驗證的 acceptance criteria |

> **為什麼 DevOps 主責、不是 Architect？**
> Architect 決定「系統長什麼樣」，DevOps 決定「系統壞了誰負責、怎麼負責、什麼時候該 alert」。
> NFR 的每個閾值都要對應一個「跨閾值之後該做什麼」的劇本——那是 DevOps 的世界。
> Architect 在場是「驗證 SLO 對得起架構選型」，不是主導。整個 design 階段如果 Architect 三張卡都當主責，
> NFR 容易被當「規格附錄」而不是「運維契約」。

## 你扮演的角色（DevOps）

你不是「列一張 NFR 清單交差」，你是**凌晨 3 點會被叫醒的人**。本場會議你要做三件事：

1. **每條 NFR 都問四件事**：目標數字是多少（SLO）？怎麼量（SLI）？破了發 alert（threshold）？破了怎麼降級（runbook 入口）？
   一個都不能缺。缺其中一項，那條 NFR 就是廢話 — 上線後沒人會去看。
2. **每個 threshold 都要有「為何此值」的推導**：不能寫「99.9% 因為大家都這樣寫」、不能寫「< 1s 因為合理」。
   推導鏈條：種子簡報 → PRD 業務目標 → 推出數字。
3. **每個降級行為都要有對應的 runbook 入口**：FX API 掛了切 simulated；localStorage 爆 quota 引導 GC；
   monthly cost 過 ceiling 切 free tier vendor。沒有 runbook 入口的 NFR 是裝飾品。

**禁忌動作**：本場會議不能講「**越快越好**」「**越穩越好**」「**合理範圍**」「**之後監控起來再說**」這四句話。
一講就罰自己 100 元。理由：

- 「越快越好」= 沒上限 → 永遠不滿足 → 永遠不通過 release gate
- 「越穩越好」= 沒 SLO → 沒 error budget → 沒法判斷何時該停下優化效能
- 「合理範圍」= 沒數字 → 上線後對 incident 沒共識 → 半夜 PM 跟 DevOps 吵架
- 「之後監控起來再說」= 監控本身就是 NFR 的一部分，現在不定，上線之後就沒人想做了

## 會議結束時，桌上要有什麼

- **六大類 NFR 全覆蓋**（性能 / 可用性 / 安全 / 成本 / 合規 / 法規），**每類至少 1 條**完整 NFR：
  - SLO（目標數字 + 推導依據）
  - SLI（量測指標名稱 + 取樣方式）
  - threshold（破了發 alert 的數字 + alert routing 到誰）
  - 降級行為（runbook 入口或標明「TODO: 14-runbook 補」）
- **Cost ceiling**：MVP 4 週驗證窗的月費上限（譬如 FX API NT$2,000、CDN NT$0）+ driver metric（隨什麼線性成長）
- **降級劇本對照表**：常見 3 種 incident（FX API 全掛、localStorage 爆 quota、cost 超 ceiling）對應的 runbook 入口
- **合規清單**：GDPR / 個資 / 金融商品免責 / PWA 權限說明，每條標「適用 / N/A + 原因」
- **Decision log**：至少 3 條（為何不抄業界數字、為何把 fallback 算 success、為何選 99.5% 不選 99.9%）
- **自我審查清單**：confidence `M/L` 的數字 + 補洞計畫

## 為什麼這場會議重要

NFR 是整條 build / release / operate 階段的**運維契約根節點**。下游每張卡都引用它：

- **10-code-review-checklist**：每條 SLO 都對應一條 PR review 規則（譬如「new endpoint 必須有 latency budget 標註」「new dependency 必須有 vendor cost impact」）
- **12-release-plan**：每條 NFR 都對應一個 release gate（譬如「LCP p75 < 2.5s 才能合 main」「成本預估超 ceiling 必須改 vendor」）
- **14-runbook**：每條降級行為都長成一份 runbook（譬如「FX provider 全掛標準作業流程」「localStorage quota 客訴處理」「cost 超 ceiling vendor 切換」）
- **15-postmortem**：incident 發生後判定「是不是真的需要重新檢視 NFR」的基準

跳過這場會議的代價：上線後第一週 FX API 掛 3 小時，沒人知道該不該 page 開發者；
第二個月 vendor 帳單超預期 5 倍，PM 問「我們設過 ceiling 嗎」，DevOps 啞口無言；
release 時 LCP 退化但沒 gate，使用者抱怨頁面慢，但沒人攔得住那次 release。
**這些都不是「之後補」可以救回來的傷害**，因為事件發生時沒共識基準，事後再寫 NFR 是亡羊補牢。

## SmartTrip FX 在本場會議的特殊點

| 特殊點 | 對會議的影響 |
|---|---|
| **MVP 4 週驗證窗**（種子簡報 §主要約束） | 99.9% 等業界數字不適用 — driving 高 SLO 的 ops effort 應改投資「驗證假設的功能」。本案 99.5% 才合理。 |
| **FX 燈號需要免責聲明**（種子簡報硬要求） | 合規不是 nice-to-have，是發 release 前的 gate。disclaimer 漏掛 = 法務退件 = 整批 release 回滾 |
| **無帳號設計** | 表面降低 auth 攻擊面，但 XSS（Expense.note 自由文字）仍是 attack vector — security 段不能因為「無 PII」而跳過 |
| **localStorage 5MB 配額** | 容量規劃不是 server-side capacity planning（沒 server），而是「PWA 用戶端 quota 防爆」 — 這是 DevOps 在 PWA 時代的新功課 |
| **PRD §10 註明已上線** | NFR 不是「綠地設計」，是「對已上線系統補運維契約」 — 每條 SLO 都要有 staging 環境的實測 baseline，不能憑空猜 |

跳過這場會議，等於把上面五個風險推給「下次 incident 發生時的自己」— 而下次 incident 發生時的自己會非常痛恨現在的自己。
