## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 SmartTrip FX 的可用性目標是 99.5% 而不是 99.9%？

`decision_log` 第一條寫得很清楚：**沒有付費客戶、沒有 SLA penalty，99.9% 等於把 90% error budget 留給自己過度優化**。

學生最常見的錯誤是「99.9% 因為大家都這樣寫」（規則 3 明文禁止）。NFR 的 threshold 必須**從 business impact 推導**：

- 4 週驗證窗的核心目標是「驗證假設」，不是「ops 完美」
- 若驗證通過進 V1（PRD §10），SLO 可重新評估升級

「先快速驗證、再嚴格收緊」是 startup 思維，**vs 「先抄業界、再痛苦達標」是 enterprise 病**。

### 2. 為什麼把 fallback to simulated 算作「success」？

`decision_log` 第二條：**graceful degradation 是 PRD P0-8 驗收標準**。

如果 FX provider 掛 1 小時，FX endpoint 仍然「正確回應 502 + UI 切 simulated 模式」，使用者依然能完成行程規劃。這是「good failure mode」，不該扣 error budget。

我們應該量「**使用者拿到 actionable response 的比例**」而非「上游成功比例」。這個區分是 SRE 哲學（user-centric SLI vs implementation-centric SLI）的核心。

### 3. 為什麼「無 PII」的專案還要寫 GDPR / privacy？

種子簡報沒收集 email / 信用卡，但 NFR 卡還是列出 `privacy.pii_inventory`：

- destination + dates 是「行為資料」
- mood + note 是「敘事資料」
- session_id 是「準識別碼」（可跨事件關聯）

GDPR 不只管姓名身分證 — **凡能識別自然人的資料皆受規範**。「清空所有資料」按鈕（08-data-model 的 erasure 設計）就是 GDPR Article 17 right-to-erasure 的對應控制。

學生若寫「無 PII 故 GDPR N/A」會在合規審查時被退件。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |

| `latency_targets.page_load_lcp_p75` | `10-code-review-checklist/` performance 維度 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 寫「response time < 1s」沒分 p50/p75/p95/p99 | 規則 7 SLI 必須可量測 | 至少寫一個 percentile（推薦 p75 for UX、p95 for ops） |
| 抄「99.99% availability」 | 規則 3 不抄業界 | 從 business impact 推導，本案無 SLA、無 penalty → 99.5% 合理 |
| 把 fallback to simulated 算 failure | UX vs implementation SLI 混淆 | 量「使用者拿到 actionable response 比例」而非「上游成功比例」 |
| `compliance_obligations` 全寫「N/A」沒解釋 | 規則 4 | 任一不適用要寫原因（如「PCI N/A — 不處理信用卡」） |
| 沒寫 `operability.alerting` 的 threshold | 規則 7 NFR 必須對應監控 | 每條 SLI 都要有對應 alert（哪個指標跨哪個 threshold 觸發） |

## 交件 checklist

- [ ] Latency / Availability / Scalability / Reliability / Security / Privacy / Compliance / A11y / Cost / Operability 九象限全部 covered（N/A 也要寫原因）
- [ ] 每條 SLI 都有 SLO target + measurement + test_method + source
- [ ] 每條 SLI 都對應一個 alert threshold（或明寫「不告警，原因」）
- [ ] `decision_log` 至少一條解釋為何不抄業界數字
- [ ] GDPR / privacy 段就算「無 PII」也要寫 session_sensitive 資料清單 + erasure 流程
- [ ] `out_of_scope` 至少 3 條（第三方 SLA、DR、客戶端 a11y）
- [ ] 每個 `confidence: M/L` 對應 `self_review.lowest_confidence` 一條補洞計畫
- [ ] threshold 數字都有「為何此值」推導，不留裸數字
