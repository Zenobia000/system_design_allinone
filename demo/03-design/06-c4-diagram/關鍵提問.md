# 06 C4 Diagram · 關鍵提問（Architect 必問）

> 本場會議 75 分鐘，Architect 只要把這 6 題 + 1 題送命題問完、問對，三層 C4 圖就會自然長出來。
> 不要問「大家想怎麼切？」這種開放題——問題要**逼出邊界依據**，不是逼出畫法。

---

## Q1. 「Context 層裡，**誰是 actor、誰是 external system**？兩個角色不准混。」

- **為什麼問這個**：很多人畫 C4 的第一個錯誤就是把「Google Maps」當 actor 畫——Google Maps
  不是 actor，是 external system。actor 是**會主動發起 use case 的人或外部系統**（譬如使用者、
  排程器、batch system），external system 是**被我們呼叫的服務**（譬如第三方 API、第三方 DB）。
  混在一起，下游 trust boundary（10-threat-model）會分不出哪邊要驗證、哪邊要授權。
- **好答案長什麼樣**：
  - Actor：「衝動型旅客（25–40 歲）」「首次自由行新手」——對應 PRD §4 兩個 persona
  - External system：「FX rate provider（Wise API / 台銀公開 API）」「Google Maps Places API」
    「Analytics service（Plausible / PostHog）」——對應 PRD §6 P0-5/P0-8/P0-9
  - 每個 actor 標**主要 use case**（旅客 → 生成行程；新手 → 看燈號）
- **壞答案長什麼樣**：「使用者跟我們的系統」——沒分 persona、沒列 external、太籠統。
- **別人會 push back 什麼**：Dev 會說「Plausible 也是被我們呼叫，為什麼是 external system 不是 actor？」
  回應：「actor 是『**發起 use case 的主體**』。Plausible 不主動找我們，是我們把 event 送過去——
  它是 external system。**判準是『呼叫方向誰主動』**。」

---

## Q2. 「Container 邊界**依據是什麼**？同一 deploy unit / 同一資料生命週期 / 同一團隊，三選一。」

- **為什麼問這個**：container 邊界是 C4 圖最容易畫錯的地方。三個正當依據是：
  (a) **同一 deploy unit**（譬如同一個 PWA bundle、同一個 Docker image）
  (b) **同一資料生命週期**（譬如「行程資料 + 行程相關的 cache」歸同一個 container）
  (c) **同一團隊歸屬**（Conway's Law——團隊邊界 = 系統邊界）
  少了依據，container 切分就是「我覺得這樣切比較順」——這在學員質疑時會崩盤。
- **好答案長什麼樣**：「**PWA Shell** 與**行程規劃引擎**雖然功能不同，但都打包進同一個
  JS bundle、deploy 到同一個 Vercel project → **依據 (a) 同一 deploy unit** → 同一 container？
  ⋯⋯**但**行程規劃引擎是 pure function logic、PWA shell 是 UI/routing，**團隊未來想拆兩個人維護**
  → 採依據 (c) **拆成 2 個 container**。標『邏輯 container』（runtime 同一個 bundle，邏輯邊界仍分開）。」
- **壞答案長什麼樣**：「FE / BE 分開」——這是技術分層不是 container 邊界依據。FE 內部也有多 container。
- **別人會 push back 什麼**：Dev 會說「都打包同一個 bundle 還分什麼 container？」回應：
  「container 不等於 runtime。是**邏輯邊界 + 部署單位**的合體。同 bundle 不同 logical container
  在 7 卡寫 API spec 時意義重大——跨 logical container 才需要明確 interface，同 container 內部
  可直接函式呼叫。」

---

## Q3. 「跨 container 的**通訊協定**是什麼？同步還是非同步？payload 格式？」

- **為什麼問這個**：C4 圖的線不只是「有關係」，要標**通訊機制**。in-process function call vs
  HTTP REST vs gRPC vs file vs event queue——每種協定有不同的 failure mode、latency、coupling。
  不標 protocol，07-api-spec 卡無法決定 endpoint 設計，10-threat-model 無法判定 trust boundary。
- **好答案長什麼樣**：
  - PWA Shell ↔ 行程規劃引擎：**in-process function call**（同 JS bundle，同步）
  - 行程規劃引擎 ↔ FX Adapter：**in-process async function call**（return Promise）
  - FX Adapter ↔ Wise API：**HTTPS REST**（外部、JSON、非同步、需 retry / circuit breaker）
  - PWA Shell ↔ localStorage：**synchronous browser API**
  - 全系統 ↔ Plausible：**HTTPS POST fire-and-forget**（非同步、失敗不阻塞主流程）
- **壞答案長什麼樣**：「會通訊就好」——下游無法寫 API spec。
- **別人會 push back 什麼**：Dev 會說「in-process call 還要標 protocol？」回應：
  「**要**。標『in-process function call』跟標『HTTP』在 deploy 時意義完全不同——
  in-process 升級不需 zero-downtime、HTTP 要。protocol 標清楚，未來想拆 service 時清楚知道 cost。」

## Q4. 「**外部依賴的穩定性等級**是什麼？Tier 1/2/3，且 Tier 1 必須有 failover 設計。」

- **為什麼問這個**：外部依賴決定系統的**真實 SLA 上限**——你的 SLA 不可能超過任何 Tier 1 依賴的 SLA。
  不分級就等於把外部 API 當作 100% 可用，但現實是：Wise API 出過 outage、Google Maps quota
  會超、第三方 service 會改 API 規格。Tier 1（壞了我們也壞）必須有 failover；Tier 2（降級可用）
  要有 graceful degradation；Tier 3（可選）壞了就壞。
- **好答案長什麼樣**：
  - **FX rate provider** = **Tier 2**（降級可用）——壞了顯示「匯率資料暫時無法取得，顯示上次更新時間」
    + 燈號改為「不確定」灰色。failover：cache 上一次 fetch 結果（最多 24 小時）。**替代方案**：
    Wise / 台銀公開 API / Frankfurter open source API 三選一可切換（adapter pattern）。
  - **Google Maps Places** = **Tier 3**（可選）——壞了行程仍能生成，只是地點沒有座標顯示。
    failover：行程改顯示文字名稱清單，無地圖。
  - **Plausible Analytics** = **Tier 3**——壞了使用者無感（fire-and-forget），只影響我們看資料。
  - **localStorage（browser）** = **Tier 1**——壞了存檔功能全壞（無 failover：使用者裝置自身問題）。
    但這是 platform 層，不是外部依賴。
- **壞答案長什麼樣**：「外部 API」——沒分級、沒 failover。這四個字本身就是 incident report 的開端。
- **別人會 push back 什麼**：SA 會說「現在還在 MVP，搞這麼複雜？」回應：
  「**Tier 不是設計，是分類**。分類花 5 分鐘，未來 incident 時知道誰是真凶；不分類，
  incident 來時花 3 天找根因。」

## Q5. 「容器數量 vs 部署成本怎麼權衡？**最少幾個 container 能 work**？」

- **為什麼問這個**：container 太多 = 部署複雜、跨 container 通訊成本高、debug 痛苦；
  container 太少 = 邏輯耦合、團隊互卡、scaling 不靈活。MVP 應該用**最少 container 數量**
  滿足功能 + ADR 約束。每多一個 container 要證明「為什麼不能合進現有 container」。
- **好答案長什麼樣**：「ADR-001 鎖死 localStorage（無 server）→ 全部 container 跑在
  **同一個 PWA bundle**。邏輯 container 6 個是因為：
  (1) **PWA Shell**：routing / UI shell，獨立是因為團隊想換 framework 不影響 logic
  (2) **行程規劃引擎**：pure function，獨立是因為要寫單元測試、未來可能變 server-side
  (3) **FX Adapter**：external HTTP + cache + tier 切換，獨立是因為外部依賴隔離原則
  (4) **燈號判定服務**：演算法邏輯，獨立是因為 PRD P0-5 有明示『非投資理財建議』法規邊界，
       邏輯獨立才能單獨測試 + 加免責聲明
  (5) **開支記錄子模組**：獨立是因為資料生命週期不同（行程 = 出發前；開支 = 旅途中）
  (6) **Storage Adapter**：包住 localStorage 細節，獨立是因為 ADR-001 預留 V1 swap 後門
  → **6 個 logical container 在 1 個 deploy unit（PWA bundle）裡**。」
- **壞答案長什麼樣**：「拆越細越好」「全部塞同一個 module」——前者過度設計，後者沒設計。
- **別人會 push back 什麼**：Dev 會說「6 個 container 太多了，PWA 哪要切這麼細」。回應：
  「**deploy unit 是 1 個，邏輯 container 是 6 個**——這不衝突。邏輯 container 是
  『內部設計邊界』，給 07-api-spec 寫 interface 用，給 11-unit-test 寫 mock 邊界用。
  跑起來還是 1 個 bundle。」

## Q6. 「**外部依賴換了怎麼辦**？譬如 Wise API 改 schema 或停服，blast radius 多大？」

- **為什麼問這個**：外部依賴是技術債的最大源頭——它不在你掌控內，可能 deprecate、改 pricing、
  改 schema、出 outage。Architect 必須回答「他改了，我們動哪幾個檔案」。理想架構是
  **adapter pattern** 把外部依賴的細節包在一個 container 內，blast radius = 1 個 container。
- **好答案長什麼樣**：「**FX Adapter container** 隔離所有 FX 來源細節。換 provider 只動：
  (a) FX Adapter 內的 provider-specific module（譬如 `wise-provider.ts` 改寫成
  `frankfurter-provider.ts`）(b) Adapter 對外介面**不變**（`fetchRate(from, to): Promise<Rate>`）
  (c) 上游所有 container 無感。**Blast radius = 1 個 container 內的 1 個 module**。
  預估換 provider 工作量：1–2 天。」
- **壞答案長什麼樣**：「直接 import 用就好，換的時候再改」——blast radius 不可控、
  上游所有用到的地方都要改。
- **別人會 push back 什麼**：Dev 會說「adapter pattern 太工程化了，MVP 直接 fetch 不就好？」
  回應：「**MVP 偷懶 = V1 重構**。adapter pattern 多花 0.5 天，未來換 provider 省 5 天。
  ROI 10x。而且 P0-8『接入即時匯率』在 PRD 標為 ❌ 待補，意味著我們還沒選 provider——
  **adapter pattern 就是給『還沒選』留空間的方法**。」

## 送命題清單

這 1 題不問，C4 圖會變成「畫得很漂亮但下游用不到」：

1. **「這張 C4 圖，**6 週後 Dev 接手寫 code 時會用到什麼**？把每個 container 對應到
   哪個檔案 / 哪個 PR 寫出來。」**

   C4 圖最常見的死法：畫完掛在 Confluence，沒人再打開。原因是「圖好看但跟 code 對不上」。
   Architect 必須在會議結束前，把每個 container 對應到**具體檔案結構**（譬如
   `src/engine/trip-planner.ts` 對應「行程規劃引擎」container），並把這個對應關係寫進
   README 或 ADR-002（程式碼結構）。

   **判準**：6 週後 Dev 拿到一個 ticket「修改換匯邏輯」，他能看 C4 圖**3 秒內**找到
   「啊這是 FX Adapter 的事，code 在 `src/fx/`」——做不到，C4 圖就是裝飾。
