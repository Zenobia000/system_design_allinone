# 06 C4 Diagram · 角色場景

## 這場會議在做什麼

ADR 把關鍵決策都鎖死後，現在要把整個系統**畫出來**——但不是隨便畫 box-and-line，
而是用 **C4 model** 的三層結構（Context / Container / Component）依序展開。
本場會議 75 分鐘，產出**三張白板圖**：

- **Layer 1（Context, 15 min）**：系統與外部世界的關係——誰是 actor、外部依賴有哪些
- **Layer 2（Container, 35 min）**：系統內部由哪些 deploy unit / runtime 構成
- **Layer 3（Component, 25 min）**：選 1–2 個關鍵 container 內部拆 component

**不是**寫實作會，**不是**選 framework 會，**不是**畫 UML 用例圖。
目的只有一個：**畫出 box 的同時，把「邊界依據」寫下來**——
為什麼這條線在這裡而不是別處？為什麼這兩個東西在同一個 box 而不是分開？

> **C4 model 重點不在「畫得漂亮」，在「邊界依據可被挑戰」**。
> 一張沒有邊界依據的 box 圖只是裝飾，等於沒畫。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Architect（主責，你）** | 05-ADR 全套決策、PRD §6 功能清單、團隊組織圖 | 三層 C4 圖 + 每個 box 的「類型 + 邊界依據」標註 |
| **SA**（System Analyst） | 跨系統依賴清單、外部 API 文件、SLA 資料 | 確認外部依賴穩定性等級、failover 路徑被畫進去 |
| **Dev**（FE / BE 各 1 人） | runtime / framework 限制、deploy pipeline 現況 | 知道「哪個 container 是我寫的」「我跟誰用什麼 protocol 溝通」 |

## 你扮演的角色（Architect）

你是「**邊界守門員**」。本場會議你要做三件事：

1. 每畫一個 box，**強迫團隊回答**：「這個 box 的類型是什麼？」（service / db / external / queue / shell⋯⋯）
2. 每畫一條線，**強迫團隊回答**：「這是什麼 protocol？同步還是非同步？JSON / gRPC / file？」
3. 每個外部依賴 box，**強迫團隊標穩定性等級**：「Tier 1（壞了我們也壞）/ Tier 2（降級可用）/ Tier 3（可選）」

**禁忌動作**：本場會議**禁止**這幾種畫法，畫了就要重來：

- ❌ **box 沒標類型**——「FX」「DB」這種無類型 box 是廢圖
- ❌ **線沒標 protocol**——「FE → BE」這種無 protocol 線等於沒畫
- ❌ **外部依賴沒標穩定性等級**——「外部 API」這四個字就是技術債的源頭
- ❌ **三層混在同一張圖**——Context / Container / Component 必須分三張，混畫 = 學員會看不懂
- ❌ **container 邊界沒依據**——「FE 跟 BE 分開」要說「依據是部署單位 / 資料生命週期 / 團隊歸屬」哪一個

## 會議結束時，桌上要有什麼

### Layer 1：Context 圖（必交）

- 1 個 system box（SmartTrip FX）
- N 個 actor box（衝動型旅客、首次自由行新手）
- M 個 external system box，每個標 **Tier 1/2/3 穩定性等級** + 替換難度
- 每條 actor → system 線標**主要 use case**
- 每條 system → external 線標 **protocol + failover 策略**

### Layer 2：Container 圖（必交）

- N 個 container box，每個標：
  - **類型**（PWA shell / service / adapter / storage / external⋯⋯）
  - **runtime / tech stack**（React PWA / Node.js / IndexedDB / external HTTP API⋯⋯）
  - **邊界依據**（同一 deploy unit / 同一資料生命週期 / 同一團隊 / external）
- 每條 container ↔ container 線標 **protocol**（in-process / HTTP / file / event⋯⋯）

### Layer 3：Component 圖（至少 1 個關鍵 container 必交）

- 挑 1–2 個**核心 container**（譬如「行程規劃引擎」「FX adapter」）
- 拆出內部 component（class / module / service）
- 每個 component 標**單一職責**（一句話）
- component 之間的呼叫關係 + 介面定義

### 附加產出

- **外部依賴清單**：表格形式，欄位含 [名稱 / 用途 / Tier / SLA / 替換難度 / 替代方案]
- 給 07-api-spec 的「container 邊界 → endpoint 清單」（哪些跨 container 通訊要定 contract）
- 給 08-data-model 的「資料生命週期表」（哪個 container 擁有哪個資料）

## 為什麼這場會議重要

C4 圖是整條 SDLC 的**系統地圖**。下游每張卡都會回來看它：

- **07-api-spec**：endpoint 清單從 container 邊界推導（跨 container 才需定 contract）
- **08-data-model**：資料 owner 從 container 圖判定（誰寫資料，誰定 schema）
- **09-non-functional-reqs**：每個 container 的 SLA 預算從這裡分配
- **10-threat-model**：trust boundary 從 container 邊界畫出
- **12-release-plan**：deploy unit 直接對應 container box
- **14-monitoring**：每個 container 的 health check / metric 從這裡規劃

**跳過 C4 圖的代價**：6 週後 Dev 寫 code 時憑感覺切 module，3 個月後想加新功能發現
邏輯散落 4 個地方、不知道要動哪個——這就是**沒有邊界依據的代價**。
C4 不是文件工作，是**共同語言的建立**：所有人在同一張地圖上指同一個 box，溝通成本降到最低。

## 本場示範主題

**SmartTrip FX MVP 全系統三層 C4 圖**：

- **Layer 1 Context**：SmartTrip FX + 2 個 actor + 3 個 external system
- **Layer 2 Container**：6 個 container，以 ADR-001（localStorage）為前提
- **Layer 3 Component**：拆 **FX Adapter** 內部（最關鍵也最容易出事的 container）

教學意義：學員會學到「即便 MVP 是 PWA 沒有 server，C4 圖一樣有 6 個 container」——
container 不等於 server，是**邏輯邊界 + deploy 單位**的合體。
