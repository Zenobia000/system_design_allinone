customer_segment:
  required: true
  type: 25–40 歲台灣衝動型出境旅客（一年 1–4 趟、日韓泰為主、預算敏感、習慣帶現金）
  ref: P1（目標受眾 主要族群）
  source: [目標受眾, 01-jtbd JTBD-001.opportunity_size]
  confidence: H

problem_statement:
  type: string
  content: |
    台灣衝動型出境旅客 struggles to 在出發前估出「該帶多少外幣現金 + 何時換最划算」,
    because 現有行程規劃工具與 OTA 完全不處理金錢決策，旅客只能憑感覺換匯，
    結果常常換太多（虧匯差）或換太少（現場狼狽），單趟損失數百到上千元。
  source: [待解痛點, 01-jtbd JTBD-001.functional_job]
  confidence: H

proposed_value:
  hypothesis: |
    我們相信「**先算錢再排行程**」的工具定位，對台灣衝動型出境旅客有價值，
    因為現有 OTA / Google / ChatGPT 都不處理「該帶多少現金」這個決策痛點。
    我們會用「啟用率 + 存檔率 + 無提示說出『換匯/現金』差異」三項指標驗證。
  behavior_change: |
    使用者進站後選擇「生成行程」而非離站，且生成後願意按「儲存此行程」存到 localStorage，
    並在 30 天內回訪查看（代表真實出行意圖，而非閒逛）。
  leading_indicator: |
    啟用率（進站者完成一次生成的比例），4 週驗證窗內可直接量測。
  source: [期望成果, 預設成功指標]
  confidence: M  # 假設本身高 confidence，但 leading_indicator 的門檻值無 baseline

riskiest_assumption:
  required: true
  content: |
    衝動型旅客**真的會在出發前**主動找一個「先算錢」的工具，
    而不是在臨出發前 1 天去機場/銀行隨手換錢、結束才發現換錯。
  category: desirability
  confidence: M  # 痛點描述存在，但沒有訪談證據說「使用者願意為此主動找工具」
  why_risky: |
    若使用者其實是「事後才覺得換錯」而非「事前會主動找工具」，
    那整個 SmartTrip FX 的入口時機就錯了——產品需求是真的，但 distribution 時機不對。
    這比「功能做不好」更致命，因為連 SEO/廣告投放策略都會錯。

test_method:
  type: smoke_test
  cost_estimate: 4 days（包含 landing page + 廣告投放 + Plausible 埋點）
  no_code: false  # landing page 需要 1 天前端
  participants: 預期觸及 1000+ uniques，期望 ≥ 40 進入計算頁
  rationale: |
    用最小成本驗證「衝動型旅客看到『先算錢』訴求會點」這件事。
    Smoke test 直接量真實人流的點擊轉換，比 fake_door 多了一步「生成」行為，
    剛好對齊「啟用率」的定義。

  metric: 啟用率（landing → 完成一次行程生成）
  baseline: TODO(從首兩週實測校準，目前完全無 baseline)
  target: ≥ 40%（團隊拍腦袋值，需校準）
  source: [預設成功指標]
  confidence: L  # 40% 是團隊拍腦袋，沒有競品 benchmark 也沒有歷史數據

kill_criteria:
  required: true
  triggerable: true
  conditions:
    - |
      若 4 週驗證窗結束，啟用率 < 25%（目標 40% 的 ~60%）→ 暫停 V1 規劃，
      重新檢視「先算錢」定位是否真的是使用者買單的點。
    - |
      若 30 天回訪 < 10%（目標 20% 的 50%）→ 即使啟用率達標，
      也代表「一次性好奇 ≠ 真實需求」，須回到 JTBD 重做訪談。

      若訪談問「這跟其他行程 App 哪裡不一樣」時，
      無提示說出「換匯/現金」的比例 < 30%（目標 60% 的一半）→ 護城河不存在。

  - decision: 為何選 smoke_test 而非 fake_door 或 concierge
    options_considered: [fake_door, concierge, smoke_test, prototype_test]
    chosen: smoke_test
    rejected_reason:

        只能驗證「點擊意圖」，無法驗證「真的會生成行程」這個行為。
        啟用率定義是「完成一次生成」，fake_door 量不到。
      concierge: |
        人工幫使用者算現金需要每單 10–15 分鐘客服時間，4 週驗證窗下無法觸及足夠樣本（< 50 人）；

      prototype_test: |
        實際上 v0.1 產品已上線，smoke test 直接用真產品 + 投廣告即可，
        不需要再做 prototype，重做反而浪費 4 週驗證窗。

    rejected_reason:
      feasibility_即時匯率資料源: |
        即時匯率確實是技術風險，但有多家供應商可選（exchangerate.host / OpenExchangeRates），

      viability_4週能否驗證: |
        4 週時間盒是約束不是風險——時間到就強制決策，無「驗證失敗」可能。
    confidence: M  # 此排序基於團隊 prior，無外部證據

  - 不設計實作細節（即時匯率 API 選型屬 ADR / PRD）
  - 不畫 landing page UI mockup（屬 UX design）

  lowest_confidence:
    - field: success_threshold.target（≥ 40% 啟用率）
      reason: 完全無 baseline，純拍腦袋。可能 40% 太低（產品確實好用）或太高（衝動族群本就低粘性）。
      need: 首兩週實測 + 至少 1 個競品（Klook / Trip.com）的公開漏斗數據參考

    Switch interview：5–8 份「你上次出國前是怎麼決定要帶多少現金」的訪談——
    可同時驗證 riskiest_assumption（會不會主動找工具）+ 校準 success_threshold（願意花多少時間/精力）。

## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 `riskiest_assumption` 選「會不會主動找工具」而非「即時匯率技術可行性」？

這是 value-hypothesis 卡的**核心教學點**：riskiest 不等於「最大」，而是「**錯了會殺死整個 idea**」的那個。
即時匯率資料源就算選錯，換一家供應商就好（漸進可修）；
但若使用者根本不會「事前主動找工具」，那 SmartTrip FX 的入口時機、SEO、廣告投放策略**整套都錯**。
這種「會打到地基」的假設才是 riskiest。學生常犯的錯是把「最讓我焦慮的技術問題」當 riskiest，那是 feasibility 不是 desirability。

### 2. 為什麼 `success_threshold.confidence` 標 L 還要寫進來？

brief 的「啟用率 ≥ 40%」是團隊拍腦袋，**沒有 baseline 也沒有競品 benchmark**。
誠實標 L 並寫 `TODO(從首兩週實測校準)` 是這張卡最重要的姿態——
**目標數字不該被當成既定真理**，而是「待驗證的假設」之一。
學生若把 40% 當 hard target 寫死，4 週驗證後拿 38% 會被誤判為失敗，但其實可能 38% 已經好過業界。

### 3. `kill_criteria` 必須可被觸發——SmartTrip 是怎麼做的

三條 kill criteria 都對應到輸入需求的具體指標 × 一個「容忍下限」：

| Kill 條件 | 對應預設目標 | 容忍倍率 |
|---|---|---|
| 啟用率 < 25% | ≥ 40% | ~60% |
| 30 天回訪 < 10% | ≥ 20% | 50% |
| 無提示認知 < 30% | ≥ 60% | 50% |

學生常寫「啟用率 < 40% 就 kill」——但這沒留誤差容忍空間，4 週驗證的樣本變異就足以誤殺。
**Kill criteria = 目標的 50–60%**，是 lean startup 圈的經驗值。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `riskiest_assumption` + `kill_criteria` | [`03-prd/`](../../02-define/03-prd/) Goal 章節（PRD 的 Goal 要對應到可被殺的假設） |
| `success_threshold` + `leading_indicator` | [`03-prd/`](../../02-define/03-prd/) Success Metrics + [`09-non-functional-reqs/`](../../03-design/09-non-functional-reqs/) 量測 NFR |
| `test_method.smoke_test` 的 landing page | [`04-acceptance-criteria/`](../../02-define/04-acceptance-criteria/) 中 landing 的 AC |
| `out_of_scope` 第 3 條（商業模式） | [`03-prd/`](../../02-define/03-prd/) Non-Goals + 未來 monetization brief |
| `self_review.highest_value_next_input` | 下一輪 user research 計畫 |

### 5. 與 01-JTBD 卡的銜接

JTBD-001 的 `success_criteria`（≤ 3 分鐘 / 誤差 < 15%）是**使用者體驗門檻**，
本卡的 `success_threshold`（啟用率 ≥ 40%）是**商業驗證門檻**。
兩者不能混淆：使用者完成 3 分鐘體驗 ≠ 我們就該繼續做 V1。
PRD 卡會把這兩層門檻同時帶下去。

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| Kill criteria 寫「啟用率不達標就再優化」 | 規則 7 | 必須是「< X% 就停掉 / 重做」這種**可執行**句式，不能留逃生口 |
| Riskiest assumption 寫「使用者會喜歡這個產品」 | 規則 6 + 7 | 「會喜歡」不可證偽——改寫成具體可觀察的行為（「主動搜尋此類工具」） |
| Test method 選 prototype_test，cost > 2 週 | 規則 4 | < 1 週原則；本案產品 v0.1 已上線，應該用 smoke_test 跑真產品 |
| 把 brief 的成功指標數字當「目標」抄進 success_threshold 且標 H | 規則 6 | 無 baseline 就標 L，並寫進 `self_review.lowest_confidence` |
| `out_of_scope` 寫「不做訂房比價」 | 規則 5（誤用） | 那是**產品 non-goal**，屬 PRD；本卡的 out_of_scope 應是「不畫 UI / 不寫實作 / 不定價」 |

## 交件 checklist

- [ ] `riskiest_assumption` 是「錯了會殺死整個 idea」的那條，不是「最讓我焦慮」的那條
- [ ] `test_method` 成本 < 1 週，且寫明選擇理由
- [ ] `kill_criteria` 至少 1 條可被觸發（< X% 就停），且容忍下限留到目標的 50–60%
- [ ] `success_threshold.baseline` 若無資料，誠實標 `TODO(待校準)` + confidence: L
- [ ] `decision_log` 至少 1 條，列 `options_considered` + 每個 rejected_reason
- [ ] `out_of_scope` 至少 3 條，且**不要與產品 non-goal 混淆**（這裡是文件 scope，不是產品 scope）
- [ ] `self_review.lowest_confidence` 對應到每個 L 標註的補洞計畫
