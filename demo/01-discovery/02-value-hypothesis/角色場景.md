# 02 Value Hypothesis · 角色場景

## 這場會議在做什麼

JTBD 會議結束後 1–3 天內召開（趁團隊還記得逐字稿語氣）。PO 召集 PM 與 UX，
把 01-jtbd 留下的 success criteria（例如「誤差 < 15%」「3 分鐘」）**翻譯成可證偽的 H1/H2/H3 價值假設**，
並掛上 4 週驗證窗、樣本門檻、失敗條件。

**不是**寫 PRD 會（功能規格留給 03-prd）、**不是**做實驗設計會（A/B 分流設計屬 14-experiment），
**也不是**訂 OKR 會。目的只有一個：

把 JTBD 的 success criteria 從「目標」變成「實驗」——說清楚 **4 週內看到什麼數字算贏、看到什麼數字算輸、輸了下一步做什麼**。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **PO（主責，你）** | 01-jtbd 的 5 條 JTBD + success criteria、種子簡報的 4 週驗證窗、商業優先序 | 3 條 H1/H2/H3 假設、每條都有失敗條件 + pivot/persevere/kill 對應動作 |
| **PM** | 競品基準數字、過往類似 launch 的 baseline、PRD 草稿要寫的功能清單 | 確認假設可以對應到 03-prd 的哪幾條 P0 需求、量測事件名 |
| **UX** | JTBD 的 emotional/social 線索、可行的量測 proxy（哪些行為可觀察、哪些只能訪談） | 後續 prototype test 與 14-experiment 的觀察維度 |

## 你扮演的角色（PO）

你不是夢想家，你是**會計師 + 法官**。本場會議你要做三件事：

1. 每條候選假設，逼提案人講出「**4 週、N 樣本、若 X 則 fail**」三個數字。三缺一就不算假設，只算許願。
2. 失敗條件要對應動作：**pivot（換方向）／persevere（再給一窗）／kill（停止投資）**——沒寫對應動作的失敗條件等於沒有失敗條件。
3. 假設之間互相牴觸時（例如 H1 衝啟用率 vs H2 衝精準度），標明 **trade-off + 取捨依據**，不要硬寫「都重要」。

**禁忌動作**（一講就罰自己 100 元，這條規則認真執行）：

- **不能講「應該會」「我覺得」「直覺認為」「感覺差不多」「大概是」這類無法證偽的話**——
  講了就罰，因為這是「我願意賭錢的判斷」會議，不是「我猜猜看」會議。
- **不能寫沒有失敗條件的假設**——
  只寫「H1: 啟用率 ≥ 40%」不寫「< X% 算 fail」就是不可證偽，整條作廢重寫。
- **不能把 leading 跟 lagging indicator 混在同一條假設裡**——
  「啟用率 ≥ 40% 且 30 天回訪 ≥ 20%」是兩條，硬綁在一起會在第 2 週看數字時不知道該慶祝還是該擔心。

## 會議結束時，桌上要有什麼

- **3 條完整假設 H1/H2/H3**，每條包含 7 個欄位（缺一不算數）：
  1. If…then… 完整陳述
  2. 對應 JTBD-NNN（必須回得去 01-jtbd 的某一條）
  3. 量測方式（具體 metric + 事件名，引用 PRD §8 的事件名）
  4. 驗證窗（4 週中的第幾週驗證，例：W2 看 leading、W4 看 lagging）
  5. 樣本門檻（最少 N 筆才能下結論，N < 此值結論作廢）
  6. 失敗條件 + 對應動作（pivot/persevere/kill 三選一）
  7. confidence `[H/M/L]`
- **假設之間 trade-off 表**：哪兩條互斥／互相牴觸、選誰為主、選誰為輔
- **Leading vs Lagging 對照**：哪些指標 W1–W2 就能看、哪些要等到 W4 才能下結論
- **送進 03-prd 的清單**：哪條假設對應 PRD §6 的哪條 P0 需求、哪條對應 PRD §7 的哪個指標、哪條對應 PRD §8 的哪個事件
- **Decision log**：被否決的候選假設 + 否決依據（樣本不夠／非核心 JTBD／無法 4 週驗證）

## 為什麼這場會議重要

Value Hypothesis 是整條 SDLC 的**決策節點**。它決定 4 週後要 pivot、persevere 還是 kill：

- 03-PRD 的「成功指標」段直接抄本卡的 metric + 門檻；本卡沒鎖死數字，PRD §7 會憑空生
- 14-experiment 卡的實驗設計直接綁本卡的「驗證窗 + 樣本門檻」；本卡沒寫，實驗會做不完或做太多
- 15-postmortem 評估「launch 成功了嗎」的基準就是本卡的成功／失敗條件；本卡沒寫，postmortem 變成「大家覺得還可以」
- 12-release-plan 的 go/no-go 決策直接看本卡假設是否成立

跳過這場會議的代價：團隊把 4 週驗證窗燒成「上線 → 看儀表板 → 老闆說再給一個月」——
因為**沒有事前約定的失敗條件**，永遠都「再給一個月」就會變成永遠都不 kill 的殭屍專案。
SmartTrip 種子簡報明示「4 週 MVP 驗證窗之後才決定要不要繼續做 V1」——這場會議就是把那個「決定」拆成可執行的判準。
