# 14 Runbook · 關鍵提問（DevOps 必問）

> 本場會議 60 分鐘，DevOps 只要把這 6 題對每一個 incident 都問完，5 份 runbook 就成形了。
> 每題的目標：**逼出『傻瓜版』的具體指令／面板／聯絡管道**，不接受「應該⋯⋯」「大概⋯⋯」「通常⋯⋯」。
> 寫 runbook 就像寫給「凌晨 3 點、半睡半醒、剛 onboarding 7 天的工程師」——他需要的不是知識，是指令。

---

## Q1. 「這個 incident 的 detection 信號是什麼？具體 alert 叫什麼？SEV 幾級？」

- **為什麼問這個**：runbook 的入口必須是「**收到這個 alert 的人，知道自己在處理哪個 incident**」。
  alert 名稱模糊（譬如 `HighLatencyAlert`）→ on-call 不知道是 FX API 慢、生成慢、還是 PWA SW 慢，
  浪費 5 分鐘做 incident classification。alert 名稱必須**直接對應 runbook 檔名**。
- **好答案長什麼樣**：「Alert `fx_api_5xx_rate_high`（Grafana 規則 #42），閾值 `error_rate > 10% over 3min`，
  SEV-2（影響核心功能但有 fallback），primary on-call 收（PagerDuty rotation `devops-primary`），
  15 分鐘 SLA 內必須 ACK。對應 runbook `runbook/01-fx-api-down.md`。」（alert 名 + 規則 ID + 閾值 + SEV + 收件人 + SLA + runbook 連結）
- **壞答案長什麼樣**：「就 Grafana 會 alert」「之前都這樣處理的」——沒名稱、沒規則 ID、沒 SEV、沒 SLA。
- **別人會 push back 什麼**：Dev 會說「我們的監控系統還沒上線」（PRD P0-9 待補）。
  回應：「**那就先寫『手動 detection 信號』**——客服收到 X 件、使用者反映 Y、自己 dogfood 發現 Z。
  alert 上線後**第一件事**就是把這份 runbook 的 Detection 段從手動改成自動。寫進 P0-9 的 AC。」

## Q2. 「diagnosis 第一步是什麼？看哪個面板？具體 URL？」

- **為什麼問這個**：runbook 最常見的 anti-pattern 是「**先做 mitigation 再 diagnosis**」——
  on-call 看到 alert 就立刻 rollback，rollback 完才發現問題不在 release，而是 vendor 那邊掛掉，
  rollback 反而讓自己的 forward fix 路徑也斷了。
  diagnosis 是**強制動作**——至少要在 1 分鐘內看 1 個指定面板，確認 incident type 才能進 mitigation。
- **好答案長什麼樣**：「第一步開 Grafana dashboard `https://grafana.smarttrip.io/d/fx-overview`，
  看右上角 `FX provider response time` panel：
  - 若全紅（所有 provider 都掛）→ 走「FX 全面失效」分支（mitigation step 3）
  - 若只有 wise 紅、bot_tw 綠 → 走「單一 provider 失效」分支（mitigation step 1）
  - 若都綠但 latency > 5s → 走「FX 慢但活著」分支（mitigation step 2）」
  （具體 URL + panel 名 + 三種情境的分支判斷）
- **壞答案長什麼樣**：「看 log 找原因」「先看一下系統狀況」——沒指定面板、沒判斷依據。
- **別人會 push back 什麼**：Dev 會說「面板會變，寫死 URL 容易過時」。
  回應：「**過時就更新 runbook，不要不寫 URL**。寫死 URL + 每 quarter 演練時驗證連結還有效。runbook 是活文件不是雕像。」

## Q3. 「mitigation 動作是什麼？這個動作可逆嗎？」

- **為什麼問這個**：mitigation 的目的是**止血**，不是**根治**（根治是事後 forward fix 或 hotfix）。
  止血動作必須優先選**可逆的**——譬如 feature flag 關閉、流量切換、cache 清空——
  因為事故當下你對情況的理解只有 20%，做不可逆動作（譬如直接改 DB、刪 cache key）很可能讓事故升級。
- **好答案長什麼樣**：「Step 1（可逆）：開啟 feature flag `fx_provider=bot_tw` 切換到備用 provider。
  指令：`launchdarkly toggle fx_provider --value=bot_tw --env=prod`。
  預期：30 秒內 FX 燈號開始使用台銀數據。
  驗證：開 Grafana `fx-overview` 面板，`provider_active_pct` 中 `bot_tw` 應 → 100%。
  Step 2（若 Step 1 無效，**可逆**）：清 service worker FX cache。詳見 step 2 區塊。」
  每步明確標示**可逆／不可逆**。
- **壞答案長什麼樣**：「想辦法切到備用」「先 rollback 看看」——沒指令、沒驗證、沒可逆性標示。
- **別人會 push back 什麼**：Dev 會說「flag 切換太慢，直接 deploy hotfix 比較快」。
  回應：「**事故當下 deploy = 第二次事故的火種**。Hotfix 寫錯一個字就完蛋。
  flag 切換是 30 秒、deploy 是 8 分鐘 + build pipeline 風險。runbook 的 mitigation 永遠優先 flag。」

## Q4. 「escalation 觸發條件是什麼？升給誰？什麼聯絡管道？」

- **為什麼問這個**：runbook 寫到「升級給 X」常常翻譯成「**ping X 然後等他回**」——
  X 在睡覺 / 在開會 / 已離職 → 事故就卡在這。
  escalation 必須有**明確的觸發條件**（時間 or 嚴重度）+ **多個聯絡管道**（primary + backup）+ **預期回應時限**。
- **好答案長什麼樣**：「若 mitigation step 1-3 都無效且事故已持續 15 分鐘 → 升級給 secondary on-call。
  聯絡順序：(1) PagerDuty page（5 分鐘無 ACK 自動升）→ (2) 直接撥電話（手機號在 vault `oncall-phonelist`）
  →(3) 仍無回應則 page tertiary（PO 兼任）。
  若事故 SEV-1 且持續 30 分鐘 → 強制 page CTO + 啟動 status page 公告。」
  （明確時間閾值 + 聯絡順序 + 自動升級規則）
- **壞答案長什麼樣**：「叫 Bob 來看」「升級給老闆」——沒時間、沒順序、沒備援。
- **別人會 push back 什麼**：Dev 會說「我們團隊小，secondary 沒人」。
  回應：「**團隊小不是不寫 escalation 的理由，是要更明確寫『沒人時怎麼辦』**。
  譬如 secondary 不在 → 直接通知 PO + 啟動 degraded mode（功能降級而不修復）。寫死。」

## Q5. 「SLO breach 後的對外通訊是什麼？模板在哪？誰發？」

- **為什麼問這個**：事故對使用者的傷害**不只是『功能壞了』，更多是『功能壞了沒人告訴我』**。
  使用者開 PWA 看到 FX 燈號錯誤，沒通訊 → 他以為自己 PWA 壞了 → 客訴升級；
  status page 沒更新 → 使用者去推特罵 → 媒體擴大。
  通訊模板必須**事故前**就寫好（事故當下沒人寫得出冷靜的對外文案），放在固定位置，由固定角色發。
- **好答案長什麼樣**：「對 PO：Slack DM 模板 `templates/page-po-sev2.md`，DevOps 發，T+5min。
  對 status page：模板 `templates/status-page-fx-down.md`，PO 發，T+20min。
  對客服：FAQ 模板 `templates/customer-faq-fx-down.md`，DevOps 推給客服群組，T+30min。
  對所有使用者：in-app banner 模板 `templates/in-app-banner-fx-degraded.md`，Dev 推，T+2hr。」
- **壞答案長什麼樣**：「我再寫 status page」「客服那邊我會說」——沒模板、沒時機、沒人。
- **別人會 push back 什麼**：PO 會說「對外文案我來寫就好，不用模板」。
  回應：「**你現在寫的是『事故已過、心情平靜』時的文案，事故當下你寫不出來**。模板現在寫，事故時填空就發。」

## Q6. 「這份 runbook 多久演練一次？誰演練？新人 onboarding 怎麼跑過？」

- **為什麼問這個**：runbook 跟 rollback path 一樣——**沒演練過的 runbook 不是 runbook，是希望**。
  寫在 wiki 上看起來很順，凌晨 3 點按下去才發現：
  - 連結失效（面板搬家了沒人更新）
  - 指令過期（CLI 工具升版 syntax 變了）
  - 聯絡人離職（vault 的 phonelist 沒更新）
  - 自己沒 PagerDuty 權限（onboarding 沒設）

- **好答案長什麼樣**：「每 quarter game day 跑 1 次（DevOps + on-call rotation 全員參加）。
  新進工程師 onboarding day 7 必須跟著資深工程師跑過 1 份 SEV-1 runbook（譬如 FX API down），
  跑完寫一份『發現的不一致』報告交給 DevOps，DevOps 24 小時內更新 runbook。」
- **壞答案長什麼樣**：「之後會排」「需要時再跑」——沒週期、沒人、沒驗收。
- **別人會 push back 什麼**：Dev 會說「演練要 1 小時，沒空」。
  回應：「演練 1 小時，事故拖 1 小時 = 一樣花時間，但演練不會傷使用者。**runbook 演練週期寫進 OKR**，不演就降績效。」

## 送命題清單

這 3 題不問，3 個月後 15-postmortem 會回來找你算帳：

1. **「這份 runbook 沒涵蓋的 incident type 是什麼？」**
   寫完 5 份 runbook 後**故意問**這題——逼自己列出 known gap（譬如「資安事故」「個資外洩」「DDoS」這些當前不寫，但要明確列為 out-of-scope + 標進 backlog）。沒列，下次發生時所有人都覺得「應該有 runbook」結果沒有。

2. **「on-call 的『心理安全感』夠嗎？做錯了會被罵嗎？」**
   blameless 文化從這裡開始。runbook 的 mitigation step 要明確寫「**做這一步不會被罵，做錯了我們一起 postmortem**」——尤其針對 SEV-1 不可逆動作。沒這條，on-call 不敢按，等於沒 runbook。

3. **「runbook 的版本控制怎麼做？修改誰 review？」**
   runbook 是 living document，但**改錯了也是事故**（譬如指令打錯字、URL 失效、SLA 改太鬆）。
   必須走 PR review（至少 1 個 DevOps + 1 個 Dev review），版本號標在每份 runbook 頭部。不做，事故當下不知道自己在看哪一版。
