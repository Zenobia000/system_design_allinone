## ⚠️ 本卡注意事項（進 Claude 前先讀）

- **「凌晨 3 點測試」是金標準**。任何一個 entry 寫完後問自己：剛被 page 醒、咖啡還沒喝的 oncall，能 5 分鐘內走完嗎？寫「contact FX team」「check the dashboard」這種句子就是壞 runbook。
- **每個 `Diagnosis Steps` 與 `Remediation Steps` 必須附具體 command 與 expected output**。`curl -sI ... | head -1` 期望 `HTTP/2 200` 是好範例。
- **每個 `Remediation Steps` 必須附 `rollback` 指令**（不可逆寫 `N/A` 並說明），是範本 `> [!IMPORTANT]` 鐵律。沒 rollback = 一次性炸彈。
- **每個 entry 必須有 `Last Tested`**。沒演練過寫 `_TODO: 需要排 game day_`，不要省略 — `not_tested` 是被動陳述，`TODO` 是主動 backlog。
- **個人專案的 `Escalation Criteria` 誠實寫 `_TODO: 填上 on-call_`**，不要假裝有 escalation chain；但 condition 要明確（什麼情況下 runbook 不夠用）。

### 服務架構摘要

SmartTrip FX 是一個 client-side 為主的 SPA：
- 前端：Next.js 14 部署於 Vercel（Hobby tier）
- 資料儲存：使用者瀏覽器 localStorage（無後端 DB）
- 外部依賴：
  - exchangerate.host（即時匯率 API，1000 req/month）
  - Plausible Cloud（analytics，付費 $9/月）
  - Vercel Edge Cache（1 小時 TTL）
- 無正式 SLO；個人 maintainer MTTR 目標 ≤ 15 分鐘

### 已知告警 / 異常清單（本次 runbook 要覆蓋的 4 條）

來自 `12-release-plan` 的 Risk Summary + `13-rollback-plan` 的 Triggers（**ALERT 編號對齊 TRIGGER 編號**）：

1. **ALERT-FX-1**（↔ TRIGGER-1）：FX API（exchangerate.host）失敗率 > 50% 連續 30 分鐘
2. **ALERT-STORAGE-1**：localStorage 寫入失敗（quota exceeded 或 disabled）
3. **ALERT-DEPLOY-1**（↔ TRIGGER-3）：Vercel deployment failed（build error 或 runtime exception）
4. **ALERT-ANALYTICS-1**：Plausible 事件 ingestion 失敗（24h 無事件進來但有有機流量）

## 替換成自己專案的方法

如果你不是要做 SmartTrip FX：

1. 跑 [`/start/`](http://localhost:3000/start/) 問卷 → 下載你自己的 `project-brief.md`
2. 步驟 1（複製站上「完整範本」tab）**完全不動**
3. 步驟 2 的 trigger 結構不動；**只替換 `⏫` 上方的「上游文件」貼位區**：
   - 把「服務架構摘要」換成你自己的 stack（不是 Vercel 就改成你的 hosting；含上游依賴 + SLO）
   - 把「已知告警清單」換成你自己 release-plan 與 rollback-plan 衍生的 trigger（ALERT 編號**必須對齊** rollback-plan 的 TRIGGER 編號）
   - 上游若有真的 postmortem（`15-postmortem/`），把摘錄貼到「過往 postmortem 與 chat log 摘錄」；沒有就誠實寫 TODO
   - 把「Dashboard 連結」換成你自己的 monitoring URL
4. 貼到 Claude → 對比你拿到的結果與 [`實際結果.md`](./實際結果.md) 的「教學要點」與「常見錯誤」

> **為什麼步驟 1 不動？** 因為站上模板就是 single source of truth。版本升級（規則修訂、章節增刪）會自動同步到所有學生的下次產出，不需要去改舊的 demo 檔。
