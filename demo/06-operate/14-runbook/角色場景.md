# 14 Runbook · 角色場景

## 這場會議在做什麼

13-rollback-plan 把「每一條 release 變更怎麼安全 rollback」搞定了，
但 release 上線後**真實世界的事故不只有 rollback 一種解法**——
有些事故要 forward fix、有些要 in-place mitigation、有些只能對外通訊先穩住使用者。

這場 60 分鐘的 **on-call 交接會** 目的是：
把已知的 **5 大常見 incident**（基於 09-NFR 的 SLO + 13-rollback-plan 的 trigger 信號）
**逐一寫成 runbook**——detection → diagnosis → mitigation → escalation 一條龍，
讓**任何一個新 on-call 工程師，凌晨 3 點被 page、半睡半醒、沒上下文**，都能照著做完正確動作。

**不是**寫 incident response policy（那是公司層級的）、**不是**做事後檢討（那是 15-postmortem）、**不是**做 capacity planning。
這場只做一件事：**把已知 incident 的應對流程，從『工程師腦袋裡的 tribal knowledge』寫成『傻瓜也能跟的 step-by-step』**。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **DevOps（主責，你）** | 過往 incident log、監控面板、alert 規則、13-rollback-plan 的 trigger 矩陣 | 5 份 runbook + 演練排程 + on-call rotation 表 |
| **Dev** | 系統內部知識、診斷指令、code path、最近 release 的 known issue | 確認 runbook 的診斷步驟正確、可執行 |
| **QA** | 已知 edge case、過往 bug pattern、驗收測試的覆蓋盲區 | 補充「不會被 alert 抓到但會被使用者抓到」的 incident 類型 |

## 你扮演的角色（DevOps）

你是「**凌晨 3 點被 page 的下一個人**」的代言人。本場會議你只做兩件事：

1. 每一條 runbook 的每一步，問 Dev「**這一步能不能讓一個剛 onboarding 7 天的工程師執行？**」
   答案是「他要先看一下 code」「他要 ping 我」「他應該知道吧」→ **這步寫得不夠細**，當場重寫。
2. 每一條 mitigation 動作，問自己「**這個動作可逆嗎？做錯了能不能撤回？**」
   不可逆 → 必須在 runbook 上標 `⚠️ DANGER` 並要求 2 人 review 才執行。

**禁忌動作**：本場會議的 runbook 不准出現：
- 「請聯絡 X」（沒寫聯絡方式、聯絡時機、什麼時候叫 X、什麼時候改叫 Y）
- 「檢查 log」（沒寫具體 log path、過濾條件、要看什麼欄位）
- 「執行 SQL 查一下」（沒寫具體 SQL、預期結果、異常時怎麼辦）
- 「應該⋯⋯」「大概⋯⋯」「通常⋯⋯」（凌晨 3 點不需要不確定性）

一出現就罰自己 100 元——這些字眼翻譯成事實是「我把問題丟給未來凌晨 3 點的自己」。

## 會議結束時，桌上要有什麼

- **5 份 incident runbook**，每份結構如下：
  - **Detection**：alert 名稱 + 觸發條件 + 嚴重程度（SEV-1/2/3）+ 第一個會被通知的人
  - **Diagnosis**：第一步要看什麼面板 + 具體 URL + 預期欄位 + 異常判斷依據
  - **Mitigation**：step-by-step 應急動作 + 每步的具體指令／按鈕／feature flag 名稱
  - **Escalation**：什麼條件下升級給誰 + 聯絡管道 + SLA 內回應時限
  - **Communication**：對使用者／PO／客服的通訊模板與時機
- **On-call rotation 表**（誰、什麼時段、聯絡方式 primary/backup）
- **Runbook 演練排程**（每份 runbook 至少每 quarter 演練 1 次，**新進工程師 onboarding 7 天內必須跑過 1 份 SEV-1 runbook**）
- **Known limitations**（這 5 份 runbook **沒涵蓋**哪些 incident type → 進 15-postmortem action item）

## 為什麼這場會議重要

Runbook 是 09-NFR 承諾的 SLO（譬如「p95 < 180s」「可用性 99.5%」）在事故時**真的能被守住**的唯一保障。
沒有 runbook，每次事故都是：

- 凌晨 3 點 → page on-call → on-call 開始 google + ping Slack + 戳 code → 30 分鐘後才理解狀況 → SLO 已 breach
- 同一個 incident 三個月後再發生 → 換了一個 on-call → 又重跑一次 30 分鐘 → 再 breach 一次

跳過這場會議的代價：**每次事故都是首次**。15-postmortem 寫的 action item「將此情境加入 runbook」永遠沒人接住。

SmartTrip MVP 雖然小，但 PWA + 第三方 FX API + localStorage 的組合有 5 個典型故障面，
這 5 個面**都會直接影響 PRD §7 的「完成時間 < 3 分鐘」與「換匯準確度 < 15%」兩條核心指標**。
runbook 寫得不夠細 → 每次事故都會多延 20 分鐘以上，4 週驗證窗的數據就被汙染了。
