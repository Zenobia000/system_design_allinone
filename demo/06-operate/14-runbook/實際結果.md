## 教學要點（看完 AI 輸出後讀這段）

### 1. 「凌晨 3 點測試」—— runbook 的金標準

打開任何一個 entry，問自己：**一個剛被 page 醒、咖啡還沒喝的工程師，能 5 分鐘內走完嗎？**

對照 ALERT-FX-1：
- ✅ 第一個 diagnosis step 是 `curl` 一行指令，秒判斷
- ✅ R1 的 command 可直接複製貼上，不需要查 Vercel 文件
- ✅ rollback 指令在同一個 entry 內，不需要切換 tab

對照學生常見的 bad runbook：
- ❌ `diagnosis_steps: [{ step: "Check if API is healthy" }]` —— 怎麼 check？沒講
- ❌ `remediation: "Contact the FX team"` —— 凌晨 3 點 FX team 不會接

### 2. 為什麼 `last_tested: TODO(需要排 game day)` 比 `not_tested` 更好？

`not_tested` 是被動陳述，沒有後續動作。
`TODO(需要排 game day)` 是主動 backlog，會被 follow-up。

**Runbook 沒被演練過 ≠ 沒用，但風險未知**。誠實標 TODO 讓 reviewer 知道哪些 entry 還沒驗證過。

### 3. 個人專案怎麼處理 `escalation_criteria`？

`escalate_to: TODO(填上 on-call)` 比假裝有 escalation chain 誠實。
SmartTrip FX 個人專案沒有 secondary oncall，所以這欄就是 TODO，但 condition 要明確（告訴未來的我「什麼情況下這條 runbook 不夠用」）。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `last_tested.date` 全是 TODO | 上線前 1 週要排 game day 演練（執行清單） |
| ALERT-FX-1 的 R1 命令 | `15-postmortem/` 若 incident 發生時要 trace 哪個 step 被執行 |
| `decision_log` 的 ad blocker 問題 | 退回 `03-prd/` Open Question 第 2 條（資料/隱私） |
| `out_of_scope`（自架 Plausible） | `05-adr/` 未來決策候選 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| `remediation` 寫「請聯絡 X team」 | 規則 8 | 寫具體指令；個人專案無 team 就寫 `TODO(填上 on-call)` |
| `diagnosis_steps` 寫「check the dashboard」 | 規則 3 | 寫 dashboard URL + 看哪個 panel + 期望值 |
| `remediation` 有 `command` 但無 `rollback` | 規則 7 | 每個 step 都附 rollback；不可逆的標 `N/A` 並說明 |
| `confidence: H` 但 step 從沒測過 | 規則 6 | 沒測過的標 M，並把測試列入 `last_tested.date: TODO` |
| `escalation_criteria` 寫成空陣列 | 規則 1 + 8 | 至少一條，個人專案誠實寫 TODO + condition |
| `permissions` 漏掉 | 規則 4 | 每個 step 標需要什麼權限（Vercel owner / GitHub admin） |
| `out_of_scope` 寫成空陣列 | 規則 5 | 至少 3 條：不做根因分析、不做架構改造、不做跨團隊協調 |

## 交件 checklist

- [ ] 4 個 ALERT 各有完整 entry
- [ ] 每個 `diagnosis_steps` 有具體 `command` + `expected_output`
- [ ] 每個 `remediation_steps` 有 `rollback`（不可逆寫 N/A 並說明）
- [ ] 每個 step 標 `permissions`
- [ ] 每個 entry 有 `last_tested`（沒測過寫 TODO + game day 計畫）
- [ ] `escalation_criteria` 至少一條，個人專案誠實寫 TODO(填上 on-call)
- [ ] `decision_log` 至少一條（如：mitigation 為何選 A 而非 B）
- [ ] `out_of_scope` 至少 3 條
