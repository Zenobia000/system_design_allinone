## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 5 Whys 終止於 `why_5`（缺乏 spec → invariant → test 流程）而非「人沒注意」？

對照壞的 5 Whys：
- why_1: 使用者看到不一致 → why_2: 程式碼有 bug → why_3: 開發者沒注意到 → why_4: 開發者經驗不足 → **停在「人」**

對照好的 5 Whys（本範例）：
- why_4: spec 模糊 + code review + test 都未涵蓋不變量
- why_5: **缺乏『spec → invariant → test』的對應流程**

差別：壞版本的 action item 會變成「訓練開發者更仔細」，個人卻學不會；好版本的 action item 是 AI-001（補 test）+ AI-002（補 spec），**系統性、可驗證、下次同模式 bug 不會再犯**。

### 2. `blameless_summary` 為什麼不寫人名？

「個人 maintainer 寫錯了 fallback」與「PRD spec 模糊導致 fallback 實作偏離」描述的是同一件事，但：
- 前者 → action item 變成「下次小心一點」，沒人能驗證
- 後者 → action item 變成 AI-002（補 PRD acceptance criteria），可驗證、可 review

**Blameless ≠ 不負責**。個人 maintainer 仍是所有 AI-XXX 的 owner，但「責任」放在「補系統」而非「自我譴責」。

### 3. `prevention_categories` 4 類必須齊全的原因

對照本 postmortem：
- **detection**（找出更快）：AI-003 paging、AI-005 game day
- **response**（處理更順）：AI-004 runbook trace
- **recovery**（恢復更快）：本次 recovery 沒問題，誠實寫「不是主要缺口」
- **prevention**（從源頭擋）：AI-001 test、AI-002 spec

學生常只寫 prevention（「下次不會再犯」）而漏 detection、response。
→ 結果是：同類問題雖然不會以「同樣方式」再犯，但「detect 延遲」、「response 偏離」會在下個 incident 重演。

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `action_items` AI-001 | `11-unit-test/` 新增測試 case |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 5 Whys 終止於「人沒注意」 | 規則 8 | 繼續問為什麼系統允許「人沒注意」就出問題 → 找 process/training/monitoring 缺口 |
| `blameless_summary` 出現人名 | 規則 7 | 改寫成「實作者依（模糊的）spec 撰寫」而非「Alice 寫錯了」 |
| `action_items` 缺 owner 或 due | 規則 6 + 7 | 每個 AI 必須有具體 owner（個人專案寫自己）+ 具體 due date（不是「ASAP」） |
| `action_items` 全是 prevention，無 detection / response | 規則 8（隱含） | 4 類至少各一條；無缺口的類別誠實寫「本次非主要缺口」 |
| `slo_burn` 寫具體 % 但無 SLO | 規則 4 | 個人專案無 SLO 就寫 `N/A — 無正式 SLO`，不要編造 |
| `contributing_factors` 寫成空陣列或只寫一條 | 規則 1 | 至少 3 條，4 類（detection / response / recovery / prevention）至少涵蓋 2 類 |
| `out_of_scope` 寫成空陣列 | 規則 5 | 至少 3 條：不檢討個人、不算商業影響、不查第三方根因 |
