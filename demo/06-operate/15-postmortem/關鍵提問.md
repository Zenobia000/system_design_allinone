# 15 Postmortem · 關鍵提問（DevOps 必問）

> 本場會議 90 分鐘，DevOps 只要把這 6 題問完、問對，postmortem 就成形了。
> 每題的目標：**逼出制度層次的改進**，不是逼出「該員教育訓練」「以後注意」這種偽 action item。
> 不要問「為什麼會這樣？」這種開放題——要問「**第一個 alert 響的時候，第一個使用者已經被影響多久？這個 gap 怎麼縮短？**」

---

## Q1. 「第一個 alert 時間 vs 第一個使用者影響時間，差多少？這個 detection gap 怎麼縮短？」

- **為什麼問這個**：postmortem 最關鍵的數字不是 root cause，是 **detection gap**——使用者已經受傷多久，我們才察覺。
  gap 大 = 監控有 blind spot；gap 小 = 監控敏感但可能誤觸發。
  這個數字直接決定下一個 action item 的優先序。
- **好答案長什麼樣**：「第一個使用者受影響：2026-05-10 14:00（從 access log 反推 P0-4 算錯第一筆生成）；
  第一個 alert：14:00 + 6 小時 = 20:00（半夜了，靠隔天早上客服回報才被發現）。
  detection gap = **6 小時**。
  action item：把『燈號異常』從半手動 + dogfood 升級為自動 alert（owner: Bob, due: 2026-06-15, acceptance: alert 在 staging 已能在 < 5 分鐘觸發 unit 不一致案例）。」
- **壞答案長什麼樣**：「14:00 開始有問題，20:00 我們知道」——沒寫 gap、沒寫怎麼縮短。
- **別人會 push back 什麼**：Dev 會說「這種 bug 本質上偵測不到」。
  回應：「**沒有偵測不到的 bug，只有沒設計偵測的 bug**。譬如 unit 不一致 → 寫一個 daily sanity check 對比 raw provider response 與內部表示。設計得出來。」

---

## Q2. 「mitigation 完成時間 vs 第一個 alert 時間，差多少？runbook 的哪一步拖累了？」

- **為什麼問這個**：response time = mitigation 完成 - alert ACK。
  這個數字檢視 14-runbook 是否真的 work。
  拖累的可能是：(a) runbook 步驟不清楚要 google、(b) 工具權限沒給要等申請、(c) 聯絡人聯絡不上、(d) mitigation 動作執行慢。
  每一種 → 對應不同的 action item。
- **好答案長什麼樣**：「Alert ACK：20:05（5 分鐘內 ACK，符合 SLA）；mitigation 完成：20:42（37 分鐘）。
  response time = 37 分鐘。拖累點：
  (a) runbook 04 第 3 步『執行 `launchdarkly toggle fx_signal_show --value=false`』，
  on-call 沒有 LaunchDarkly admin 權限，花了 15 分鐘找 DevOps Alice 給權限。
  action item：建立『所有 on-call 默認擁有 prod flag toggle 權限』（owner: Alice, due: 2026-05-31, acceptance: 新 on-call onboarding 時權限自動 provisioning 已寫進 IaC）。」
- **壞答案長什麼樣**：「37 分鐘還行啊」——沒分析瓶頸、沒 action item。
- **別人會 push back 什麼**：Dev 會說「給 on-call admin 權限風險太高」。
  回應：「**權限延遲 = 事故延長**。可以做 scoped 權限（只給 prod 部分 flag），但**不能因為怕誤觸發而讓 on-call 拿不到工具**。」

## Q3. 「Root cause 是什麼？這是真正的 root，還是 contributing factor？」

- **為什麼問這個**：**root cause fallacy** 是 postmortem 最常見的錯誤——
  寫「root cause: 工程師沒注意 unit」**完全錯**。這是 contributing factor，不是 root cause。
  真正的 root cause 要用 5-whys 推到「**為什麼系統允許這個錯誤發生**」的制度層次。
  停在「該員不夠細心」是 blame，不是 root cause analysis。
- **好答案長什麼樣**：
  > 表面原因：FX adapter 把台銀的 `rate_per_100` 直接當 `rate_per_1` 使用，導致 P0-4 建議現金額算成 1/100。
  > Why-1：為什麼 adapter 不轉換？因為 adapter code 沒寫 unit 轉換邏輯。
  > Why-2：為什麼 code 沒寫？因為 review 沒抓到——10-CR checklist 沒有「外部 vendor unit 一致性檢查」這條。
  > Why-3：為什麼 checklist 沒有？因為 SmartTrip 過去只接過一家 vendor（Wise），沒有 multi-vendor 經驗。
  > Why-4：為什麼沒有 multi-vendor 經驗就要切換？因為 13-rollback-plan 變更 A 的演練只演練「切換成功」沒演練「切換後資料一致性」。
  > **Root cause**：13-rollback-plan 的 vendor 切換演練缺少「資料一致性驗證」這個演練項目；10-CR checklist 缺少 multi-vendor unit 檢查。
  
- **壞答案長什麼樣**：「工程師沒注意」「unit 寫錯了」——這是 contributing factor，不是 root cause。
- **別人會 push back 什麼**：Dev 會說「但確實是寫錯了啊」。
  回應：「**個人寫錯不是 root cause，是徵狀**。任何工程師都會寫錯，制度設計要『**讓寫錯被攔下來**』。如果你的結論是『他下次注意』，下一個工程師還是會犯。」

## Q4. 「Contributing factors 有哪些？至少列 3 條，不要塞回 root cause。」

- **為什麼問這個**：複雜事故從來不是單一原因。寫「root cause」單一原因會掩蓋系統性問題。
  contributing factors 是「沒有它事故不會這麼嚴重」的因素——可能是時間點（剛好週末沒人）、可能是組合（兩個 release 一起上）、可能是文化（趕 deadline 略過 review）。
  列出來才能逐一改善。
- **好答案長什麼樣**：
  > Contributing factor 1（**監控**）：燈號計算缺乏 sanity check，事故發生後 6 小時才被察覺，期間 1,200 個行程被影響。
  > Contributing factor 2（**演練**）：13-rollback 變更 A 的 game day 演練只測「切換是否成功」，未測「切換後算式一致性」。
  > Contributing factor 3（**Review**）：10-CR checklist 缺少 multi-vendor unit 一致性檢查，PR review 兩位 reviewer 都未察覺。
  > Contributing factor 4（**時間點**）：事故發生在週五傍晚 release，週末客服人力低，第一個客服回報延遲。
  > Contributing factor 5（**文化**）：13-rollback Game Day 演練因為「上次都成功」而把驗證項目簡化了。
- **壞答案長什麼樣**：只列 1 條「unit 寫錯」——這是 root cause 的徵狀，不是 contributing factors。
- **別人會 push back 什麼**：PM 會說「列太多看起來像在找藉口」。
  回應：「**列多反而不是藉口，是負責**。每一條 contributing factor 都對應一個改善方向。藏起來才是逃避。」

## Q5. 「Action items 分 prevent / detect / mitigate 三類，每類至少 1 條，每條有 owner + due date + acceptance。」

- **為什麼問這個**：action items 不分類 = 全堆在「prevent」（不再發生），結果做不完。
  健康的 action items 分布應該是：
  - **prevent**（讓它不再發生）：1–2 條，通常成本最高
  - **detect**（更快發現）：2–3 條，CP 值最高
  - **mitigate**（更快復原）：1–2 條，runbook 補強
  分類強迫思考「即使下次還是發生，怎麼讓傷害減少」。
- **好答案長什麼樣**：
  > **Prevent**：在 10-CR checklist 加入「外部 vendor 整合 unit 一致性檢查」（owner: QA Carol, due: 2026-06-10, acceptance: checklist 已 merge、過去 3 個 PR 已 retroactive review）
  > **Detect**：建立 daily FX sanity check cron job（owner: Dev Bob, due: 2026-06-15, acceptance: staging alert 已能在 5 分鐘內觸發 unit 不一致案例）
  > **Mitigate**：所有 on-call 默認擁有 prod flag toggle 權限（owner: DevOps Alice, due: 2026-05-31, acceptance: IaC 已 merge、新 on-call onboarding 自動 provisioning）
  > **Mitigate**：14-runbook 04 燈號異常加入「強制 dogfood 每日早 09:00」步驟（owner: DevOps Alice, due: 2026-05-30, acceptance: runbook PR 已 merge、calendar 已排程）
  > **Prevent**：13-rollback game day 演練 SOP 加入「資料一致性驗證」必填項目（owner: DevOps Alice, due: 2026-06-30, acceptance: 下次 game day 模板已更新、QA Carol 已 review）

- **壞答案長什麼樣**：「Dev team 加強 review」「DevOps 補監控」——沒人、沒日期、沒驗收。
- **別人會 push back 什麼**：Dev 會說「sprint 已經滿了，這些 action item 我接不下」。
  回應：「**postmortem action items 默認 P0 優先序**，要砍別的東西出來做。如果接不下，當場跟 PM 排出『砍什麼』。不接受『之後再說』。」

## Q6. 「What went well 是什麼？這次有真的做對的事嗎？」

- **為什麼問這個**：postmortem 不只檢討錯誤，也要**保留並推廣對的事**。
  「what went well」常被當成客套（「大家都很努力」），但真正的好答案是「**這個 pattern 救了我們，要寫進 SOP**」。
  如果寫不出 well，要嘛是真的全錯（極少），要嘛是漏掉了某個救援的關鍵動作沒被認可。
- **好答案長什麼樣**：
  > Well 1：13-rollback feature flag `fx_signal_show` 設計救了我們——5 分鐘內隱藏燈號止血，否則 6 小時影響會變 12 小時。
  > **要推廣**：所有「資料正確性相關功能」都應該有 kill switch flag。寫進 09-NFR §operability。
  > Well 2：客服 FAQ 模板 v3.3 在事故發生前 1 週剛寫好，事故當下 30 分鐘內可上架。
  > **要推廣**：14-runbook 通訊段的模板要在 release 前寫，不要等事故發生才寫。
  > Well 3：on-call ACK 在 SLA 內（5 分鐘）。
  > **要推廣**：PagerDuty 設定要保持。
- **壞答案長什麼樣**：「大家很辛苦」「團隊合作好」——空話、沒可推廣的 pattern。
- **別人會 push back 什麼**：Dev 會說「沒什麼做對的吧，事故都發生了」。
  回應：「**事故規模沒擴大就是做對了**。沒 feature flag 影響會 12 小時不是 6 小時。沒 ACK SLA 響應會晚 30 分鐘。這些都是 well。」

## 送命題清單

這 3 題不問，3 個月後同樣的事故會再發生：

1. **「30 天後誰追蹤這些 action items 的完成率？低於 80% 怎麼辦？」**
   action items 寫了沒人追 = 沒寫。明確指定追蹤人（通常是 DevOps）、明確完成率門檻（< 80% 升級給 leadership）、明確下次 postmortem review action item completion。
   沒這條，這份 postmortem 三個月後變成 wiki 上的死文件。

2. **「這次事故是不是『同一個 root cause 第 N 次發生』？翻過去 6 個月 postmortem 查。」**
   重複事故 = 上次的 action item 沒做或做錯了。**重複事故的 postmortem 必須升級到 leadership review**，不能當作普通事故處理。沒這條，「同樣的事故每季發生一次」會被當常態。

3. **「我們的 postmortem 文化夠 blameless 嗎？當事人在會議裡有沒有覺得被指責？」**
   結束前 5 分鐘**直接問當事人**「這場會議你覺得 blameless 嗎？哪一句話讓你不舒服？」
   有就當場道歉並改寫該段。沒這條，下次出事工程師會藏，更難 postmortem。
