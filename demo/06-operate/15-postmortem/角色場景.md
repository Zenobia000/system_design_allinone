# 15 Postmortem · 角色場景

## 這場會議在做什麼

事故發生過，14-runbook 跑完了，使用者影響也大致止住了。
但**事故不是結束，是學習的起點**。

這場 90 分鐘的 **blameless postmortem** 在事故止血後 **72 小時內**舉行，
目的是：把「**剛剛這件事為什麼發生、為什麼晚發現、為什麼修慢了、怎麼讓它不再發生**」
變成具體可追蹤的 action items，**塞回 04-AC / 09-NFR / 10-CR / 14-runbook 四張上游卡**形成閉環。

**不是**找戰犯、**不是**寫公關稿、**不是**做技術 deep-dive PPT。
這場只做一件事：**把這次事故學到的教訓制度化**——讓下次事故的 detection / response / recovery 都更快。

**blameless 是不可妥協的原則**：
- 制度設計不夠，不是工程師「不夠小心」
- 監控缺失，不是工程師「應該注意」
- runbook 寫不清楚，不是 on-call「沒讀」
- 所有「該員教育訓練」「之後注意」的結論一律打回——這些不是 action item，是推卸責任的代名詞

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **DevOps（主責，你）** | 事故時間軸、監控數據、runbook 執行紀錄、escalation 紀錄 | 5+ 條 action items（含 owner / due date / acceptance），塞回上游卡 |
| **PM** | 使用者影響量化、客服回報數據、商業影響評估 | 確認 action items 的優先序符合產品階段 |
| **Dev（事故當事人 + 相關 module owner）** | code change history、診斷過程、mitigation 執行細節 | 自己要寫 / 改哪些 code & test 防止再發 |
| **QA** | 既有測試覆蓋、為什麼這個 bug 沒被測到、可加哪些 test case | 補上的 regression test 清單 |

## 你扮演的角色（DevOps）

你是「**制度設計者**」。本場會議你只做兩件事：

1. 每當有人說「**該員應該⋯⋯**」「**他下次注意⋯⋯**」「**我們以後要⋯⋯**」，立刻打斷：
   「**這不是 action item，這是 wish**。重新講——是什麼**制度／工具／流程**讓這次他沒注意？我們改哪個制度讓下次注意自動發生？」
2. 每一條 action item，當場逼出三件套：
   - **owner**（一個人，不是「DevOps 團隊」）
   - **due date**（具體日期，不是「下個 sprint」）
   - **acceptance criteria**（怎麼算做完，不是「弄好」）
   缺一不可，不接受「之後補」。

**禁忌動作**：本場會議的會議紀錄不准出現：
- 「該員教育訓練」「之後注意」「下次小心」「應該要⋯⋯」（person-targeted 結論）
- 「DevOps 處理」「Dev 看一下」「之後排」（沒明確 owner / due date）
- 「修好它」「弄完它」「處理掉」（沒 acceptance criteria）

一出現就打回重寫。罰自己 100 元。

## 會議結束時，桌上要有什麼

- **完整 postmortem 文件**，結構固定（learn from Google SRE）：
  1. **Summary**（3 句：什麼壞了、多久、影響誰）
  2. **Timeline**（≥ 6 個時間點：第一個信號 → 第一個影響 → 第一個 alert → ACK → mitigation 開始 → 止血 → 後續 hotfix）
  3. **Impact**（量化：影響使用者數、收入損失、SLO 消耗、客服 ticket 數）
  4. **Detection**（怎麼被發現的？為什麼這時間才發現？detection gap 在哪？）
  5. **Root Cause**（**一個**根本原因，用 5-whys 推到底）
  6. **Contributing Factors**（≥ 3 條 contributing factors，避免 root cause fallacy——複雜事故從來不是單一原因）
  7. **What Went Well**（**真的**做對的事，不是客套，是要保留並推廣的 pattern）
  8. **What Went Poorly**（具體做錯的事，制度層次，不指人）
  9. **Action Items**（≥ 5 條，分 prevent / detect / mitigate 三類，每條含 owner + due date + acceptance）
- **Action items 流向矩陣**：每條 AI 標明要塞回 04-AC / 09-NFR / 10-CR / 14-runbook 哪一張卡的哪一段
- **下次 postmortem 追蹤排程**：30 天後檢查 action items 完成率（< 80% 則升級到 leadership）

## 為什麼這場會議重要

Postmortem 是 SDLC 的**閉環機制**。沒有它，整條 SDLC 是線性的：
JTBD → PRD → ADR → ... → release → 事故 → ??? → 下次事故重來一次。

postmortem 把這條線**彎回去**：事故的教訓**真的**回到 04-AC / 09-NFR / 10-CR / 14-runbook，
讓上游卡變得**更有抵抗力**，下次同類事故就會被擋下來。

跳過這場會議的代價：**同一種事故會重複發生 3 次以上**——
- 第 1 次：「沒人想到會這樣」
- 第 2 次：「上次說好要改的⋯⋯沒人接到」
- 第 3 次：「我們不是處理過了嗎」→ 然後沒人記得處理結果

SmartTrip MVP 階段 4 週驗證窗，1 個事故汙染 1 週數據。
不做 postmortem，4 週驗證窗會被同一個事故拖垮兩次，第二次事故發生時 PM 連是不是同一個都判斷不出來。
