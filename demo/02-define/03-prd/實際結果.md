## 教學要點（看完 AI 輸出後讀這段）

### 1. P0 / P1 / P2 切分的判準是什麼？

**P0 = 砍掉就無法驗證 riskiest_assumption 的功能**。
不是「使用者最想要」也不是「最容易做」，而是「沒有它，4 週驗證結果無意義」。

| FR | 為何是 P0 |
|---|---|
| FR-004 即時匯率 | 模擬值會污染種子簡報 G3「差異化認知」訊號 |
| FR-005 使用分析 | 沒它 → 連 kill_criteria 都無法觸發 |
| FR-001~003 行程/換匯/燈號 | 三者合起來 = 驗證主張本身 |

學生最常犯的錯：把「使用者會喜歡」當 P0 判準，把回顧/心情故事放 P0，結果 4 週做不完。

### 2. `counter_metric` 為什麼是「生成時間中位數 ≤ 3 分鐘」？

`counter_metric` = **防止 goal-hacking 的副指標**。
若只看啟用率，PM 會傾向把流程拉長（多問幾題 → 更個人化 → 提高完成意願）來衝啟用率，
但這會破壞 JTBD-001 的 ≤ 3 分鐘 success_criteria。
所以 counter_metric 直接綁 JTBD-001 + 01-jtbd 的 JTBD-001 vs JTBD-005 互斥。

### 3. NFR 4 象限怎麼對應到 SmartTrip？

| 象限 | 本卡選擇 | 為何不是更嚴 |
|---|---|---|
| latency p95 < 3s | JTBD-001 要 3 分鐘總時間 | < 1s 會過度工程化 |
| a11y AA | 戶外通勤手機使用情境 | AAA 拖慢 4 週驗證窗 |
| security internal | 無帳號無金流 | confidential 對應到帳號系統，V1 才需要 |
| audit 90 天無 PII | Plausible 預設 | 完整 GDPR 流程當 MVP 是過度設計 |

學生常見錯：把 NFR 抄業界 best practice，忘了本案是 4 週 MVP，過嚴會直接做不完。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `functional_requirements` 每條 | `04-acceptance-criteria/` 每條展開 Given/When/Then |
| `non_functional_requirements` | `04-acceptance-criteria/` NFR AC + `05-adr/` 技術選型 decision_drivers |
| `decision_log[localStorage]` | `05-adr/` ADR-001（同決策但用 ADR 格式記錄） |
| `risks_and_unknowns.risks[1]` 即時匯率成本 | `05-adr/` ADR-002（API 選型） |
| `out_of_scope` | `06-c4-diagram/` 系統邊界 |
| `counter_metric` | `09-non-functional-reqs/` + 監控告警 |

### 5. PRD 與 02-value-hypothesis 的銜接

02-value-hypothesis 給的是「**驗證假設**」框架，PRD 是「**為了驗證該假設，必須做什麼功能**」。
若 PRD 的 P0 與 value-hypothesis 的 riskiest_assumption 對不起來——
做出來的 MVP 4 週後拿到的數據，無法回答「假設是否成立」這個問題。
這就是為什麼這張卡的思考步驟 5 特別寫「P0 必須足以驗證 riskiest」。

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 把所有「使用者想要的功能」都放 P0 | 規則 7 + 思考步驟 5 | P0 篩選用 riskiest_assumption 反推，非主觀重要性 |
| FR 寫成「使用 React + Tailwind 實作行程頁」 | 規則 7 | PRD 只寫 what & why，框架選型屬 ADR |
| `success_metrics` 全標 H 並寫死數字 | 規則 6 | 無 baseline 時標 M/L，並在 `self_review.lowest_confidence` 寫補洞 |
| NFR 只寫 latency，沒寫 a11y / security / audit | 規則 4 | 4 象限都要寫；不適用時要寫「為何不適用」 |
| `out_of_scope` 寫成「不做匯率燈號」 | 規則 5（混淆） | 那是**產品 non-goal**；本卡的 out_of_scope 是「不寫實作 / 不畫 UI / 不出 API spec」 |
| `decision_log` 只寫 chosen，不寫 rejected_reason | 規則 2 | 必須列至少 2 個 rejected option + 各自為何不選 |

## 交件 checklist

- [ ] 每條 FR 都有 priority（P0/P1/P2）+ source + confidence
- [ ] P0 的功能合起來足以驗證上游 02-value-hypothesis 的 riskiest_assumption
- [ ] NFR 4 象限（latency / a11y / security / audit）都有寫，且每個都有「為何此值」
- [ ] `counter_metric` 對應到一個 JTBD 互斥（防 goal-hacking）
- [ ] `decision_log` 至少 2 條，每條列 ≥ 2 個 options_considered + rejected_reason
- [ ] `out_of_scope` 至少 3 條，且是**文件 scope**（不寫 UI、不寫 API、不寫 sprint），不是產品 non-goal
- [ ] `self_review.lowest_confidence` 對應到每個 M/L 標註的補洞計畫
