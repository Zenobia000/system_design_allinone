> 用 SmartTrip FX 種子簡報（`demo/種子簡報.md`）+ 上游 01-JTBD（`demo/01-discovery/01-jtbd/SmartTrip示範.md`）

## 上游素材速查

**JTBD（來自 01-JTBD SmartTrip示範.md）**：

- **JTBD-001** [H]：3 分鐘決定該帶多少現金、何時換 → confidence [H]
- **JTBD-002** [M]：何時換匯划算的明確信號（燈號）→ confidence [M]
- **JTBD-003** [L]：高頻使用者反覆微調最佳化 → P2 排除
- **JTBD-004** [L]：在朋友面前顯得會理財 → emotional/social job
- **JTBD-005** [M]：旅途中即時記開支對比預算

**Hypothesis（來自 02-value-hypothesis）**：

- **H1**：60% 行程「實際 vs 建議換匯誤差 < 15%」→ 30 天回訪 ≥ 20%
- **H2**：使用者願意相信燈號（滿意度 ≥ 4/5）→ 留存提升
- **H3**：無提示 60% 能說出「換匯/現金」差異 → 護城河成立

## Q2 示範：「為什麼 P0-X 是 P0 而不是 P1？分階段依據？」

**分階段判準（會議第 5 分鐘宣布，並貼在白板）**：

> 一條需求進 P0 的條件：**(a) 對應至少 1 條 JTBD-NNN [H or M] + (b) 4 週驗證窗能完成 + (c) H1/H2/H3 任一假設驗證若沒它就斷掉**。
> 三條缺一就降 P1。

**逐條解釋**：

- **P0-1 ～ P0-4 為何 P0**：(a) 對 JTBD-001 [H] (b) 已上線 (c) H1 的「誤差 < 15%」沒有規劃 + 三方案 + 建議換匯額這條鏈，根本量不到。
- **P0-5 為何 P0**：(a) 對 JTBD-002 [M] (b) 燈號邏輯已上線 (c) H2 「使用者願意相信燈號」沒燈號就驗不到。
- **P0-6 為何 P0**：(a) 對 JTBD-001 + JTBD-005 (b) 已上線 (c) 沒儲存功能，使用者無法二次開啟，H1「30 天回訪 ≥ 20%」沒得量。
- **P0-7 為何 P0**：(a) 對 JTBD-005 [M] (b) 已上線 (c) H1 的「實際現金 vs 建議換匯」沒開支紀錄就沒分子。
- **P0-8 為何 P0（爭議點）**：(a) 對 JTBD-002 (b) 待補 (c) **H2 沒它就空話**——用模擬資料量出來的滿意度 4/5 不算數，公司會在 V1 決策時被誤導。Architect 評估 1.5 週、可塞進 4 週窗。
- **P0-9 為何 P0（爭議點）**：(a) 對應全部假設的量測鏈 (b) 待補 (c) **沒有事件，H1/H2/H3 全部無法驗證**，4 週驗證窗等於白做。

**為何 P1 不升 P0**：

- 旅程回顧 / 機票估算 / 分享功能：對應 P1 段；不直接驗證 H1/H2/H3。塞進去會排擠 P0-8 / P0-9 的開發容量。

## Q4 示範：「P0 的 scope 邊界與外部依賴」

| P0 # | Scope 包含 | Scope 不包含 | 外部依賴 | 失敗策略 |

## 現場對話（12 輪攻防示範）

> 場景：90 分鐘會議第 50 分鐘，討論「P0-8 即時匯率」與「進階編輯模式」的取捨。

**PM**：「P0-8 即時匯率，我標 P0。Architect 你估多久？」

**Architect**：「資料源 spike 3 天 + 整合 1 週 + fallback 邏輯 2 天，共 1.5 週。但前提是 4/29 前定資料源——目前 exchangerate.host、Frankfurter、OpenExchangeRates 三選一還沒決。」

**PO**：「能不能降 P1？我們燈號已經上線了，使用者根本看不出是模擬資料。」

**PM**：「你看 PRD §附錄寫什麼？『把模擬匯率換成即時匯率，否則護城河「省錢」站不住』。
H2 假設『使用者願意相信燈號』，量到滿意度 4/5 全是假的，因為使用者相信的是**假數字**。
這條不上 P0，4 週驗證窗等於沒做。」

**PO**：「⋯⋯那我這邊的『進階編輯模式』呢？這也是衝動型回頭客要的。」

**PM**：「等等。01-JTBD §Q5 我們已經決議過——JTBD-001（3 分鐘快）跟 JTBD-003（精打細算反覆比較）**心智模型互斥**。
進階編輯模式對應 -003，標 P2。你重提就是改 JTBD 結論，要改先重開 JTBD 會議。」

**PO**：「我不是要重開，我是想說『順便加一下』編輯功能不會破壞 -001。」

**Architect**（插話）：「『順便』要 8 週。可編輯每項 + 換幣別 + 調 buffer% + 比較 A/B，每項 2 週。
4 週窗放不下。」

**UX**：「而且編輯模式的 UX 跟『選心情就生方案』完全相反——一個是『幫我決定』，
一個是『讓我控制』。同一個介面塞兩種心智模型，使用者只會困惑。」

**PM**：「對。所以我的提案是：**進階編輯模式 → P2，data model 預留 buffer 參數，UI 不暴露**。
PO，這個寫進 decision log，三個月後 -003 真的有需求我們知道是誰先提的。」

**PO**：「⋯⋯好。但我要在 OQ 加一條『進階編輯模式重啟條件』——需要看到什麼數字才會重開 -003？」

**PM**：「合理。OQ 加：『若 4 週驗證窗結束後，超過 30% 使用者反映「想自己調 buffer」，重開 JTBD-003。』
Architect，4 週窗你能在 P0-9 分析事件裡加一個 `manual_adjust_request` 嗎？」

**Architect**：「可以，算在 P0-9 範圍內，多 1 天。」

**PM**：「成交。最後一輪——P0-9 隱私同意，誰跟法務確認？我這週能談？」

**PO**：「我約法務週四 10 點，PM + Architect 都來。決議寫進 OQ owner 欄位。」

**PM**：「好。今天會議結論：P0 共 9 條（P0-1 ～ P0-9）；P1 4 條；P2 5 條；OQ 6 條，其中 3 條阻擋 P0、必須 4/29 前關閉。
散會前 5 分鐘，我把白板拍下來貼到 Slack，今天結論大家有異議現在說，散會後改要重開會。」

## 下游影響：本場結論如何流向後續卡

| 下游卡 | 引用本場的哪個欄位 | 怎麼用 |
|---|---|---|
| **04-acceptance-criteria** | Q5 acceptance hint 表（P0-1 ～ P0-9） + Q6 user story 表（US-1 ～ US-6） | QA 對每條 P0 user story 寫完整 G/W/T，本場的 hint 是入口 |
| **05-ADR** | Q4「P0-8 外部依賴：資料源 4/29 前定案」 | ADR 寫「為什麼選 exchangerate.host 不選 Frankfurter」，scope 由本場鎖定 |
| **06-spec** | Q5 acceptance hint「金額格式化規則」「失敗 fallback 文案」未定的部分 | spec 階段補完，但不准擴大 scope |
| **07-API-Spec** | Q4 「P0-1 必填欄位」「P0-3 行程卡片資料結構」「P0-7 開支欄位」 | API schema 直接抄 PRD §6 + 本場澄清的欄位 |
| **10-code-review-checklist** | Q5 acceptance hint 表 | PR review 必檢「該 PR 是否滿足對應 P0 的 hint」 |
| **11-unit-test** | Q6 user story 表（US-1 ～ US-6） | 每條 user story 至少 1 個 unit test，命名對應 US-N |
| **12-release-plan** | Q2 分階段判準（P0 → P1 → P2） | release 順序：P0 收尾 → 4 週驗證 → P1 →（驗證通過）V1 |
| **14-metrics** | PRD §7 成功指標（已寫死，不准 14-metrics 改） | metrics dashboard 直接量 §7 的 6 個數字 |
| **15-postmortem** | Q3 decision log | 出事時追溯「當時為什麼這樣決定」 |

**特別注意——數字流向鏈**：

- 01-JTBD §Q4「**誤差 < 15%、3 分鐘內、無提示 60%**」
  → 02-hypothesis H1/H2/H3
  → **03-PRD §7 成功指標（直接抄，不准改）**
  → 04-AC G/W/T 的閾值（直接抄）
  → 14-metrics dashboard 的閾值（直接抄）

任何下游卡若改動這四個數字，**自動觸發回頭重開 JTBD 會議**——這條 SOP 寫進 decision log。
