# 03 PRD · 關鍵提問（PM 必問）

> 本場會議 90 分鐘，PM 只要把這 7 題問完、問對，會議就成功了。
> PM 的任務不是「**收齊大家的意見**」，是「**逼出每條 P0 的取捨**」。
> 開放題（「大家覺得呢？」）會讓會議跑 3 小時還收不了；
> 選擇題（「A 還是 B？理由？」）30 分鐘就能定 4 條 P0。

---

## Q1. 「**每條 P0 對應到 01-JTBD 的哪一條？對應到 02-hypothesis 的哪一條 H？**」

- **為什麼問這個**：PRD 是 JTBD 與 hypothesis 的**翻譯文件**，不是新發想文件。
  每條 P0 都必須掛 `JTBD-NNN` + `H-NNN` 兩個 ID，掛不上的就是團隊自己加的願望清單，
  踢出 P0、進 backlog。這條規則保證 PRD 不會在中段「漂走」。
- **好答案長什麼樣**：「P0-4『建議換匯現金額』對應 JTBD-001（衝動型 3 分鐘規劃）+ H1（誤差 < 15% → 30 天回訪 ≥ 20%）。」明確的雙 ID 對應 + 一行說明。
- **壞答案長什麼樣**：「P0-4 是 PO 上週開會說一定要做」「P0-4 是競品都有」——這兩條都是踢出 P0 的訊號。
- **別人會 push back 什麼**：PO 會說「但這條商業上很重要！」回應：「商業重要 ≠ 假設驗證重要。商業要就進 P1，先不卡 4 週驗證窗。」

---

## Q2. 「**為什麼 P0-X 是 P0 而不是 P1？分階段的依據是什麼？**」

- **為什麼問這個**：P0/P1/P2 的分階段是 PRD 的**核心輸出**——不是「全部都想做、只是排個順序」，
  而是「驗證核心假設**最小**需要哪些 → P0；錦上添花但能延後 → P1；架構預留但本期不做 → P2」。
  分階段的判準必須一致：是 by frequency × pain（JTBD 排序）、by hypothesis dependency（H1 需要哪些 P0 才能量測）、還是 by technical risk（先做有風險的 spike）。
- **好答案長什麼樣**：「P0-8 即時匯率是 P0，因為 H2『使用者願意相信燈號』完全靠真實匯率才能驗證。模擬資料量到的滿意度不算數。」
- **壞答案長什麼樣**：「P0-8 是 P0，因為團隊覺得很重要」「先標 P0 之後再看」——沒判準、沒理由。
- **別人會 push back 什麼**：Architect 會說「P0-8 接外部 API 風險高，建議降 P1」。回應：「降 P1 = 4 週驗證窗驗不到 H2。要嘛找 fallback 資料源，要嘛重新檢視假設，不能單方面降階。」

---

## Q3. 「**這條被排除 / 降到 P2 的需求，理由是什麼？寫進 decision log 了嗎？**」

- **為什麼問這個**：被踢出 P0 的需求**會回來**——三週後 PO 會問「為什麼當時不做 X？」沒寫 decision log，
  PM 會啞口無言。decision log 不是行政文件，是**團隊的記憶**。
- **好答案長什麼樣**：「JTBD-003（精打細算反覆比較）對應的『進階編輯模式』被降 P2，理由：(a) 訪談只有 1/5 樣本支持 (b) 與 JTBD-001『3 分鐘出方案』心智模型相反 (c) Architect 估 8 週、超出 4 週驗證窗。decision log 寫在 PRD §附錄。」
- **壞答案長什麼樣**：「之後再做」「PO 同意先不做」——沒有可追溯的判準。
- **別人會 push back 什麼**：團隊會懶得寫。回應：「不寫，三個月後爭執再爆一次，比現在花 5 分鐘貴 100 倍。」

---

## Q4. 「**這條 P0 的 scope 邊界在哪？依賴哪些外部假設？**」

- **為什麼問這個**：scope creep 從「順便處理一下 edge case」開始。
  每條 P0 都要明確列「**做到哪算完**」+「**靠誰才能做完**」。
  外部依賴沒列出來，到開發時才發現「等供應商給 API key」整條 P0 都卡死。
- **好答案長什麼樣**：「P0-8 即時匯率 scope = 主要 5 幣別（JPY/KRW/THB/USD/EUR）；不做 30+ 幣別（屬 P1）；
  外部依賴：選定資料源（exchangerate.host 或 Frankfurter，4/29 前決定）+ 失敗時 fallback 顯示『模擬資料』標籤。」
- **壞答案長什麼樣**：「P0-8 接即時匯率 API」——沒講範圍、沒講失敗策略、沒講選哪家。
- **別人會 push back 什麼**：UX 會問「失敗的 UI 長怎樣？」回應：「**UI 不在這場會議講**，但這場會議要鎖『失敗時必須顯示模擬標籤』，UX 細節留 04-AC 與 06-spec。」

---

## Q5. 「**每條 P0 的 acceptance hint 高層次描述是什麼？（不寫 G/W/T，那是 04-AC 的事）**」

- **為什麼問這個**：PRD 不寫完整 Given/When/Then（那是 04-AC 的工作），
  但 PM 必須給出「**怎樣才算這條 P0 完成**」的一句話描述，
  好讓 04-AC 場次有起點。沒寫 hint，QA 第一個小時都在猜「P0-4 到底要驗什麼」。
- **好答案長什麼樣**：「P0-4 acceptance hint：『使用者按生成 → 看到三方案 → 每個方案下方顯示「建議換匯現金 ¥XXX,XXX」+ 台幣約當值 + 緩衝說明』。完整 G/W/T 由 04-AC 寫。」
- **壞答案長什麼樣**：「P0-4 acceptance：使用者能看到建議換匯額」——太籠統，QA 寫不出測項。
- **別人會 push back 什麼**：團隊會說「直接把 AC 寫完不是更好？」回應：「不好。AC 是 QA 主導的攻防會議，PM 寫一遍 QA 還要再寫一遍，浪費 60 分鐘。PM 給 hint，QA 寫 G/W/T。」

---

## Q6. 「**P0 對應的 user story 怎麼寫？句型對嗎？**」

- **為什麼問這個**：user story 是 04-AC、11-unit-test、13-user-acceptance-test 的**共通語言**。
  句型必須是「**作為 [persona]，我想 [action]，這樣我 [outcome]**」——
  少 outcome 就會變成 feature description（這是 P1 的事），少 persona 就會變成系統設計（這是 ADR 的事）。
- **好答案長什麼樣**：「**作為衝動型旅客，我想選心情 + 預算範圍就生出三種方案，這樣我不用花時間細排就能決定。**」三段齊全、persona 對應 PRD §4、outcome 對應 JTBD-001。
- **壞答案長什麼樣**：「使用者能生成三方案」——這是系統行為，不是 user story。
- **別人會 push back 什麼**：開發會說「我看 story 不知道要做什麼」。回應：「故事不是給開發看的，是給 QA 寫 AC 的。開發看 06-spec。」

---

## Q7. 「**Open Questions 怎麼處理？哪些是阻擋 P0 的？哪些可以延到 V1？**」

- **為什麼問這個**：PRD 一定有沒查清楚的東西（資料源成本、法務免責、商業模式），
  把它們明確分成「**阻擋 P0**」（必須 PRD 簽收前解決）和「**延到 V1**」（記下來但不卡 MVP），
  避免「全部都還沒決定 → PRD 一直無法簽收 → 開發無法啟動」的死結。
- **好答案長什麼樣**：「Open Q1『即時匯率資料源選哪個』→ 阻擋 P0-8，4/29 前 Architect spike 完回報。
  Open Q4『聯盟分潤 vs 訂閱』→ 延 V1，不卡 MVP。」每條 OQ 標 owner + 截止日 + 是否阻擋。
- **壞答案長什麼樣**：「之後討論」「PM 再看看」——沒 owner、沒截止日、不知道是否阻擋。
- **別人會 push back 什麼**：PO 會把所有 OQ 都標阻擋。回應：「全部阻擋 = PRD 永遠簽不了。挑真的會讓 P0 寫不下去的，其他都延 V1。」

## 送命題清單

這 3 題不問，3 週後開發到一半會回來找你算帳：

1. **「P0-8 跟 P0-9 的技術風險誰評估的？4 週能做完嗎？」**
   PM 自己拍胸脯說「應該可以」是最大誤區。Architect 沒在現場估，到 sprint 2 才發現外部 API 要審 2 週，整個驗證窗破功。

2. **「P0 跟 P1 的判準如果只有 PM 一個人懂，這 PRD 就廢了。」**
   PO 跟 UX 要能複述「為什麼 X 是 P0 而 Y 是 P1」。不能複述 = 沒對齊 = 兩週後又會開一次同樣的會。

3. **「PRD §7 的成功指標數字哪裡來的？跟 01-JTBD §Q4 的 success criteria 一致嗎？」**
   如果不一致，整條 SDLC 因果鏈斷掉——JTBD 量誤差 < 15%，PRD 卻寫滿意度 ≥ 4/5，
   04-AC 跟 14-metrics 各做各的，最後不知道假設驗了沒。
