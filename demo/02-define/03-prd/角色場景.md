# 03 PRD · 角色場景

## 這場會議在做什麼

JTBD 翻譯完、value hypothesis 簽完之後，PM 召集 PO、UX、Architect，
把「3–5 條 JTBD + N 條假設」轉換成 **P0/P1/P2 需求清單**與 **user story**。
**不是**創意發想會，**不是**畫面評審會，**不是**架構決議會。目的只有一個：
**每條進 P0 的需求都必須掛 `JTBD-NNN` + `H-NNN` 來源**，沒掛來源的全部踢出 P0。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **PM（主責，你）** | 01-JTBD 文件、02-value hypothesis、種子簡報、競品 scope 對照 | 一份排序過的 P0/P1/P2 需求表、user story 清單、open questions |
| **PO** | backlog、商業優先序、之前打槍的 feature、合作夥伴承諾 | 確認 P0 不違反商業承諾、知道 P1 何時上 |
| **UX** | persona 草稿、journey map、訪談情境素材 | scope 邊界（哪些畫面不畫、哪些 state 不處理） |
| **Architect** | 技術可行性、相依的外部 API、4 週驗證窗能不能塞進 P0-8 | 知道 P0 的技術風險點、需要先 spike 的項目 |

## 你扮演的角色（PM）

你不是寫文件的人，你是 **Scope 看門人**。本場會議你只做三件事：

1. 每條候選需求問：「**對應哪條 JTBD？哪條假設？**」答不出來就踢出 P0。
2. 每條 P0 問 PO：「**進這條，要放棄什麼？**」沒答出 trade-off 的不准進。
3. 每條 P0 問 Architect：「**4 週驗證窗能完成嗎？**」答不出來就降 P1 或拆細。

**PM 的 mindset**：
> 「我不是要把所有人的點子寫進文件，我是要決定**哪些不寫進文件**。
>  每多進一條 P0，4 週驗證窗就少一週給其他 P0。」

**禁忌動作**：本場會議不准講以下這些字：

- 「使用者**友善**」「**直覺**操作」「**流暢**體驗」——形容詞 = 無法驗收 = 假需求
- 「**按鈕**」「**頁面**」「**API 接哪家**」「**用什麼 framework**」——那是 05-ADR / 06-spec / 07-API 的事
- 「**順便加一下**」「**這個應該不難**」——estimation 不是你拍胸脯，是 Architect 講

一講就罰 100 元，這是認真的——一開始講解法，scope 就跑掉了。

## 會議結束時，桌上要有什麼

- **P0 需求清單**（4–9 條），每條含：
  - 需求編號 `P0-N`
  - 對應 `JTBD-NNN` + `H-NNN` 來源（**強制**，不准空）
  - 一行需求描述（祈使句、無形容詞）
  - 高層次 acceptance hint（不是完整 G/W/T，那是 04-AC 卡的事）
  - Architect 標註 `[T-RISK: 高/中/低]`
- **P1 清單**（快速跟進、非阻擋上線）
- **P2 清單**（架構預留、本期不做）
- **User Story 清單**（3–8 條，「作為 X 我想 Y 這樣我 Z」句型，對應到 P0）
- **被踢出 P0 的需求 + 理由**（decision log，未來追溯用）
- **Open Questions**（資料源沒定、商業模式沒定、法務沒查清的，全部列出來）
- **送進 04-AC 的問題清單**（每條 P0 user story 在 AC 階段要釐清什麼）

## 為什麼這場會議重要

PRD 是 SDLC 的**契約點**。下游每張卡都直接引用：

- **04-AC** 把每條 P0 user story 拆成 Given/When/Then
- **05-ADR** 引用「P0-8 需要即時匯率」當作技術選型的功能需求
- **07-API-Spec** 引用 P0-1～P0-4 的資料欄位定義 schema
- **10-Code Review** 拿 P0 acceptance hint 當 PR review 的 checklist
- **12-Release Plan** 引用 P0 排序決定 release 順序
- **15-Postmortem** 評估「我們做了該做的事嗎」的基準

跳過這場會議的代價：**PRD 變成 feature list**——
工程師拿到一張 30 條功能的清單，每條都「好像很重要」，沒有取捨依據；
QA 拿到一份「使用者友善」當驗收標準，測什麼都對也都不對；
PO 三週後加新需求，沒人能說「這違反 P0 排序」。
最後 4 週驗證窗變 12 週，假設沒驗到，產品沒上線。

## 跟 01-JTBD / 02-value-hypothesis 的關係

- **01-JTBD 的 success criteria**（例：「3 分鐘內」「誤差 < 15%」）→ 直接抄進 PRD §7 成功指標
- **02-value-hypothesis 的 H1–H3** → 每條 P0 要對應至少 1 條 H
- **01-JTBD 的 mutually exclusive jobs** → PRD 的 P0/P2 取捨依據（被排除進 P0 的另一條，標 P2「架構預留」）

**鐵律**：JTBD 跟 hypothesis 寫死的數字，PRD 不准改。
要改，回頭重開 JTBD 會議。
