# 04 Acceptance Criteria · 角色場景

## 這場會議在做什麼

03-PRD 把 P0 user story 列完之後，QA 召集 PO 與 Dev，
**對每條 P0 user story 寫出 Given/When/Then + 失敗條件 + 邊界場景**。
**不是**測試規格撰寫會，**不是**自動化測試設計會，**不是**bug triage 會。目的只有一個：
**把「使用者要什麼」翻成「機器與人都能判定『過了 / 沒過』的條件**」。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **QA（主責，你）** | 03-PRD user story 表、PRD acceptance hint、過往線上 bug pattern | 完整 G/W/T 清單、邊界場景表、Definition of Done |
| **PO** | 商業 trade-off（「這個 edge case 不處理會被客訴嗎？」）、persona 行為知識 | 確認破壞性場景的處理決策符合商業優先序 |
| **Dev** | 技術可行性（「這個邊界要處理需要重構整層」）、現有錯誤處理機制 | 知道每條 G/W/T 對應到的程式碼修改範圍 |

## 你扮演的角色（QA）

你不是寫測試的人，你是 **破壞性思維者（Adversarial Thinker）**。本場會議你只做三件事：

1. 每條 P0 user story 先寫 happy path（1 條），然後**強迫自己想 3 種搞壞它的方法**。
2. 每個破壞性場景問 PO：「**這發生時系統要怎麼反應？降級？阻擋？靜默？**」沒答出就 mark Open Q。
3. 每條 G/W/T 寫完問 Dev：「**這條真的可測嗎？怎麼模擬 Given？**」測不出來就重寫。

**QA 的 mindset**：
> 「**Happy path 只是 AC 的 20%**。
>  使用者按按鈕、結果跑出來——這是最不需要寫的部分。
>  真正值錢的 AC 是『**網路斷的瞬間、輸入 emoji、按兩次、儲存到滿、後端回 500**』——
>  這些場景沒寫進 AC，PR review 看不到、unit test 不會寫、上線就炸。」

**禁忌動作**：本場會議不准講以下這些字：

- 「**應該要 work**」「**不會有人這樣用**」「**這個 case 很少**」——少見 ≠ 不用處理，要明示「不處理」的決策
- 「**之後再說**」「**先做 happy path 就好**」——這是技術債的源頭，要明示是 P1 還是 won't fix
- 「**這個我來測**」「**這個 QA 看就好**」——AC 是契約，不是分工，每條都要寫清楚誰判定

一講就罰 100 元——一旦把破壞性場景往後延，上線後通通變客訴。

## 會議結束時，桌上要有什麼

- **每條 P0 user story 對應一張 AC 卡**，內含：
  - **Happy Path G/W/T**（1 條，必填）
  - **Sad Path G/W/T**（至少 3 條，破壞性場景）
  - **邊界值清單**（空字串、極大值、極小值、零、負值、Unicode、emoji、超長字串）
  - **失敗降級策略**（API fail → 顯示什麼？儲存 fail → 重試還是放棄？）
  - **Definition of Done**（一行：什麼算「這條 P0 真的做完了」）
- **共通破壞性場景清單**（網路斷、後端 5xx、併發、髒資料、權限失效）——適用所有 P0
- **Won't Fix 清單**（明示哪些場景**故意不處理**，含理由）→ 寫進 decision log
- **Open Questions**（破壞性場景的處理決策需要 PM / 法務 / Architect 回覆的）
- **送進 11-unit-test 的測試案例 outline**

## 為什麼這場會議重要

AC 是 SDLC 的**判定基準**。下游每張卡都直接引用：

- **05-ADR** 引用 AC 的破壞性場景決定技術選型（例：「需要支援離線降級」→ 影響 storage 選型）
- **06-spec** 引用 AC 補完錯誤訊息文案、降級畫面 UI
- **07-API-Spec** 引用 AC 定義錯誤碼、retry policy
- **10-code-review-checklist** 每條 PR 必對照「對應 P0 的 AC 全部滿足？」
- **11-unit-test** 每條 AC 直接變一個或多個 test case
- **13-user-acceptance-test** UAT 腳本直接抄 AC happy path + sad path
- **15-postmortem** 出事時追溯「這個場景 AC 寫了嗎？沒寫為什麼？」

跳過這場會議的代價：**Dev 自己腦補 acceptance**——
每個工程師對「完成」的定義不同，PR 進來 reviewer 不知道該檢什麼，
QA 在最後一週才發現「咦這個場景沒處理」，要嘛硬上、要嘛延期。
線上炸了之後 postmortem 寫「acceptance criteria 不完整」——但已經晚了。

## 跟 03-PRD 的關係

- **03-PRD §Q5 acceptance hint** → 04-AC 的**起點**（happy path 模板），但 PRD 寫的是高層次描述
- **03-PRD §Q6 user story** → 04-AC 的**單位**（一條 US 一張 AC 卡）
- **03-PRD §Q7 Open Questions** → 若 OQ 涉及 acceptance（例：「失敗 fallback 文案」），這場會議要關閉

**鐵律**：AC 寫完發現 PRD 漏了某條 P0 → **不准在 AC 場次補 P0**，回頭重開 PRD 範圍會議。
AC 的職責是「**把 P0 寫精**」，不是「**把 P0 寫多**」。
