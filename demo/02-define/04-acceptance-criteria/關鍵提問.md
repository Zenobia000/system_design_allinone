# 04 Acceptance Criteria · 關鍵提問（QA 必問）

> 本場會議 60 分鐘，QA 只要把這 6 題問完、問對，會議就成功了。
> QA 的任務不是「**寫好 happy path**」，是「**逼團隊正視破壞性場景**」。
> 同情題（「這應該 work 吧？」）會讓會議在 happy path 打轉；
> 破壞題（「網路斷了會怎樣？」）30 分鐘逼出真正的失敗處理決策。

---

## Q1. 「**這條 user story 的邊界值有哪些？空、極大、極小、零、負、Unicode、emoji？**」

- **為什麼問這個**：邊界值是線上 90% bug 的源頭。輸入框忘了限制最大長度 → 後端炸；金額忘了處理零 → 顯示 NaN；
  幣別忘了處理 Unicode → JSON 解析失敗。每個 input field 都至少要列 5 個邊界值，**不列出來就是沒測**。
- **好答案長什麼樣**：「P0-1 預算欄位：空（拒絕）、0（拒絕，顯示『至少 NT$1,000』）、負數（拒絕）、999999999（拒絕，超過 NT$10,000,000 提示『請輸入合理金額』）、含千分位逗號（接受並解析）、含全形數字（接受並轉半形）、emoji（拒絕）。」
- **壞答案長什麼樣**：「正常數字都會處理」「使用者不會輸入怪東西」——這是線上 P0 事故的標準前奏。
- **別人會 push back 什麼**：Dev 會說「框架自動處理」。回應：「**示範一次**給我看，輸入 emoji 結果是什麼？框架預設可能是『接受並存進 DB』，不是『拒絕』。」

## Q2. 「**空狀態怎麼處理？第一次進站、沒資料、被刪光、API 回空陣列？**」

- **為什麼問這個**：空狀態是 UX 死角。Dev 寫的時候有測試資料，看不到空狀態；QA 不問，上線後使用者第一次打開看到白螢幕，就再也不回來。空狀態必須有**明確設計**：是 onboarding？是引導 CTA？是降級提示？
- **好答案長什麼樣**：「P0-6『我的行程』空狀態：顯示插圖 + 文案『還沒儲存任何行程，去規劃一趟吧！』 + CTA 按鈕回到 P0-1 規劃輸入。第一次進站 / 全部刪光 / localStorage 被清 都走同一個空狀態。」
- **壞答案長什麼樣**：「空的就什麼都不顯示」——使用者以為 App 壞掉。
- **別人會 push back 什麼**：UX 會說「這是 06-spec 才畫」。回應：「**畫**是 06-spec 的事，**有 / 沒有**這個狀態是這場 AC 要定。沒定，spec 階段大家會忘掉這條。」

## Q3. 「**網路斷掉、後端 5xx、API timeout 的時候，畫面怎麼反應？**」

- **為什麼問這個**：MVP 階段最容易跳過的就是 error handling。網路斷的時候顯示 spinner 轉到死、後端 500 顯示「Network Error」這種開發者訊息——使用者直接跳離。每一條打 API 的 P0 都要明示：(a) 多久算 timeout (b) 失敗時 UI 是什麼 (c) 重試還是放棄 (d) 訊息文案怎麼寫。
- **好答案長什麼樣**：「P0-8 即時匯率 API：10 秒 timeout；失敗時 fallback 顯示『⚠️ 模擬資料（即時匯率取得失敗）』+ 繼續顯示燈號（用模擬值）+ 背景靜默重試 3 次（指數退避）；連 5 分鐘失敗則整個燈號區塊改顯示『匯率暫時不可用』。」
- **壞答案長什麼樣**：「失敗就跳錯誤訊息」——什麼錯誤訊息？什麼顏色？使用者能不能繼續用 App？
- **別人會 push back 什麼**：Dev 會說「fallback 邏輯要寫很多」。回應：「不寫 fallback，上線第一天就會炸給使用者看。P0-8 從 03-PRD 開始就是高 T-RISK，這場必須鎖。」

## Q4. 「**併發場景：使用者按兩次、同時開兩個分頁、儲存到一半關掉 — 系統怎麼反應？**」

- **為什麼問這個**：使用者**會**按兩次按鈕、**會**同時開兩個分頁編輯、**會**在儲存到一半關掉瀏覽器。
  這些併發場景沒寫 AC，產生的 bug 最難 debug——重現困難、日誌看不出、客訴只能說「我不知道為什麼這樣」。
- **好答案長什麼樣**：「P0-1 按生成：按下後按鈕 disabled 直到回應；網路慢的時候不會送出第二次請求；同時開兩個分頁規劃：彼此獨立、各自存到 localStorage（用 timestamp 區分）；儲存到一半關掉：localStorage 是同步寫，下次進站可見最後一次完整的儲存（部分寫入不可能發生）。」
- **壞答案長什麼樣**：「使用者不會按兩次」——使用者**會**，而且每次客訴都會說「我只按了一次」。
- **別人會 push back 什麼**：PO 會說「這太細了」。回應：「不細。雙擊重複扣款是電商業的 P0 事故 top 3。我們做的是行程不是付款，但同樣邏輯——按兩次生成 = 兩份結果在使用者面前，他選哪個？」

## Q5. 「**資料汙染 / 髒資料：localStorage 被人改、JSON parse 失敗、版本升級欄位缺少 — 怎麼處理？**」

- **為什麼問這個**：使用者**真的**會用 DevTools 改 localStorage（特別是工程師 persona）；
  App 升級後**真的**會發現舊資料缺新欄位；JSON.parse **真的**會在某些 edge case 拋例外。
  這些場景不在 AC 寫清楚，就會 white screen of death——整個 App 掛在啟動畫面，使用者只能清快取。
- **好答案長什麼樣**：「P0-6 載入儲存的行程：JSON.parse 包 try/catch；解析失敗 → 該筆視為損毀、顯示『此行程資料異常，已自動跳過』、不阻擋其他行程載入；欄位缺少（舊版本） → 用 default 值補上；version 不相容 → 顯示『請升級至最新版』+ 保留原始 JSON 供使用者匯出。」
- **壞答案長什麼樣**：「localStorage 我們存什麼讀什麼，使用者不會去動」——說這話的 Dev 一年內會被一個 client-side bug 教做人。
- **別人會 push back 什麼**：Dev 會說「localStorage 不會壞」。回應：「**請示範一次**：手動在 console 改 `localStorage.setItem('trips', '{not valid json')`，重整。App 還能用嗎？」

## Q6. 「**這條 AC 怎樣算過、怎樣算沒過？誰判定？什麼工具量？**」

- **為什麼問這個**：AC 不是寫給人看的詩，是寫給機器（unit test）跟人（QA / PO）判定用的契約。
  「使用者覺得順暢」沒辦法判定；「3 秒內顯示結果」可以量（用 Lighthouse / Performance API）。
  每條 AC 都要明示：(a) 過的條件 (b) 沒過的條件 (c) 量測工具 (d) 誰判定。
- **好答案長什麼樣**：「P0-4 建議換匯額準確度——過的條件：cash_only 總和 × 1.1，依幣別 ceil 到最小單位；
  沒過的條件：與公式偏差 > 1 元；量測工具：unit test（11-unit-test 卡會寫）；
  人為判定：QA 用 5 組已知輸入跑回歸，PO sign-off。」
- **壞答案長什麼樣**：「使用者看了覺得 OK」「沒 bug 就過」——這不是 AC，這是請神拜佛。
- **別人會 push back 什麼**：PO 會說「太嚴格了」。回應：「不嚴格 = 不可驗收 = QA 隨便測 = 上線炸。寬鬆放在『won't fix 清單』裡明示，不是把 AC 寫鬆。」

## 送命題清單

這 3 題不問，3 週後線上炸給使用者看時會回來找你算帳：

1. **「失敗的時候，使用者**還能繼續用 App 嗎**？還是整個卡住？」**
   降級（graceful degradation）比完美錯誤訊息重要十倍。匯率 API 死了，使用者還能不能至少看到行程？不能 = 整個 App 變廢墟。

2. **「這條 P0 user story 我們**故意不處理哪些場景**？寫進 won't fix 了嗎？」**
   不寫，三週後團隊吵架「這個應該處理吧」「不是說好不處理嗎」。won't fix 清單是 AC 的負空間，跟 AC 本身一樣重要。

3. **「11-unit-test 拿到這份 AC，能直接寫出測試嗎？還是還要再開一次會澄清？」**
   AC 是寫給 11-unit-test 的契約，**不夠精** = unit test 工程師會繞回來再問，AC 場次就白開了。每條 G/W/T 寫完，QA 自己**唸一遍假裝是 Dev**——唸不通就重寫。
