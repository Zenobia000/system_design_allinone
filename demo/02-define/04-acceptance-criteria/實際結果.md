## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 AC 不能用「順、好用、合理」這種主觀字眼？

AC 的最終消費者是**自動化測試碼**。
你寫「使用者覺得很順」，QA 沒法把這句話翻成 Jest / Playwright assertion。
本卡 AC-008 寫「p95 < 3 秒 + 量測點 + 量測工具」——QA 可以直接寫 `expect(perfDuration).toBeLessThan(3000)`。
這就是 AC 與 user story 的分工：user story 可以感性，AC 必須機械。

### 2. Edge case 為什麼只覆蓋 4 類（categories_covered）而非全部 6 類？

`decision_log` 第 2 條寫得很清楚：**MVP 不適用 concurrency / perm_denied**。
強行補不適用的 edge 會誤導 Dev 過度設計（為 MVP 寫 distributed lock 是浪費）。
但**必須在 out_of_scope 寫清楚**，且註明 V1 加帳號時要補——
這樣 V1 的 PM/QA 知道這裡有個刻意留的洞要回來補。

### 3. 為什麼 AC-005（happy path）標 `mockable: false`？

`mockable: true` = 用 fixture/stub 就能驗證；
`mockable: false` = 必須對真實系統跑（contract test / perf test / real device a11y）。
AC-005 是即時匯率 API 的 happy path——用 mock 跑只能驗證**前端解析邏輯**，
無法驗證 API 真的有 SLA、回傳格式真的對得起來。
這就是為什麼 contract test 不能省，否則 PRD risks 第 1 條（即時匯率 API 額度/成本/可用性）會變成生產事故。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `criteria[].given/when/then` | Dev 寫單元/整合測試 + QA 寫 e2e |
| `error_handling` | 後端錯誤碼總表 + i18n 文案表 |
| `performance_thresholds` | [`05-adr/`](../../03-design/05-adr/) ADR-002（即時匯率資料源選型 SLA 目標） |
| `security_constraints` | 後端 middleware（input validation / XSS escape） |
| `audit_log_fields` | 分析平台 schema + 隱私聲明文案 |
| `self_review.lowest_confidence` | 觸發 [`05-adr/`](../../03-design/05-adr/) 額外決策（閾值定義） |

### 5. 與 03-PRD 的銜接：1 個 FR → ≥ 3 個 AC

PRD 一條 FR 只能寫 1–2 句 high-level acceptance（PM 視角），
本卡負責**每條 P0 FR 展開 ≥ 1 happy + ≥ 1 error + ≥ 1 NFR 對應 AC**。
本卡 FR-004（即時匯率）展開為 AC-005（happy）+ AC-006（fallback）+ AC-007（異常資料）—— 3 條覆蓋了 PRD risks 中即時匯率 API 的 3 個失敗模式。

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| AC 寫「使用者應該覺得燈號清楚」 | 規則 2 | 改成具體：「燈號 contrast ratio ≥ 4.5:1 + 文字含 STRONG_BUY/BUY/HOLD」 |
| 只寫 happy path，沒寫 error_path 或 edge_case | 規則 3 + 思考步驟 5 | 每條 P0 至少 1 happy + 1 error + 1 NFR |
| `error_handling` 寫「顯示錯誤訊息」沒寫 error_code / log_level / retry | 規則 4 | 4 欄都要寫，retry 必須是 enum 不能寫「再試」 |
| NFR 只寫 latency，省略 a11y / security / audit | 規則 5 | 4 象限都要對應到 AC（本卡 AC-008/009/010/011） |
| `out_of_scope` 寫「不測試這條 FR」 | 規則 7（誤用） | out_of_scope 是「不涵蓋的測試類型」（壓測、滲透、跨 story），不是「不做的功能」 |
| Edge case 編造不會發生的情境湊數 | 規則 3 + 自審 1 | 每個 edge 都要對應到 PRD risks 或 NFR 的真實風險 |

## 交件 checklist

- [ ] 每條 AC 都有 Given / When / Then 三段，且無主觀字眼
- [ ] Happy path ≥ 2、Edge case ≥ 3、NFR 4 象限都有對應 AC
- [ ] `error_handling` 每條都有 error_code + user_message + log_level + retry_policy
- [ ] `performance_thresholds` 含 p50 + p95 + 量測點（不只是數字）
- [ ] `security_constraints` 含 input_validation + data_classification + audit_log_fields
- [ ] 不適用的 edge 類型（如 concurrency）寫進 `decision_log` 且註明何時要補
- [ ] `self_review.lowest_confidence` 對應到每個推論的閾值/策略（會流到 ADR）
