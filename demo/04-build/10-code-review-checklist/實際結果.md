## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 SmartTrip FX 的 review checklist 跟「典型後端」很不一樣？

學生常複製貼上「SQL injection / N+1 query / connection pool」等後端 checklist，但本案是 PWA + localStorage + 邊緣函式。**真正的風險點是另一組**：

| 後端 checklist 常見項 | SmartTrip 對應風險 |
|---|---|
| SQL injection | XSS via localStorage（CR-010） |
| N+1 query | localStorage prefix scan 效能 + bundle size LCP（CR-007） |
| Transaction isolation | localStorage 寫入非原子 → schema migration 邊界（CR-002, CR-013） |
| API rate limit | FX provider free tier 額度 + cache 命中率（CR-008） |

Checklist 必須**從 PRD / NFR 反推風險**，不是抄業界範本。

### 2. 為什麼 CR-016（a11y 色盲）是 must_block 而 CR-017（aria-live）是 should_fix？

`decision_log` 第一條解釋了：FX 燈號（STRONG_BUY / BUY / HOLD）是**核心決策資訊**，色盲（約 8% 男性）若無法判讀 = 違反 PRD G1「人人能 3 分鐘完成」的隱含承諾。

`aria-live` 重要但屬於「狀態通知」非「核心決策」，且 PR 內可快速補。**must_block 不是越多越好** — 太多 must_block 會把 review 變成 gatekeeping 戰場，作者開始學會「繞過」流程。

### 3. 為什麼 `nit_cap` 寫死「單一 PR ≤ 5 條」？

reviewer 心理：看到 30 條 nit 會直接累，連 must_block 都沒精力認真看。

**rule of thumb**：超過 5 條 nit → reviewer 應該開 cleanup PR 一次處理，或乾脆放棄這批 nit。否則 review 變吵架，PR 卡死。

這是把「review 文化」寫進 checklist 的範例 — 流程設計也是工程紀律的一部分。

### 4. 這張卡的輸出流向哪些下游

| 本卡欄位 | 流向哪 |
|---|---|
| `checklist_items` | 真實 PR review 模板（GitHub PR template 引用） |
| `escalation_path` | 團隊協作 SOP |
| `slo_for_review_turnaround` | Dev Lead 追品質 / 速度趨勢 |
| `decision_log` 哪些 lint 已涵蓋 | ESLint / commitlint 設定 |
| 整份 checklist | 給 Claude 跑 PR first-pass 的輸入（真實使用情境） |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 複製業界後端 checklist（SQL injection / N+1）但本案無 SQL | 規則 4 dimension 必須對應實際技術 | 從 PRD / NFR / data model 反推風險點，刪不適用項目 |
| 所有項目都標 must_block | severity 平衡 | must_block 限縮為「不可逆 / 法規 / P0 驗收」三類；其餘 should_fix |
| 沒寫 `when_not_applies` | 規則 6 false positive 浪費時間 | 每個 item 寫清楚什麼 PR 跳過（純文件、純樣式等） |
| 重複 lint / commitlint 已做的事 | 規則 5 + out_of_scope 第一條 | 把這些移到 out_of_scope，checklist 只放人類判斷項目 |
| `confidence` 全 H 無 `self_review` | 規則 6 | 至少 1-2 個 M/L 並對應補洞計畫；team SOP 沒明確的地方誠實標 |

## 交件 checklist

- [ ] 7 dimension（correctness / readability / perf / security / test / observability / a11y）全部 covered
- [ ] 每個 item 寫齊：question + rationale + when_applies + when_not_applies + default_severity + source
- [ ] must_block 項目 ≤ 1/3 總項數（避免 gatekeeping）
- [ ] `escalation_path` 寫明異議 + security 兩條路徑
- [ ] `nit_cap` 寫死（避免 nit 滿天飛）
- [ ] `out_of_scope` 至少 3 條（lint / architecture / commit message）
- [ ] 每個 `confidence: M/L` 對應 `self_review.lowest_confidence` 一條補洞計畫
- [ ] 整份不超過 20 個 item（再多 reviewer 不會看完）
