### 04-build > 10 Code Review Checklist · 關鍵提問（Dev 必問）

> 本場會議 45 分鐘，Dev 只要把這 6 題問完、問對，會議就成功了。
> 不要問「大家覺得 review 標準怎樣？」——問題要**逼出 must / should / nit 的分檔判決**，不是收集意見。

---

## Q1.「**這條規則是『不過不准 merge』，還是『建議改但可商量』，還是『品味偏好』？**」

- **為什麼問這個**：checklist 的價值在分檔。混在一起的 checklist 等於沒有 checklist——
  reviewer 會自由心證、PR 作者會選擇性遵守。must / should / nit 三檔的差別是 **block / discuss / mention**，
  必須對每條明確標示。
- **好答案長什麼樣**：「`[MUST]` FX API 呼叫沒有 timeout + retry 上限不准 merge。原因：09-NFR §3 規定外部 API p95 < 180s，沒 timeout 會卡死整個 generate flow。anti-pattern：`fetch(fxUrl)` 沒任何 timeout/AbortController。」
- **壞答案長什麼樣**：「FX API 應該要有 timeout 比較好。」——「應該」「比較好」是沒分檔。
- **別人會 push back 什麼**：Architect 可能說「全標 MUST 就好了，反正都是好習慣」。回應：「全 MUST = 全不 MUST。reviewer 會選擇性執行，最後變成隨機標準。**必須有取捨**，這條到底會不會擋掉 production 事故？會 → MUST，不會 → SHOULD。」

---

## Q2.「**這條 lint / formatter / type checker 查不查得到？查得到就拿掉。**」

- **為什麼問這個**：checklist 不是給機器查的事項。命名規範、縮排、import 順序、unused variable
  全部交給 ESLint / Prettier / tsc / mypy。寫進 checklist 等於浪費 reviewer 注意力，
  也等於讓真正需要人腦判斷的條目被淹沒。
- **好答案長什麼樣**：「`unused import`、`var-vs-const`、`no-explicit-any` 全交給 ESLint + tsc strict mode；checklist 只留『型別斷言 `as any` 必須附 comment 說明原因』這種需要人判斷的。」
- **壞答案長什麼樣**：「checklist 寫『變數命名要清楚』」——機器查不到，但也太抽象，reviewer 沒辦法用。
- **別人會 push back 什麼**：QA 可能說「但我們專案還沒設好 ESLint」。回應：「**那就先去設 ESLint**，不是把這些事塞進 checklist。設定一次 vs 每個 PR 人工查 50 次，哪個划算？」

---

## Q3.「**這條的 anti-pattern 範例是什麼？寫不出來就刪掉。**」

- **為什麼問這個**：抽象的 checklist 條目（「程式碼要乾淨」「邏輯要清楚」）等於沒寫——
  reviewer 跟 PR 作者對「乾淨」的定義可能完全不同。**每條 MUST 必須附 anti-pattern 範例**，
  reviewer 看到該範例可以直接指認「就是這個」。
- **好答案長什麼樣**：「`[MUST] log 不准包含 Expense.amount / category`，anti-pattern：`console.log('user added expense:', expense)` —— `expense` 是整包物件，會帶 amount。正確：`console.log('expense added, id:', expense.id)`。」
- **壞答案長什麼樣**：「`[MUST] log 不准寫敏感資料`」——什麼算敏感？沒範例沒辦法 review。
- **別人會 push back 什麼**：Dev 可能說「reviewer 都資深，看得懂啦」。回應：「資深的 reviewer 也會有偏好分歧。**寫進範例不是給資深看，是給三個月後新人 onboard 看的**——他第一次 review PR 時，不該還要去問『什麼算敏感資料』。」

---

## Q4.「**這條跟 05-ADR / 08-data-model / 09-NFR 的哪一段對齊？沒對齊就拿掉。**」

- **為什麼問這個**：checklist 是上游決策的執行層。每條 MUST 都要能回溯到一份「為什麼這條重要」的上游文件。
  沒有上游依據的 checklist 條目就是個人偏好——個人偏好應該是 NIT，不是 MUST。
- **好答案長什麼樣**：「`[MUST] localStorage 寫入失敗必須降級不能 throw`，依據：05-ADR-001 結論『MVP 用 localStorage、無雲端備份』。throw 會讓使用者整個行程消失，違反 ADR 的 consequence「資料生命週期 = 裝置生命週期」。」
- **壞答案長什麼樣**：「`[MUST] 函數要小一點`」——回溯不到任何 ADR / NFR，是個人偏好。
- **別人會 push back 什麼**：Architect 可能說「checklist 寫太死會綁手綁腳」。回應：「**綁的是『跟上游決策對齊』，不是綁實作方式**。實作怎麼寫沒寫死，但不能破壞 ADR 的前提。這跟『憲法』vs『法律』的差別一樣。」

---

## Q5.「**這條 review 時需要 30 秒 vs 30 分鐘？太久就不該是 MUST。**」

- **為什麼問這個**：MUST 條目必須能在 PR review 流程中快速判讀。如果某條 MUST 需要 reviewer 跑起整個 App、開 DevTools、模擬 3 種網路狀況才能查——那它不該是 MUST，應該是 QA 流程或 e2e 測試。
  Review 是 code-level 的快速閘門，不是品質保證的全部。
- **好答案長什麼樣**：「`[MUST] FX API 呼叫必有 timeout`——30 秒：grep `fetch(.*fx` 看有沒有 `AbortController` 或 `signal`。可機械判讀。」
- **壞答案長什麼樣**：「`[MUST] FX API 失敗時使用者體驗要 graceful`——這要跑 App 模擬，30 分鐘起跳，不該是 MUST。改成 SHOULD + 補 e2e test 場景。」
- **別人會 push back 什麼**：QA 可能說「但 UX 也很重要」。回應：「**UX 也重要 → 寫進 e2e test，不是塞進 PR checklist**。PR checklist 是 reviewer 30 秒能判讀的事；UX 是 QA 場景測試的事。職責分清楚。」

---

## Q6.「**這條會擋住合理的工作嗎？會就要寫例外條件。**」

- **為什麼問這個**：絕對化的 MUST 會把合理的特殊情境也擋掉。譬如「`[MUST] 禁止使用 any`」會擋掉跟 third-party library 互動時無可避免的型別斷言。要嘛改成「禁止使用 any **除非附 comment 說明為什麼**」，要嘛降階為 SHOULD。
- **好答案長什麼樣**：「`[MUST] PR 不准引入 > 50KB 的新 dependency`，**例外**：經 Architect 簽核且寫進 ADR 的可放行（譬如即時匯率 SDK）。」
- **壞答案長什麼樣**：「`[MUST] 禁止新增 npm dependency`」——沒例外條件，連 axios 都不准加。
- **別人會 push back 什麼**：Dev 可能說「例外條件寫多了等於沒規則」。回應：「**例外條件 ≠ 任意例外**。例外要寫『誰簽核、寫進哪』。沒簽核流程的例外才是漏洞。」

## 送命題清單

這 3 題不問，sprint 跑兩週後 review 流程會崩潰：

1. **「敏感資料的範圍誰定義？」**
   PII / 金額 / 第三方 API key 三類各自的定義要在 checklist 寫死。沒寫，每個 reviewer 對「敏感」有自己一套，
   結果 PR 作者賭運氣——「這次的 reviewer 可能不查 log」就把 amount 寫進去了。後果是上線後 incident report
   發現 user expense 全在 server log 裡。

2. **「這份 checklist 多久 review 一次？」**
   Checklist 不是聖經，是工作工具。MVP 4 週驗證窗結束後要回頭看「哪幾條從沒擋下任何 PR？」（=過嚴）、
   「哪幾條我們事後發現該擋但沒擋？」（=遺漏）。沒設 review 週期，半年後 checklist 跟現實脫節變廢紙。

3. **「PR 作者自審清單跟 reviewer 清單一樣嗎？」**
   兩份清單應該一樣——PR 作者送出前自己走一遍，reviewer 用同一份對。如果作者跟 reviewer 看不同清單，
   會出現「作者覺得我都查過了」vs「reviewer 覺得這條你怎麼沒查」的拉扯。同一份 checklist，
   兩端都要簽。
