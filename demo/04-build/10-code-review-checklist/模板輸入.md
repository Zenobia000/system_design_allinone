# 10-CODE-REVIEW-CHECKLIST · 模板輸入

> **這個檔案怎麼讀**：
>
> 1. 先看 **本卡注意事項** — 進 Claude 前要記在腦袋裡的 5 條
> 2. 再看 **上游文件對照** — 學會 trigger 的「上游文件」貼位區要塞什麼
> 3. 然後跟著 **完整 prompt** 的 3 步驟組裝、貼到 Claude（等 30 秒）
> 4. 拿到結果後對照 [`實際結果.md`](./實際結果.md)
> 5. 最後看 **接棒下游** — 知道這份輸出要餵給後面哪幾張卡

> **小提醒**：這張卡的輸出不是「對某個 PR 的具體 finding 清單」，而是「**團隊共用的 review checklist 模板**」。
> 真實使用時，丟一份具體 git diff，AI 才能跑 first-pass 列 finding；本卡先把 checklist 框架建好。

## ⚠️ 本卡注意事項（進 Claude 前先讀）

- **不要抄業界後端 checklist**（SQL injection / N+1 query / connection pool）。本案是 PWA + localStorage + 邊緣函式，真正的風險是 XSS via localStorage、schema migration、bundle size、FX provider 額度。必須**從上游 PRD/NFR 反推風險**。
- **must_block 限縮為「不可逆 / 法規 / P0 驗收 / 資料損毀 / 重大 a11y」五類**。must_block 太多 → review 變 gatekeeping 戰場 → 作者學會繞過流程。建議 must_block ≤ 1/3 總項數。
- **每個 item 必須寫 `when_not_applies`**。沒寫的話 reviewer 會把純文件 PR 也套上「需要 e2e test」造成 false positive。
- **§Must Block vs Nit 必須寫死 `nit_cap`**（建議單一 PR ≤ 5 條 nit）。沒上限 → nit 滿天飛 → 蓋掉 must_block 訊號。
- **lint / commitlint 已涵蓋的項目要丟到 §Out of Scope**。重複勞動 = noise，違反規則 5。

## 替換成自己專案的方法

如果你不是要做 SmartTrip FX：

1. 跑 [`/start/`](http://localhost:3000/start/) 問卷 → 下載你自己的 `project-brief.md`，並跑完上游卡（[`03-prd`](../../02-define/03-prd/模板輸入.md) / [`07-api-spec`](../../03-design/07-api-spec/模板輸入.md) / [`08-data-model`](../../03-design/08-data-model/模板輸入.md) / [`09-non-functional-reqs`](../../03-design/09-non-functional-reqs/模板輸入.md)）拿到上游輸出
2. 步驟 1（複製站上「完整範本」tab）**完全不動**
3. 步驟 2 的 trigger 結構不動；**只替換 `⏫` 上方的「上游文件」貼位區**（把 git diff / coding standard / 既有 checklist / 上游 PRD / 上游 API / 上游 Data Model / 上游 NFR 7 個小節換成你自己的對應內容）
4. 貼到 Claude → 對比你拿到的結果與 [`實際結果.md`](./實際結果.md)
5. **真實 review 時**：把這份 checklist + 具體 PR diff 一起丟給 Claude，請 AI 跑 first-pass

> **為什麼步驟 1 不動？** 因為站上模板就是 single source of truth。版本升級（規則修訂、章節增刪）會自動同步到所有學生的下次產出，不需要去改舊的 demo 檔。
