# 10 Code Review Checklist · 角色場景

## 這場會議在做什麼

ADR / data-model / NFR 都凍結了，第一個 sprint 的 PR 即將進入 review 流程。
本場會議**不是寫 code 的會議、不是教 git 的會議、不是討論工具選型的會議**。
目的只有一個：訂出 **本專案 PR review 必查 8–12 條 checklist**，
明確區分 **must（不過不准 merge）／ should（提出但可商量）／ nit（建議）**，
並對每條給出**原因**與 **anti-pattern 範例**。

跑完本場，下一個進來的 PR 就有對齊的 review 標準，
不再出現「A 審你過、B 審你不過」的雙標慘案。

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Dev（主責，你）** | sprint 1 即將提的 PR 草稿、過去專案踩過的雷、08-data-model 的 PII 標註 | 8–12 條 PR checklist + anti-pattern 範例 |
| **Architect** | 05-ADR 的決策邊界（譬如「資料只活在 localStorage」「FX API 限流」） | 確認 review 標準不會把 ADR 鎖死的決策放掉 |
| **QA** | 09-NFR 的性能預算、安全紅線、可測性要求 | 確認 review 環節能擋下「之後測到才發現」的問題 |

## 你扮演的角色（Dev）

你是「**未來在 review 別人 PR 的人**」。本場會議你要做三件事：

1. 對每條候選 checklist 問自己「**這條是 deal-breaker、商量空間、還是品味偏好？**」——三檔，不准混
2. 對每條 must 寫**具體**的 anti-pattern 範例（不准寫「程式碼品質」「可讀性」這種抽象話）
3. 跟 lint / formatter / type checker 重複的條目**直接拿掉**——機器查得到的不寫進 checklist

**禁忌動作**：本場會議**禁止**講這幾種話，講了就要重來：

- ❌「**這條最好要⋯⋯**」「**應該⋯⋯**」「**盡量⋯⋯**」——沒有強度的字。must / should / nit 三選一
- ❌「**寫 docstring**」「**變數命名清楚**」「**縮排對齊**」——這些 lint / formatter 已經查
- ❌「**架構要好**」「**設計要乾淨**」——抽象到無法 review。要寫成「禁止 X 模式」這種可機械判讀的話
- ❌**把 nit 跟 deal-breaker 混在一起**——這叫「review wishlist」不叫 checklist

## 會議結束時，桌上要有什麼

- **8–12 條 checklist 條目**，每條含：
  - 分類標籤：`[MUST]` / `[SHOULD]` / `[NIT]`
  - 一行說明（祈使句、< 50 字）
  - **原因**（為什麼這條在本專案重要——必須引用 ADR / data-model / NFR 段落）
  - **anti-pattern 範例**（具體 code snippet 或情境）
- **lint 已覆蓋清單**：哪些事項已經自動化、本 checklist 不再列入
- **review SLA**：MUST 違反 → 不准 merge；SHOULD 違反 → 留 comment + 等回覆；NIT → 留 comment 但不 block
- 給 11-unit-test 的「**測試覆蓋率掛勾點**」（譬如 `[MUST] core logic 沒有對應 unit test 不准 merge`）

## 為什麼這場會議重要

PR review 是 **build 階段的最後一道閘門**。沒有對齊的 checklist，會出現三種慘案：

1. **雙標**：A 嚴 B 鬆，PR 作者開始挑審查者 → 團隊信任崩盤
2. **review fatigue**：每個 PR 留 30 條 nit comment → 真正的 deal-breaker 被淹沒
3. **lint 重複勞動**：人工查機器查得到的事 → 浪費 review 時間，真 bug 漏看

下游每張卡都依賴這份 checklist：

- **11-unit-test**：「core logic 必有測試」是 MUST 條目 → 直接成為下一場會議的入場券
- **12-release-plan**：rollout 前的 PR audit 標準就是這份 checklist
- **14-monitoring-runbook**：log 不准寫 PII 是 MUST → runbook 的 alert 規則跟著走
- **15-postmortem**：事故發生時回頭看「PR 有沒有違反這份 checklist」——是 review 漏看還是 checklist 沒寫

**跳過這場會議的代價**：sprint 跑兩週後團隊吵 review 標準，每個 PR 都要重開一場 meta 會議決定要不要 merge，
sprint velocity 直接砍半。Checklist 不是文件工作，是**審查共識的固化**。

## 本場示範主題

**SmartTrip FX MVP 第一份 PR Review Checklist**

- **為什麼選這題示範**：種子簡報明示「4 週 MVP 驗證窗」，build 階段只有 ~3 週開發時間，
  PR review 不能變成瓶頸。本場要把「快速但不犧牲關鍵防線」的 checklist 訂出來。
- **教學意義**：學員會學到「checklist 不是越長越好——8–12 條剛好，每條都能在 review 時 30 秒判讀」。
  PII 不准寫 log、FX API 必有 timeout、bundle size 不准超預算——這幾條是 SmartTrip 的命脈，
  其他可以靠 lint / formatter 自動化的就交給機器。
