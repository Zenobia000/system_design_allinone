### Vitest 範例程式碼（TC-001 + TC-005）

```typescript
// src/lib/fx/cash-suggestion.test.ts
import { describe, it, expect } from 'vitest';
import { suggestCashAmount } from './cash-suggestion';

describe('suggestCashAmount', () => {
  // TC-001: happy path — JPY cash_only 加總 × 1.1
  it('sums cash_only JPY items and applies 10% buffer', () => {
    // Arrange
    const items = [
      { id: 'a', title: 'Ramen',  estimatedCost: 1200, currency: 'JPY' as const, paymentType: 'cash_only' as const },
      { id: 'b', title: 'Subway', estimatedCost: 800,  currency: 'JPY' as const, paymentType: 'cash_only' as const },
    ];

    // Act
    const result = suggestCashAmount(items, 'JPY', 0.21);

    // Assert
    expect(result).toEqual({
      currency: 'JPY',
      amount: 2200,
      twdApprox: 462,
      breakdown: { cashOnlySum: 2000, bufferRate: 0.1 },
    });
  });

  // TC-005: 過濾 cash_only — card_ok 與 either 不算入
  it('excludes card_ok and either items from cash suggestion', () => {
    const items = [
      { id: 'a', title: 'Ramen',    estimatedCost: 1200, currency: 'JPY' as const, paymentType: 'cash_only' as const },
      { id: 'b', title: 'Dept',     estimatedCost: 5000, currency: 'JPY' as const, paymentType: 'card_ok'   as const },
      { id: 'c', title: 'Takoyaki', estimatedCost: 600,  currency: 'JPY' as const, paymentType: 'either'    as const },
    ];

    const result = suggestCashAmount(items, 'JPY', 0.21);

    // 只算 cash_only 的 1200，乘 1.1 = 1320 → JPY 向上進位至 100 倍數 = 1400
    expect(result.amount).toBe(1400);
    expect(result.breakdown.cashOnlySum).toBe(1200);
  });

  // TC-007: 空行程不該丟例外
  it('returns zero for empty itinerary without throwing', () => {
    expect(() => suggestCashAmount([], 'JPY', 0.21)).not.toThrow();
    expect(suggestCashAmount([], 'JPY', 0.21).amount).toBe(0);
  });

  // TC-010: idempotent — 同 input 多次呼叫結果一致
  it('is idempotent — same input yields deep-equal output', () => {
    const items = [
      { id: 'a', title: 'Ramen', estimatedCost: 1200, currency: 'JPY' as const, paymentType: 'cash_only' as const },
    ];
    const first = suggestCashAmount(items, 'JPY', 0.21);
    for (let i = 0; i < 99; i++) {
      expect(suggestCashAmount(items, 'JPY', 0.21)).toEqual(first);
    }
  });
});
```

## 教學要點（看完 AI 輸出後讀這段）

### 1. F.I.R.S.T 原則對應到這份 test plan

| 原則 | 在這份 plan 怎麼體現 |
|---|---|
| **F**ast | `mocking_strategy.mock: []` — 純函式不需 mock，CI 跑完 10 個 case < 100ms |
| **I**ndependent | 每個 `test_cases[].input` 自帶完整輸入，case 之間不共享 fixture |
| **R**epeatable | TC-010 明確驗證 idempotency；`do_not_mock` 不包含 `Date.now/Math.random` |
| **S**elf-validating | `expected_output` 用具體值（2200、12400），不用「應該大於某數」這種模糊斷言 |
| **T**imely | 寫在 P0-4 實作的同一個 PR，不是上線後補（coverage 0% 就是上線前要解的 ❌） |

### 2. 為什麼 TC-009（負數）standardly confidence L？

spec 完全沒寫負數行為，但我們不能：
- ❌ 不測（會在 production 爆）
- ❌ 編一個錯誤訊息文案進去（違反規則 3）

正確做法是 **寫測試 + 標 L + 在 `self_review` 寫補洞計畫**。學生若把 confidence 美化成 H，下游 PRD 會以為這條規則已確認，造成資訊污染。

### 3. mutation testing 為何比 line coverage 重要？

考慮這段壞測試：
```typescript
it('calculates suggestion', () => {
  const r = suggestCashAmount(items, 'JPY', 0.21);
  expect(r).toBeDefined();  // ← 跑到了 95% 的 line，但什麼都沒驗證
});
```

`coverage_target.line: 95%` 會通過，但 mutation test（Stryker 把 `× 1.1` 改成 `× 1.0`）會發現這個測試殺不掉 mutant → `mutation_kill` 為 0。
所以 `mutation_kill: 70%` 比 `line: 95%` 更能證明「測試真的在檢查邏輯」。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `coverage_target` | `12-release-plan/` go/no-go criteria 的「test coverage gate」 |
| `mutation_test_score.known_survivors` | `15-postmortem/` 若 P0-4 上線後出現算錯案例，這份是第一手線索 |
| `self_review.lowest_confidence`（負數行為） | 退回 `03-prd/` 補 P0-4 邊界規則 |
| `out_of_scope` 第 2 條（不測 fxRateToTWD 來源） | `14-runbook/` 的「FX API down」處理流程 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| 測試寫成 `expect(result).toBeDefined()` | F.I.R.S.T - Self-validating | 用具體 expected value（`expect(amount).toBe(2200)`） |
| 把 `Math.round` mock 掉，只為「測進位邏輯」 | 規則 7 mocking_strategy | 同 module pure function 不該 mock；改成測 input → output |
| 只測 happy path，沒測空陣列、跨幣別 | 規則 4 涵蓋 6 類 | 至少 happy / boundary / null_empty 三類齊全 |
| 邊界 case 標 confidence H 但 spec 沒寫進位演算法 | 規則 6 | 沒明確 spec 的標 M/L，並寫 TODO(需 spec 確認) |
| `out_of_scope` 寫成空陣列 | 規則 5 | 至少 3 條：不測 UI、不測第三方、不測 integration |
| 測試名稱寫 `it('test 1', ...)` | F.I.R.S.T - Self-validating | 用行為敘述：`it('excludes card_ok items from cash sum', ...)` |
