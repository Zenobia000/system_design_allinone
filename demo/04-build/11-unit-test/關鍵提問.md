### 04-build > 11 Unit Test · 關鍵提問（Dev 必問）

> 本場會議 45 分鐘，Dev 只要把這 6 題問完、問對，會議就成功了。
> 不要問「我們要不要寫測試？」——問題要**逼出 core 與 glue 的分界、mock 邊界、coverage 真正在追什麼**。

---

## Q1.「**哪些函數是『core logic』必測？哪些是 glue / UI 不追 coverage？**」

- **為什麼問這個**：unit test 的價值集中在**會壞且壞了會出事**的程式碼。core logic（算法、業務規則、純函數）
  邏輯密集、變動成本高、bug 影響大——必測。glue code（API 串接、event handler、UI render）邏輯稀疏、
  變動快、bug 多半透過 e2e 或人眼就能抓——不該追 unit test coverage。混在一起追 = 浪費。
- **好答案長什麼樣**：「core logic = `lib/recommend.ts`（換匯建議公式）、`lib/fx-signal.ts`（燈號判定）、`lib/expense-variance.ts`（誤差計算）。這三檔目標 coverage ≥ 90%。UI component 不寫 unit test，靠 Playwright e2e。Glue code（API route handler）目標 0%——只 e2e 測 happy path。」
- **壞答案長什麼樣**：「全部都測，目標 90% coverage。」——這會逼大家寫無價值的 React component test，
  浪費時間且讓 refactor 痛苦。
- **別人會 push back 什麼**：QA 可能說「但 UI bug 也很多」。回應：「**UI bug 用 e2e 抓，不是用 unit test**。
  Enzyme 那種測 `wrapper.find('.button').simulate('click')` 的 test 99% 在測 React 行為不是測產品邏輯，refactor 一次全部要改寫。」

---

## Q2.「**Coverage 目標數字背後追的是什麼？信心還是百分比？**」

- **為什麼問這個**：100% coverage 不等於 100% confidence。可以用 `expect(true).toBe(true)` 把數字衝上去
  也可以對 critical path 寫 1 個 test 涵蓋 80% 行數但完全沒測 edge case。Coverage **是負面指標**——
  低 coverage 表示有漏；高 coverage 不表示有覆蓋對地方。應該追的是「**這個函數壞了我們會立刻知道嗎？**」
- **好答案長什麼樣**：「Core logic 目標 90%——這 10% 是 defensive code（type guard、impossible state），測不測都行。Glue code 不追 coverage，靠 1–2 個 e2e happy path。整體 coverage 數字會落在 50–65%，不重要。」
- **壞答案長什麼樣**：「100% coverage，CI 不過就 fail。」——會逼出 garbage test。
- **別人會 push back 什麼**：管理層可能說「業界都看 coverage」。回應：「業界看 coverage 是因為**沒有更好的可量化指標**。
  我們的可量化指標是『修 bug 必加 regression test』+『core logic 必有對應 AC 場景測試』。這兩條比 coverage 數字有意義 10 倍。」

---

## Q3.「**Mock 邊界畫在哪？什麼永遠 mock、什麼永遠不 mock？**」

- **為什麼問這個**：mock 自己寫的核心邏輯 = 在測 mock。改了 core 邏輯但 test 還是綠的——這種情況是
  unit test 最大的反指標。Mock 邊界要畫在「**自己不擁有的程式碼**」：外部 API、時鐘、隨機數、檔案系統、
  localStorage 這些。**永遠不 mock 自己的純函數**——直接呼叫真實實作。
- **好答案長什麼樣**：「**永遠 mock**：FX API（用 `msw` 攔截）、`Date.now()`（用 `vi.useFakeTimers()`）、`Math.random()`、`localStorage`（jsdom 自帶）。**永遠不 mock**：`lib/recommend`、`lib/fx-signal`、`lib/expense-variance`——這三個是 core 本身。測呼叫它們的 React component 時直接讓真實函數跑，不准 stub。」
- **壞答案長什麼樣**：「全部依賴都 mock 才好測。」——這就是 mock 自己的核心邏輯，最後 test 跟 production 行為脫鉤。
- **別人會 push back 什麼**：Dev 可能說「但 mock 寫起來方便」。回應：「**方便寫的 test 通常是沒在測東西的 test**。
  Mock 本身的維護成本會吃光你省下的時間。」

---

## Q4.「**Property-based 還是 example-based？哪些 case 用哪種？**」

- **為什麼問這個**：example-based test（給定 input X，斷言 output Y）寫起來快但**只測到你想得到的 case**；
  property-based test（給定任意 input 滿足條件 P，斷言不變式 I 永遠成立）能 fuzz 出邊界但寫起來慢。
  關鍵：**數學性質明確的算法用 property-based，業務規則用 example-based**。
- **好答案長什麼樣**：「換匯建議公式有明確不變式（`buffer % ≥ 0`、`recommended_amount ≥ cash_total`、
  `recommended_amount ≤ budget * 1.5`）→ 用 `fast-check` property-based 跑 1000 個隨機 input。
  燈號判定是有限狀態機（3 種輸出）→ example-based 覆蓋 9–12 個關鍵場景就夠。」
- **壞答案長什麼樣**：「全部用 example-based 就好。」——換匯公式的浮點邊界一定漏。
- **別人會 push back 什麼**：QA 可能說「property-based 太花時間學」。回應：「**1 個 property test 抵 100 個 example test**。
  學一次用三年，每改一次公式跑一次 1000 case fuzz——這個投資報酬率沒得比。」

## Q5.「**快照測試（snapshot test）我們用嗎？什麼場景用？**」

- **為什麼問這個**：snapshot test 是 React 圈濫用最嚴重的反 pattern——對 UI 渲染結果做 string diff，
  改任何樣式都會 fail，team 變成「每次 review 都按 `u` 更新 snapshot」的儀式。**snapshot 只該用於
  序列化資料**（譬如 API response shape、deterministic function 的 output dump），**不該用於 UI**。
- **好答案長什麼樣**：「snapshot 只用於 `generate()` 函數的 output JSON dump（驗證 schema 穩定）。React 元件**禁用** snapshot test——UI 行為用 Playwright，UI render 用人眼 + Storybook。」
- **壞答案長什麼樣**：「全部元件都跑 snapshot。」——這是經典反 pattern。
- **別人會 push back 什麼**：Dev 可能說「snapshot 可以快速 detect regression」。回應：「**detect 到的多半是噪音不是 regression**。
  改個 CSS class snapshot fail，沒有人會仔細看 diff，全部按 `u`。三個月後真的 regression 來，也是按 `u`。」

---

## Q6.「**修 bug 必加 regression test 怎麼確保不被跳過？**」

- **為什麼問這個**：bug fix 不加 regression test 是技術債第一名來源。同一個 bug 第二次出現，
  postmortem 才發現第一次沒鎖。**規則化**：PR title 含 `fix(`、`hotfix` 或 PR body 引用 issue
  必有 test 變更——CI 強制，不靠 reviewer 善心。
- **好答案長什麼樣**：「對齊 10-code-review-checklist `[MUST-06]`：path-based test required + 額外加 `bugfix-test-required` CI rule——PR title 開頭是 `fix(` 必有 `*.test.ts` 變更，否則 CI fail。Exception：純文案修正可以加 `[no-test]` label 跳過，但要 reviewer 簽核。」
- **壞答案長什麼樣**：「reviewer 看到沒測就提醒。」——靠人就會漏。
- **別人會 push back 什麼**：Dev 可能說「有些 bug 沒辦法寫 unit test」。回應：「**那就寫 e2e test**。
  完全寫不出測試的 bug fix 99% 是『把症狀掩蓋住』不是修因。寫不出測試本身就是訊號。」

## 送命題清單

這 3 題不問，sprint 跑兩週後 test suite 會崩潰：

1. **「test 跑多久算合理上限？超過怎麼辦？」**
   Unit test 跑 > 30 秒就會被開發者跳過（「等下再跑」→ 永遠不跑）。要訂上限（譬如本地 < 15s、CI < 2 min），
   超過就要 profile 找出慢的 test 拆掉。沒設上限的 test suite 一年後跑 10 分鐘，沒人在本地跑了。

2. **「flaky test 出現我們怎麼處理？」**
   flaky test 比沒測還毒——它教會團隊「綠的 test 也不可信」。SOP 要寫：flaky 出現先 `skip` + 開 ticket
   24h 內查根因。不准視而不見讓它週週紅一次。

3. **「test 跟 production code 同一份 PR review 嗎？」**
   答：是。test 跟對應的 production code **必須同一份 PR**。分開 PR 會出現「先 merge code 之後補 test」
   永遠不會補的情況。對齊 10-code-review-checklist `[MUST-06]`：path-based test required CI rule。
