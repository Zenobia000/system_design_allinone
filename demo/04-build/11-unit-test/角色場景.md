# 11 Unit Test · 角色場景

## 這場會議在做什麼

AC 凍結、API spec 凍結、data model 凍結，sprint 1 的 PR 即將進入 review。
本場會議**不是寫測試的會議、不是 demo testing framework 的會議、不是補 coverage 數字的會議**。
目的只有一個：**訂出本專案 unit test 的「測什麼、不測什麼、mock 在哪、coverage 目標」**。

跑完本場，每個 Dev 寫 PR 時都知道：
- 哪些函數**必測**（沒測 reviewer 會 block）
- 哪些函數**不追求 coverage**（純 glue code、UI rendering）
- mock 邊界畫在哪（mock 外部依賴，不 mock 自己的核心邏輯）
- 修 bug 必加 regression test 是 deal-breaker

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **Dev（主責，你）** | 04-AC 列出的 Given/When/Then、07-api-spec、08-data-model、過去 testing 踩雷經驗 | 必測函數清單 + coverage 目標分檔 + mock 邊界 |
| **QA** | 測試金字塔視角、e2e 場景需求、bug 歷史紀錄 | 確認 unit test + e2e 覆蓋沒有縫隙 |

## 你扮演的角色（Dev）

你是「**core logic 守護者**」。本場會議你要做三件事：

1. 對每個函數問「**這是 core logic 還是 glue code？**」——core 必測，glue 不追 coverage
2. 對每個 mock 問「**這是外部依賴還是自己寫的？**」——mock 外部 OK，mock 自己 = 在測 mock
3. 對 coverage 目標問「**追的是什麼？信心還是數字？**」——100% coverage 是反指標

**禁忌動作**：本場會議**禁止**講這幾種話，講了就要重來：

- ❌「**我們追 100% coverage**」——追的是 confidence，不是百分比。100% coverage 通常意味著大量無價值測試
- ❌「**這函數有寫測試就好**」——測什麼比有沒有寫重要。測 happy path 沒測 edge case = 沒測
- ❌「**Mock 一下這個函數就好**」——如果這個函數是自己的核心邏輯，mock 它 = 你在測 mock 本身
- ❌「**這 bug 改完就好不用加 test**」——修 bug 不加 regression test，三個月後同一個 bug 會再回來

## 會議結束時，桌上要有什麼

- **「core logic 必測清單」**：3–5 個函數 / 模組名，附「為什麼這是 core logic」
- **Coverage 目標分檔**：core ≥ 90% / glue 不要求 / UI 透過 e2e 覆蓋
- **Mock 邊界宣言**：哪些「**永遠 mock**」（外部 API、時鐘、隨機）、哪些「**永遠不 mock**」（核心算法、純函數）
- **6+ test scenario 規格**：每個含函數名 / input / expected / 對應 AC / 為什麼必測
- **修 bug 必加 regression test** 寫進 PR checklist（已對齊 10-code-review-checklist 的 `[MUST-06]`）
- 給 12-release-plan 的「**Go criteria 之一：core logic coverage ≥ 90%**」

## 為什麼這場會議重要

Unit test 是 **build 階段的安全網**。沒有對齊的策略，會出現三種慘案：

1. **追 coverage 不追 confidence**：寫一堆 `expect(true).toBe(true)` 把數字衝上 90%，bug 上線才發現沒測對地方
2. **mock 自己的核心邏輯**：core 函數 mock 掉去測呼叫它的函數 → 改 core 邏輯 test 還是綠 → 邏輯壞了沒人知道
3. **修 bug 不加 regression**：同一個 bug 半年內出現三次 → 客服信箱爆炸 → postmortem 才發現第一次沒加 test

下游每張卡都依賴這份策略：

- **12-release-plan**：Go criteria 直接引用「core coverage ≥ 90%」「regression test 必補」
- **13-rollback-plan**：rollback 後要驗證的測試清單來自本場「必測函數」
- **15-postmortem**：事故發生時回頭看「這個函數有沒有測？沒測為什麼？」

**跳過這場會議的代價**：sprint 跑兩週後 PR 開始充斥兩種極端——有的人 0 行測試硬塞，
有的人對 React component 寫 50 行 enzyme 測試（測 UI 渲染細節）。Code review 變成測試風格大戰，
真正該測的 core logic 反而被忽略。Unit test 不是 nice-to-have，是 **build 階段的契約執行器**。

## 本場示範主題

**SmartTrip FX MVP 第一份 Unit Test 策略**

- **為什麼選這題示範**：種子簡報「實際現金 vs 建議換匯誤差 < 15%」是 PRD G1 的數字承諾，
  這個承諾的可信度來自三個核心算法是否正確：
  1. **換匯建議公式**：input 行程天數 + persona + 預算 → output 建議現金額 + buffer %
  2. **FX 燈號判定**：input 歷史匯率 N 天 → output STRONG_BUY / BUY / HOLD
  3. **開支 vs 建議誤差計算**：input 實際開支 + 建議值 → output 誤差 %
- **教學意義**：學員會學到「core logic 必測 ≠ 全部都測」。SmartTrip 的 UI 元件（卡片、表單、燈號顏色）
  全部透過 e2e 覆蓋，unit test 火力集中在 3 個核心算法。Coverage 目標 core 90% / glue 0% / UI 不追，
  整體 60% 但 confidence 100%。
