## 1. Executive Summary

把 PRD §6 的 P0 需求切成**可估、可做、可驗收**的最小單位。

本文件只切 **Now 段**（PRD 附錄收斂的兩個缺口 P0-8／P0-9，加上與其直接相關的既有功能調整）。已上線的 P0-1～P0-7 不重新切故事——**為已完成的功能補寫故事是浪費**，需要的是回填驗收條件（見 `acceptance-criteria`）。

切分原則：

1. **一個故事 = 一個使用者可感知的結果**。「建 FX API client」不是故事，是任務。
2. **垂直切，不水平切**。不接受「先做後端、下個 sprint 做前端」。
3. **能在一個 sprint 內完成**，否則拆。

## 2. Stories

### Epic A · 讓匯率變成真的（P0-8）

| ID | Story | 為什麼要（連回 canon） |
|---|---|---|
| **US-01** | 作為旅客，我想看到**標示為即時的匯率**，這樣我才敢相信換匯建議 | `user-research` F4 信任門檻；PRD G4 |
| **US-02** | 作為旅客，當即時匯率抓不到時，我想**明確知道現在看的是舊資料**，這樣我不會被誤導 | PRD P0-8 驗收標準「失敗時明確標示」；`north-star` C3 反指標 |
| **US-03** | 作為旅客，我想看到**燈號是根據今日 vs MA30 算的**與偏離百分比，這樣我能自己判斷要不要信 | PRD P0-5 驗收標準；`user-research` F4 |
| **US-04** | 作為 DevOps，我想在單一 FX 來源失效時**切換到備援來源而不需要發版**，這樣事故能在 5 分鐘內收斂 | `runbook` Runbook 01 Mitigation A |

### Epic B · 讓我們看得見（P0-9）

| ID | Story | 為什麼要 |
|---|---|---|
| **US-05** | 作為 PM，我想知道**進站者有多少完成一次生成**，這樣我能判定 KR1 | `okr` KR1；`north-star` L1 |
| **US-06** | 作為 PM，我想知道**生成後有多少人選了方案或存檔**，這樣我能判定採用率 | `north-star` L2 |
| **US-07** | 作為旅客，我想在**不註冊、不被追蹤個資**的前提下使用，這樣我才願意繼續用 | 種子簡報「免登入、重隱私」；PRD §9 隱私 Open Question |
| **US-08** | 作為 PM，我想知道**使用者從進站到看到第一個數字花多久**，這樣我能判定 3 分鐘承諾 | PRD §7 完成時間；`journey-map` MoT-1 |

### Epic C · 讓價值可被證明（KR3 前置）

| ID | Story | 為什麼要 |
|---|---|---|
| **US-09** | 作為旅客，我想在旅程結束時**用一題回答「現金夠不夠」**，這樣我不用記帳也能給回饋 | `journey-map` 缺口 G-a；`user-research` F6（記帳意願低） |
| **US-10** | 作為 PM，我想看到**實際現金 vs 建議換匯的誤差分佈**，這樣我能判定 KR3 | `okr` KR3；`north-star` C1 |

### 明確不切成故事的項目

| 項目 | 為什麼不切 |
|---|---|
| P0-1～P0-7 既有功能 | 已上線。需要的是回填 AC，不是重寫故事 |
| 帳號、雲端同步、分享匯出 | 屬 Next（`roadmap`），驗證窗內不做 |
| 多人分帳、個人化推薦 | PRD §3 明列非目標 |

### 容量對照

| 項目 | 數值 | 來源 |
|---|---|---|
| 團隊 | FE 2 人（`adr` Option A 提及）、DevOps 0.5、PM/PO 1 | canon 推導 `[L]` |
| Sprint 長度 | 2 週 | 假設 `[L]` |
| 歷史 velocity | **無**（無歷史 sprint 資料） | — |
| 假設 velocity | ~16 點／sprint | **純推估** `[L]` |
| **結論** | 29 點 ≈ **2 個 sprint = 4 週** | 與 PRD §10「MVP 收尾 1–2 週」**衝突** |

> **這是本文件最重要的發現**：PRD §10 說 MVP 收尾 1–2 週，但把 P0-8／P0-9 完整做出來（含可驗證 KR3 的 US-09／US-10）需要約 4 週。
>
> **兩個選項**：
> (a) 砍 Epic C（US-09／US-10）→ 收尾 2–3 週，但 **KR3 無法判定**，`okr` 的一票否決條件形同虛設。
> (b) 接受收尾 4 週 → 驗證窗延後，總時程 8 週。
>
> **建議 (b)**，理由：KR3 是唯一能證明「算得準」的指標，砍掉它等於驗證窗跑完也不知道核心價值成不成立。**此決定需 PO 拍板**。
