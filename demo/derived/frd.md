## 1. Executive Summary

PRD 說「顯示建議換匯額」，FRD 要回答的是：**進位到多少？多幣別怎麼算？沒有現金項目時顯示什麼？**

本文件只細化**會產生歧義、且歧義會導致錯誤實作**的功能。已上線且行為明確的部分（如表單必填驗證）不重複展開。

三個最容易被做錯的地方，先寫在前面：

1. **建議換匯額的進位規則**——日幣進位到 1,000 與進位到 100 差三倍體感。
2. **MA30 的「30」是交易日還是自然日**——這是 `runbook` Runbook 04 已知的燈號誤判陷阱。
3. **多幣別行程的建議換匯額**——PRD P1 已上線「多目的地 + 30+ 幣別」，但 P0-4 的算式只描述單一幣別。

## 4. Business Rules（必要規則）

### BR-01 · 建議換匯現金額

```
建議換匯額 = ROUND_UP( Σ(行程中 payment = cash 的預估金額) × 1.1 , 幣別進位單位 )
```

| 項目 | 規則 | 依據 |
|---|---|---|
| 基數 | **僅**計入標記為 `cash` 的項目；`card` 項目不計入 | PRD P0-4「cash_only 總和」 |
| 緩衝 | **× 1.1**（固定 10%） | PRD P0-4 |
| 進位 | JPY → 進位至 **1,000**；KRW → **10,000**；THB → **100**；USD/EUR → **10** | **推導** `[L]`，見 §TODO |
| 顯示 | 須同時顯示：外幣金額、台幣約當、**緩衝說明**（「已含 10% 緩衝」） | PRD P0-4 驗收；`user-research` F4 |
| 邊界 | 若 cash 項目總和為 0 → 顯示「這趟不需要準備現金」，**不顯示 0** | 推導：顯示 0 會讓使用者以為系統壞了 |
| 多幣別 | **每個幣別各自計算並分列**，不合併為單一數字 | 見 §TODO，此為推導非既有規格 |

> **為什麼是 1.1 而不是別的**：canon 未記錄推導過程。`user-research` F1 顯示使用者「寧可多換」，10% 是**保守的單一固定值**。
> 注意這條與 `north-star` C1（誤差率反指標）直接衝突——**調高緩衝會讓使用者更少遇到現金不足，但會讓 KR3 誤差變大**。任何調整必須同時看兩個指標。

### BR-02 · FX 燈號判定

```
偏離% = (今日匯率 − MA30) / MA30 × 100
```

| 燈號 | 條件 | 文字建議 |
|---|---|---|
| **STRONG_BUY** | 偏離% ≤ −2%（台幣相對強勢） | 「目前匯率明顯優於近月平均，可考慮現在換」 |
| **BUY** | −2% < 偏離% ≤ −0.5% | 「略優於近月平均」 |
| **HOLD** | 偏離% > −0.5% | 「與近月平均相當，不急著換」 |

| 規則 | 內容 | 依據 |
|---|---|---|
| **MA30 定義** | **30 個交易日**（非自然日），不足 30 筆時**不顯示燈號** | `runbook` Runbook 04 已知陷阱 |
| **單位一致性** | 所有來源的匯率須正規化為「1 外幣 = N 台幣」再比較 | `runbook` Runbook 04 已知陷阱（per 1 vs per 100） |
| **資料標示** | 資料來源為 cached／模擬時，**必須顯示時戳與來源標籤** | PRD P0-8 驗收；`north-star` C3 |
| **免責** | 燈號區塊必須附「非投資／理財建議」 | 種子簡報 §法規 |
| **降級** | 無可用資料時隱藏整個燈號區塊，**不顯示 HOLD 當作預設** | 推導：預設 HOLD 是無中生有的建議 |

### BR-03 · 三級距

| 規則 | 內容 | 依據 |
|---|---|---|
| 遞增 | Low < Mid < High（總花費） | PRD P0-2 驗收 |
| 預算約束 | 各級距總額 ≤ 該級距預算上限 | PRD P0-2 驗收 |
| 不可退化 | 若三級距算出的總額相同，**不得顯示三張一樣的卡**；改提示「此預算範圍過窄」 | 推導；`persona` 阿哲靠級距落差建立量級認知 |

### BR-04 · 開支對照

| 規則 | 內容 |
|---|---|
| 即時性 | 新增／刪除開支後**即時**更新總額與超支／結餘（PRD P0-7 驗收） |
| 分類 | 開支分現金／刷卡；**只有現金開支**計入「vs 建議換匯額」的準確度比較 |
| 準確度 | `誤差率 = |實際現金 − 建議換匯額| / 建議換匯額`，供 `okr` KR3 使用 |
| 單人 | 不做分帳（PRD §3 非目標） |

### BR-05 · 分析事件

| 事件 | 觸發時機 | 附帶欄位（不含個資） |
|---|---|---|
| `generate` | 方案回傳並**渲染完成** | 目的地國別、天數、幣別、FX 來源類型（live／cached／mock） |
| `tier_select` | 使用者展開任一級距 | tier（low/mid/high） |
| `save_trip` | 寫入 localStorage 成功 | tier |
| `add_expense` | 新增開支成功 | 現金／刷卡 |
| `deal_link_click` | 點擊外部連結 | 連結類別 |
| `return_visit` | 距上次 session > 24h 的開啟 | 距上次天數 |

| 規則 | 內容 |
|---|---|
| 匿名 | 不得送出可識別個資；不得使用跨站識別碼 |
| 非阻塞 | 發送失敗須靜默丟棄，**不得影響 UI**（`srs` D3） |
| 觸發點 | `generate` 綁「渲染完成」而非「按下按鈕」——否則 KR1 會虛高 |

## 10. Decision Log

| # | 決策 | 理由 | 影響 |
|---|---|---|---|
| D1 | **MA30 明確定義為 30 個交易日，不足不顯示** | 避免 Runbook 04 的誤判事故 | 上線後最多 30 個交易日內燈號可能不可用（見 TODO） |
| D2 | **cash 總和為 0 時顯示文案而非數字 0** | 0 會被讀成系統故障 | 新增一條 AC |
| D3 | **多幣別分列不合併** | 合併需要跨幣別換算，會引入第二層匯率誤差 | 影響 UI 版面，需 `wireframe` 配合 |
| D4 | **降級時不預設 HOLD** | 預設值等於憑空給建議，違反 G4 | 對應 `feature-flag` `fx_signal_show` |
| D5 | **`generate` 綁渲染完成** | 保護 KR1 不被虛報 | 寫入 `observability-spec` |
