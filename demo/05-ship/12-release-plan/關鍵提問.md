### 05-ship > 12 Release Plan · 關鍵提問（PO 必問）

> 本場會議 60 分鐘，PO 只要把這 6 題問完、問對，會議就成功了。
> 不要問「我們什麼時候可以上線？」——問題要**逼出每個階段的 Go / abort 數字、通訊責任、回滾邊界**。

---

## Q1.「**我們要分幾階段？每階段的使用者比例是多少？依據什麼？**」

- **為什麼問這個**：一鍵全量上線是 ship 階段最大的反 pattern——4 週的成果 1 小時內可以燒光。
  階段拆分的原則是「**每階段都能獨立 abort 且每階段都餵一條假設驗證**」。階段太少（< 3）= 失控風險高；
  階段太多（> 6）= 4 週驗證窗根本跑不完。
- **好答案長什麼樣**：「3 階段。S1=5%（W1 D1–D3，內部 + 早鳥）驗證『系統沒崩』；S2=25%（W1 D4–W2 D7）驗證『啟用率達 PRD §7 的 40% 門檻』；S3=100%（W3 D1 起）驗證『30 天回訪 ≥ 20%』。每階段對應一條 H 假設。」
- **壞答案長什麼樣**：「先給 50% 看看。」——50% 不上不下，出事影響太大、看數據又不夠快。
- **別人會 push back 什麼**：PM 可能說「行銷活動 W1 就要全量」。回應：「**行銷活動跟 rollout 階段對齊**，不是反過來。行銷活動延到 S3 開始才放，前兩階段是內部 beta 心態。否則 H1 假設驗證會被行銷流量污染——分不出『產品好』還是『行銷投得多』。」

---

## Q2.「**每階段的 Go criteria 是什麼具體數字？回溯到 H1/H2/H3 哪一條？**」

- **為什麼問這個**：Go criteria 沒寫數字 = 沒 criteria。「使用者反應不錯」「沒看到 bug」這種主觀標準，
  上線當天會變成情緒辯論。Go 標準必須是 **(指標, 門檻, 量測窗) 三元組**，且每個門檻都要能回溯到
  02-value-hypothesis 的 H 假設或 09-NFR 的 SLO。
- **好答案長什麼樣**：「S1 → S2 的 Go 條件：(a) 過去 24h 無 P0/P1 incident (b) FX API 錯誤率 < 1% (c) generate flow 完成率 ≥ 95% (d) 燈號顯示成功率 ≥ 99%——對齊 H1『系統能穩定生成建議』與 09-NFR 燈號可用性 SLO。」
- **壞答案長什麼樣**：「看起來 OK 就 Go。」——「看起來 OK」是誰的眼睛？凌晨 3 點誰負責看？
- **別人會 push back 什麼**：DevOps 可能說「指標太多儀表板做不完」。回應：「**那就減指標不是減數字**。
  每階段挑 3–5 個關鍵指標就夠，但每個都要有絕對數字，不是相對描述。」

---

## Q3.「**Abort 信號是什麼？多久內必須觸發 rollback？誰拍板？**」

- **為什麼問這個**：沒寫 abort 條件的 rollout 計畫等於「Go 是按鈕、abort 是許願」。
  Abort 必須有 (a) **自動觸發條件**（譬如 5xx error rate > 5% 持續 5 分鐘 → PagerDuty 自動叫人）
  (b) **人工拍板者**（指定 PO / DevOps lead 二擇一，不是「大家討論」）
  (c) **rollback SLA**（從觸發到完成 < 30 分鐘）。
- **好答案長什麼樣**：「Abort 信號：(a) FX API 錯誤率 > 5% 持續 5 分鐘 → PagerDuty P0 (b) generate flow 完成率 < 80% → P1 (c) 客服 Slack 收到 5 件以上相同性質投訴 → P1。拍板者：PO（主）/ DevOps lead（PO 30 分鐘無回應的代理）。Rollback SLA：觸發到 100% 流量切回上版本 < 30 分鐘。」
- **壞答案長什麼樣**：「有大問題就回滾。」——「大問題」沒定義，凌晨出事誰判斷？
- **別人會 push back 什麼**：PO 自己最常想跳過這題（「abort 應該不會發生」）。
  回應：**「應該不會發生」是 abort 出現時最危險的句子**。寫了不會用沒關係，沒寫到時用不了會死。
  abort criteria 是保險，不是預測。

## Q4.「**Feature flag 的拆分顆粒度是什麼？哪些功能可以獨立 abort？**」

- **為什麼問這個**：如果整個 MVP 只用一個 flag 控，那「FX 燈號出錯」就只能 abort 整個 MVP——
  連啟用率達標的 P0-1 行程生成也一起關掉，浪費資料。Feature flag 顆粒度應該對應「**可獨立 rollback 的功能單位**」——
  通常與 PRD P0 條目對應。
- **好答案長什麼樣**：「3 個獨立 flag：(a) `ff_realtime_fx`（P0-8 即時匯率，可獨立關回模擬） (b) `ff_fx_signal`（P0-5 燈號顯示，可獨立關回不顯示） (c) `ff_analytics`（P0-9 分析事件，可獨立關閉避免 GDPR 風險）。每個 flag 對應 PRD 一個 P0 條目，可獨立 abort。」
- **壞答案長什麼樣**：「一個 flag 控全部，方便管理。」——管理方便 = abort 顆粒度爛。
- **別人會 push back 什麼**：DevOps 可能說「flag 太多狀態組合會爆炸」。回應：「**狀態組合會爆是因為 flag 之間有相依**。
  我們的 3 個 flag 互相獨立——`ff_fx_signal` 關掉 `ff_realtime_fx` 還能用（顯示匯率但不給燈號建議）。
  獨立 flag = 線性狀態，不會爆炸。」

---

## Q5.「**跨團隊通訊計畫是什麼？Go / abort 發生時誰在幾分鐘內通知誰？**」

- **為什麼問這個**：上線出事 80% 是組織協調問題，不是技術問題。客服不知道今天上線 → 使用者投訴沒人能答；
  行銷不知道暫停 → 廣告繼續砸但功能被 abort；法務不知道燈號上線 → 免責聲明文案沒到位。
  通訊計畫要寫 **(事件, 通知者, 接收者, 管道, SLA)** 五元組。
- **好答案長什麼樣**：「Happy path：S1 Go 當天 09:00 PO 在 #ship-smarttrip Slack 公告 + 同步 mail 給客服／行銷／法務 leads；S2 Go 當天 09:00 同上 + 行銷確認 W2 廣告投放可開啟。Abort path：abort 觸發後 PO 5 分鐘內在 #incident-smarttrip 開戰情室 thread + PagerDuty 通知 DevOps；15 分鐘內 PM 通知客服 lead 準備 FAQ 模板；30 分鐘內如未恢復，PO 在 #all-eng 全 ENG 公告。」
- **壞答案長什麼樣**：「有事 Slack 通知。」——通知誰？什麼 channel？多久？
- **別人會 push back 什麼**：PM 可能說「客服訓練要兩週，來不及」。回應：「**那就把 S1 的時間延後**，不是跳過客服訓練。
  上線當天客服沒準備好 = 直接 abort 條件之一，這條寫進 Go criteria。」

## Q6.「**Rollout 視窗禁區是什麼？週五、假日前、月底結算日要不要避開？**」

- **為什麼問這個**：rollout 視窗選錯日子 = 賭命。週五晚上上線 = 週末沒人能修 = 週一炸成新聞；
  假日前上線 = 整個 long weekend 沒人 standby；月底結算日 = DevOps 全在處理財務系統沒空 fight fire。
  視窗禁區要事先寫明，不是上線前才討論。
- **好答案長什麼樣**：「禁區：(a) 週五 14:00 之後到週一 10:00（給週末緩衝） (b) 國定假日前 1 個工作日到假期結束後 1 工作日 (c) 月底最後 2 個工作日（財務系統高峰）。所有 Go 動作必須在週二 ~ 週四 10:00–16:00 觸發，留 2–3 小時觀察窗。」
- **壞答案長什麼樣**：「週五上 反正流量低。」——流量低 ≠ 風險低。修 bug 的工程師才是稀缺資源。
- **別人會 push back 什麼**：行銷可能說「我週五要配合周末廣告」。回應：「**廣告改下週週二**。
  上線當天廣告全停才能驗證自然流量假設。週五壓力 + 週末沒人 = 我不簽。」

## 送命題清單

這 3 題不問，上線當天會出事：

1. **「rollback 過程中使用者資料怎麼辦？」**
   譬如 S2 階段使用者已經存了 100 個 trip 到 localStorage 用新版 schema，rollback 回上版本舊 schema 讀不到——
   資料消失。要事先決定：(a) data migration 雙向兼容（建議） (b) rollback 時通知使用者重整 (c) 接受資料丟失。
   沒決定 → rollback 變成「修了 bug 但燒了使用者信任」。

2. **「驗證窗結束後誰判斷『假設成立』，依據什麼？」**
   4 週跑完不是自動下班。要事先指定：每階段結束 PO 召集 1 場 30 分鐘 review，看數據對齊 H1/H2/H3 哪幾條過、
   哪幾條沒過，決議「進 V1」或「重檢定位」。沒指定 → 4 週後資料躺在儀表板沒人讀，繼續做 V1 = 假驗證。

3. **「監控成本 vs 監控完備性怎麼平衡？」**
   完美的監控很貴（高頻 metrics + APM + RUM + log + trace），但 MVP 階段預算有限。要先列「最低可接受的監控」清單：
   譬如 generate flow 完成率、FX API 錯誤率、JS error rate、3 個 P0 functional probe——這 6 個是 must，
   其他 nice-to-have 等 V1。沒列清單 → 不是監控太貴就是監控太少，兩種都會死。
