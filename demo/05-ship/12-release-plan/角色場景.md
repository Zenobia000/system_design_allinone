# 12 Release Plan · 角色場景

## 這場會議在做什麼

MVP 三個 sprint 跑完、unit test 策略對齊、NFR 燈號全綠、value hypothesis 的成功指標也寫死了。
但「程式 deploy 上去」≠「功能對使用者放行」。
本場會議**不是排 deploy schedule 的會議、不是討論 CI/CD pipeline 的會議、不是寫 runbook 的會議**。
目的只有一個：**訂出本次 MVP 的 feature flag 拆分 + 分階段 rollout 排程 + 每個階段的 Go / No-Go 數字 + abort 信號 + 通訊計畫**。

跑完本場，全公司都知道：
- 哪一天放給 5% 使用者、什麼條件達到才往 25%、什麼條件達到才放 100%
- 出事時誰按下 abort、abort 條件具體是什麼數字
- 每階段誰負責看儀表板、誰負責通知使用者、誰負責跟客服對齊

## 誰在場

| 角色 | 帶來什麼 | 想拿走什麼 |
|---|---|---|
| **PO（主責，你）** | 02-value-hypothesis 的 H1/H2/H3、種子簡報「4 週驗證窗」與「成功指標」、商業優先序 | 分階段排程 + 每階段 Go / abort criteria + 通訊計畫 |
| **DevOps** | feature flag 系統能力（拆分顆粒度、目標族群定義、即時切換 SLA）、observability 儀表板 | 確認 abort 信號可監控、Go criteria 可量測 |
| **PM** | 跨團隊溝通需求（行銷活動、客服訓練、法務最後一哩）、過去 MVP 上線踩雷紀錄 | 確認排程跟行銷 / 客服 / 法務協同沒有衝突 |

## 你扮演的角色（PO）

你是「**不允許「一鍵全量上線」的人**」。本場會議你要做三件事：

1. 對每個階段問「**這階段的 Go 標準是什麼數字？依據哪條 H 假設？**」——沒數字、沒依據的階段不存在
2. 對每個階段問「**abort 信號是什麼？多久內要觸發 rollback？**」——沒 abort 信號的階段叫「許願」不叫 rollout
3. 對通訊計畫問「**Go / abort 發生時，誰在幾分鐘內通知誰？用什麼管道？**」——「會在 Slack 通知」不算通訊計畫

**禁忌動作**：本場會議**禁止**講這幾種話，講了就要重來：

- ❌「**先全部放出去看看反應**」——你只有 4 週驗證窗，全量出事直接燒掉整個 MVP
- ❌「**Go criteria 我們之後再定**」——之後就是「沒人敢按 Go 也沒人敢按 abort」的 paralysis
- ❌「**有事再通知**」——通訊計畫要事先寫，包含 happy path 與 abort path 兩條 timeline
- ❌「**週五晚上上吧反正流量低**」——週五晚上上 = 週末沒人能修 = 週一炸成新聞

## 會議結束時，桌上要有什麼

- **≥ 3 個 rollout 階段**，每階段含：
  - **日期窗**（譬如「W1 D1–D3」）
  - **使用者比例**（譬如 5% → 25% → 100%）
  - **Feature flag 名稱與目標族群定義**
  - **Go criteria**（具體數字，回溯到 H1/H2/H3 與 09-NFR SLO）
  - **Abort criteria**（具體數字 + 觸發 rollback 的 SLA）
  - **通訊計畫**（誰在幾分鐘內通知誰、用什麼管道、有 happy path 與 abort path）
- **Rollout 視窗禁區清單**（譬如「禁止週五 18:00 之後、禁止國定假日前一天」）
- **Feature flag 顆粒度地圖**（哪個 flag 控哪個功能，可獨立 abort 嗎）
- 給 13-rollback-plan 的「**rollback decision tree 入口**」（從 abort criteria 觸發到完整 rollback 流程）

## 為什麼這場會議重要

Release plan 是 **ship 階段的剎車系統**。沒有對齊的計畫，會出現三種慘案：

1. **一鍵全量**：把 4 週的成果 1 小時內燒光。FX API 流量爆 10 倍打死配額、bug 影響 100% 使用者、回不去
2. **沒有 abort 信號**：上線後出狀況「要不要 rollback」變成情緒辯論，DevOps 看 PO 臉色、PO 看 PM 臉色，沒人敢拍板
3. **通訊計畫空談**：上線當天客服信箱炸了，客服才知道「啊我們今天上新功能喔？」——使用者跑去 PTT 罵，公關危機

下游每張卡都依賴這份計畫：

- **13-rollback-plan**：abort 觸發後的具體流程，入口就是本場定的 abort criteria
- **14-monitoring-runbook**：每階段 abort criteria 直接變成 alert 規則
- **15-postmortem**：事故後回頭看「abort 信號有沒有觸發？觸發後流程跑對嗎？」

**跳過這場會議的代價**：MVP 上線當天 = 自由心證日，每個人對「Go / abort」有自己一套標準。
出事時不是技術問題，是**組織協調問題**——而組織協調出事，沒有任何 rollback 能救。
Release plan 不是繁文縟節，是**驗證窗能不能跑完的前提**。

## 本場示範主題

**SmartTrip FX MVP 4 週驗證窗 Rollout 計畫**

- **為什麼選這題示範**：種子簡報明示「4 週 MVP 驗證窗之後才決定要不要繼續做 V1」。
  這 4 週每一週都是錢、每一週都是團隊精力——不能用「全量上線 4 週後再看」的方式燒，
  必須拆 stage、每 stage 都能 abort、每 stage 都餵 H1/H2/H3 假設驗證。
- **教學意義**：學員會學到「rollout 階段不是『百分比遞增』那麼簡單」——每個百分比階段背後是
  一條假設的驗證機會。5% 階段驗證「**功能沒崩**」、25% 階段驗證「**啟用率達標**」、
  100% 階段驗證「**留存與差異化認知**」。階段與假設一一對應，缺一不可。
