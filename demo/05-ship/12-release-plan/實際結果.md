## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 `decision_maker` 寫「我自己」而非 TODO？

個人專案誠實寫『單人 maintainer』比假裝一個跨團隊組織更好。
重點是 **go/no-go 必須有人負責決策**，不能寫「待定」。
工作坊學生若是個人專案 → 寫自己；公司專案 → 寫 PO + Eng Lead 雙簽。
**錯誤示範**：`decision_maker: TODO` —— 等於沒人扛責任。

### 2. `go_criteria` vs `success_criteria` vs `abort_criteria` 三者差異

| 階段 | criteria 名稱 | 時機 | 範例 |
|---|---|---|---|
| 上線**前** | `go_criteria` | T-1h 決定按不按 | unit test 全綠 / staging 試打成功 |
| 上線**後**判定成功 | `success_criteria` | T+24h ~ T+7d | 24h 內 0 個 P0 incident |
| 上線**後**判定失敗 | `abort_criteria` | T+30min ~ T+1h | API 失敗率 > 50% → 觸發 rollback |

學生常把三者混在一起寫成「成功標準」，下游 SRE 不知道何時看哪一條。

### 3. 為什麼 `abort_criteria` 必須引用 `rollback-plan` 的 TRIGGER 編號？

`abort_criteria` 不能只寫「失敗率高就 rollback」—— 要明示**用 rollback-plan 的哪個 trigger**。
這樣下游 oncall 不需要重新判斷，照 rollback-plan 的 SOP 執行即可。
這是 release plan 與 rollback plan 的 **單向 trace link**。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `abort_criteria` | `13-rollback-plan/` 的 `triggers` 必須對得起來 |
| `risk_summary.unknowns` | `14-runbook/` 的「FX API down」處理流程 |
| `post_release_metrics.business_kpi_watch` | `14-runbook/` 的 dashboard 連結 |
| `self_review.fabricated_assumptions` 第 2 條（法規） | 退回 `03-prd/` Open Question 法務 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| `go_criteria` 寫「測試通過」 | 規則 8 | 明示哪幾個 case、coverage 門檻數字、grep-able 條件 |
| `abort_criteria` 寫「出問題就 rollback」 | 規則 8 | 明示「失敗率 > X% 連續 Y 分鐘」與對應 trigger 編號 |
| `comms_plan` 只寫 internal，漏 external / support | 規則 7 | 三層都要寫，沒人時誠實寫 TODO(填上 oncall) |
| `decision_maker` 留空或寫「團隊」 | 規則 4 + 8 | 寫具體 role 或人名；個人專案寫「我自己」 |
| `risk_summary.unknowns` 寫成空陣列 | 規則 1 + 6 | 至少 3 條真實 unknown；沒 baseline 數字就誠實寫「無歷史資料」 |
| `out_of_scope` 寫成空陣列 | 規則 5 | 至少 3 條：不寫詳細指令、不重校 SLO、不寫行銷文案 |

## 交件 checklist

- [ ] `release_id.version` 用 SemVer，`target_date` 含時區
- [ ] `go_no_go.decision_maker` 是具體角色/人，不是「團隊」或「待定」
- [ ] `go_criteria` 至少 3 條可機械驗證（不是「測試通過」這種模糊句）
- [ ] `abort_criteria` 引用 `13-rollback-plan` 的 trigger 編號
- [ ] `comms_plan` internal / external / support 三層都有內容（無人時寫 TODO 而非省略）
- [ ] `rollback_link` 指向實際的 rollback plan（不是 TODO）
- [ ] `out_of_scope` 至少 3 條
- [ ] `decision_log` 至少一條（如：為何全量而非灰度）
