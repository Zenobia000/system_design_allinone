## 教學要點（看完 AI 輸出後讀這段）

### 1. 為什麼 STEP-1 同時提供「CLI 方法 A」與「UI 方法 B」？

凌晨 3 點 oncall 可能：
- 找不到 `$VERCEL_TOKEN` → 方法 A fail
- Vercel CLI 沒裝 → 方法 A fail
- 但 UI 永遠可以從手機開 → 方法 B 永遠保底

**錯誤示範**：只寫「`vercel rollback`」—— 一旦 token 過期、CLI 沒裝就卡住。
**正確做法**：每個 step 提供至少一條 fallback，凌晨 3 點不思考也能走完。

### 2. `irreversible_points` 為什麼必須寫補救方案？

PR #45 是 forward-only migration（V0 → V1），rollback 後 v0.1 讀不到 V1 schema。
如果只標 `irreversible: true` 不寫補救，下次 rollback 真的發生時，oncall 會：
- ❌ 清掉 localStorage（以為這樣可以「回到乾淨狀態」）→ **真的把使用者資料弄丟**
- ✅ 看到「不要在 rollback 時清掉 localStorage」這條警告 → 保住資料

這就是「在 incident 發生前先決定」的價值。

### 3. `manual` vs `auto` rollback：trade-off 必須誠實

學生常想寫「auto rollback 比較專業」—— 但 auto 需要：
- 可信任的 SLI（延遲 < 1 分鐘）
- alert pipeline + decision engine
- 確認 false-positive rate < X%

個人 MVP 階段這些都沒有。`decision_log` 必須誠實寫「現階段條件不滿足，先 manual」，並標明何時升級到 auto。

### 4. 這張卡的輸出流向下游哪些卡

| 本卡欄位 | 流向哪張卡 |
|---|---|
| `triggers` | `14-runbook/` 同名告警處理流程 |
| `rollback_steps` 的具體指令 | `14-runbook/` 的 remediation_steps |
| `data_compat_strategy.irreversible_points` | `15-postmortem/`（若 rollback 真的發生）的 action_items 補洞清單 |
| `self_review.highest_value_next_input`（演練） | 上線前一天的 rehearsal 工作項 |

## 學生常見錯誤（交件前自己對照）

| 錯誤 | 違反規則 | 怎麼修 |
|---|---|---|
| `rollback_steps` 寫「revert deploy」 | 規則 8 | 寫具體指令 `vercel rollback` + UI 路徑 |
| `irreversible_points` 只標旗號不寫補救 | 規則 4 | 每個不可逆點必須附「補救方案」段落 |
| `comms_plan.decision_maker` 留空 | 規則 4 | 寫具體角色；個人專案寫「我自己」 |
| `triggers` 引用的編號跟 release-plan 對不上 | 規則 1 | 跟 `12-release-plan` 的 `abort_criteria` 編號（TRIGGER-1/2/3）完全一致 |
| 沒有 `verification` 欄位 | 規則 7 + 8 | 每個 step 必須有「如何確認此步成功」的 grep-able 指令 |
| `mttr_target` 沒寫或寫「越快越好」 | 規則 6 | 寫具體分鐘數，個人專案 15 分鐘是合理上限 |
| `out_of_scope` 寫成空陣列 | 規則 5 | 至少 3 條：不做 DR drill、不做 circuit breaker、不做法務通報 |
