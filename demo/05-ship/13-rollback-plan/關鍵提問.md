# 13 Rollback Plan · 關鍵提問（DevOps 必問）

> 本場會議 45 分鐘，DevOps 只要把這 6 題問完、問對，會議就成功了。
> 每題的目標：**逼出一條可執行的 rollback path，或把這條變更打回 12-release-plan**。
> 不要問「rollback 計畫做了嗎？」這種開放題——要問「**第 17 分鐘 p95 飆到 250ms 時，誰按按鈕？按哪個按鈕？按下去之後使用者看到什麼？**」

---

## Q1. 「什麼信號觸發 rollback？自動還是人工？閾值是多少？」

- **為什麼問這個**：rollback 最常見的失敗模式不是「按了不能用」，而是「**沒人敢按**」。
  沒有明確的 trigger 信號 + 閾值，凌晨 3 點被 page 的人會猶豫「這是要 rollback 還是再觀察 10 分鐘？」，
  10 分鐘變 30 分鐘，30 分鐘變 SLO breach。trigger 信號必須在 release 前就**寫死數字**。
- **好答案長什麼樣**：「p95 generate 延遲 > 180s 連續 5 分鐘 → auto rollback；
  FX rate API 5xx error rate > 10% 連續 3 分鐘 → page on-call，人工判斷 5 分鐘內決策；
  使用者回報『建議現金額異常』≥ 3 件 / 30 分鐘 → 強制 rollback。」（具體指標 + 閾值 + 時間窗 + 動作）
- **壞答案長什麼樣**：「看 log 判斷」「異常就 rollback」——沒指標、沒閾值、沒時間窗。
- **別人會 push back 什麼**：Dev 會說「閾值太敏感會誤觸發」。
  回應：「**寧可誤觸發 rollback，不要漏觸發**。誤觸發的成本是 5 分鐘使用者體驗倒退；漏觸發的成本是 6 小時 1,200 個使用者帶錯錢。閾值寫鬆，但寫了，寫一個就是一個。」

---

## Q2. 「這個 rollback 步驟可逆嗎？資料 schema 怎麼處理？」

- **為什麼問這個**：rollback 最被忽略的層面是**資料相容性**。
  Code rollback 5 秒鐘的事，但若新 code 寫了舊 code 讀不懂的欄位（schema migration、序列化格式變更），rollback 之後使用者看到的就是「**白屏、JSON parse error、行程不見**」。
  資料變更必須走 **dual-write / feature flag / backfill / 不可逆+補償** 四選一，沒選 → 不准上。
- **好答案長什麼樣**：「schema v2 新增欄位 `cash_buffer_pct`，v1 code 讀不到會 fallback default 0.1。
  寫入採 dual-write 2 週，rollback 期間 v1 code 寫入 localStorage 仍會被 v2 code 讀懂。
  feature flag `enable_v2_schema` 預設 off，灰度開啟。」（明確策略 + 灰度週期 + fallback 行為）
- **壞答案長什麼樣**：「應該相容吧」「rollback 就好，反正 localStorage 在 client 端」——
  client 端的 localStorage 一旦寫入 v2 格式，使用者把 PWA 降級回 v1 也讀不回去，等同資料消失。
- **別人會 push back 什麼**：Dev 會說「dual-write 開發成本太高」。
  回應：「**dual-write 成本 = 開發 2 天；不做的成本 = 1,200 個使用者行程消失 + 客服爆炸 + postmortem 3 天**。算一下。」

---

## Q3. 「rollback 完成後使用者體驗會降到哪？這個降級可接受嗎？」

- **為什麼問這個**：rollback 不是「回到沒事發生的狀態」，而是「**回到上一個已知穩定但功能較少的狀態**」。
  PO 必須親口說「這個降級的使用者體驗，我接受」，不接受 → rollback 不能按 → 等同沒有 rollback。
  尤其要釐清：**rollback 後既有使用者會被踢去哪？** PWA 卡在新版怎麼辦？
- **好答案長什麼樣**：「FX provider 從台銀 rollback 回 Wise → 燈號計算延遲從 3s 升回 8s，可接受。
  PWA service worker rollback → 使用者下次開啟 PWA 會看到一次 reload，已存行程仍可讀，可接受。
  使用者影響說明：status page + in-app banner 顯示『匯率資料來源切換中，部分行程燈號可能延遲更新』。」
- **壞答案長什麼樣**：「rollback 後就跟之前一樣」——99% 不是。至少有快取、session、PWA 版本差異。
- **別人會 push back 什麼**：PO 會說「能不能 rollback 不影響使用者？」
  回應：「**rollback = 用使用者體驗降級換取使用者體驗止血**。一定有降級，不接受降級就是不接受 rollback。**那就要 forward fix，但 forward fix 平均 2 小時，rollback 平均 5 分鐘**，你選哪個。」

---

## Q4. 「rollback 的通訊鏈條是什麼？誰通知誰？對外文案誰寫？」

- **為什麼問這個**：rollback 的技術動作 5 分鐘，但**通訊延遲常常變成事故的主要影響**。
  客服沒拿到 talking points → 使用者問了答不出來 → 客訴升級；status page 沒人更新 → 推特開始炎上；PO 沒被通知 → 老闆從新聞看到事故。
  通訊鏈條必須在 rollback 演練時一起跑過。
- **好答案長什麼樣**：「on-call → 5 分鐘內 page PO + 客服主管 → PO 15 分鐘內發 status page（樣板已備）→ 客服拿 FAQ v3（如下）回覆 → 滿 30 分鐘未解決升級 CTO → 滿 2 小時通知所有使用者 in-app banner。」（明確角色 + 時限 + 樣板存放位置）
- **壞答案長什麼樣**：「Slack 上 ping 一下大家」——沒角色、沒時限、沒文案。
- **別人會 push back 什麼**：PO 會說「我隨時可以發 status page」。
  回應：「**事故當下沒人寫得出冷靜的對外文案**。樣板要在沒事的時候寫好，事故時填空就發。現在就寫。」

---

## Q5. 「這條 rollback path 上次實際演練是什麼時候？演練紀錄在哪？」

- **為什麼問這個**：**沒演練過的 rollback 不是 rollback，是希望**。
  Rollback 步驟寫在 wiki 上看起來都很順，實際按下去才發現：權限沒給、CLI 工具沒裝、舊 docker image 已被 GC、feature flag 控制台需要 SSO、外部 API 的 contact 已離職。
  每一條 rollback path 都必須有「演練時戳 + 執行人 + 發現的問題」三件套，沒有 → 當場排演練。
- **好答案長什麼樣**：「FX provider rollback：2026-04-12 game day 演練，DevOps Alice 執行，
  發現 Wise API key 在 vault 過期 → 已修；演練耗時 8 分鐘（目標 < 10 分鐘 達成）。
  下次演練 2026-07 quarter game day。」
- **壞答案長什麼樣**：「之前演練過」（沒日期）／「應該 work」（沒執行人）／「文件寫了」（沒實際跑）。
- **別人會 push back 什麼**：Dev 會說「演練很花時間」。
  回應：「演練 1 小時，事故 6 小時。**rollback 演練不是 nice-to-have，是 release 的閘門**。沒演練就不准上。」

## Q6. 「這個變更如果根本不可 rollback，補償方案是什麼？」

- **為什麼問這個**：不是所有變更都可 rollback。**真正不可逆的變更**（譬如：localStorage 寫入新欄位且舊版讀不懂、外部 API 整合的 webhook 已註冊、發信／推播已送出）必須走 **forward fix + 補償** 而不是 rollback。
  混淆「不可 rollback」與「rollback 還沒寫」是 SmartTrip MVP 階段最容易踩的坑。
- **好答案長什麼樣**：「**localStorage v2 寫入後降版** 屬不可 rollback。補償方案：
  (a) PWA 啟動時偵測 schema 版本，v2 → v1 自動執行 down-migration script，
  (b) down-migration 失敗則顯示 modal『請點此重置本地資料』+ in-app 教學如何 export 行程 PDF。
  預估復原時間：使用者點選 modal 後 30 秒內可重新使用。」
- **壞答案長什麼樣**：「不可 rollback 就不要 rollback 啊」——那這條變更就**不能上 release**，直到補償方案寫完並演練。
- **別人會 push back 什麼**：PO 會說「補償方案做完功能就拖了一個 sprint」。
  回應：「**沒補償方案就上線 = 把不可逆變更的風險轉嫁給使用者**。要嘛縮小變更範圍讓它可逆，要嘛寫補償，二選一，沒有第三條路。」

## 送命題清單

這 3 題不問，3 個月後 14-runbook 的 on-call 工程師會回來找你算帳：

1. **「rollback 後我們會丟失什麼資料？這份資料對使用者意味著什麼？」**
   譬如 PWA service worker rollback 會把使用者「未同步至 localStorage 的最新 1 筆開支」吃掉。「丟 1 筆」聽起來小，但對使用者意味著「明天行程預算對不上」。不問，使用者體驗的降級會被低估。

2. **「rollback 演練的 game day 排在 release 前還是 release 後？」**
   排 release 後 = 沒演練過就上線，等於賭博。**演練必須在 release 前 1 週內跑完**，這樣演練發現的問題還來得及修。寫進 12-release-plan 的 timeline。

3. **「rollback 的執行權限是誰？這個人下班 / 在飛機上 / 離職怎麼辦？」**
   單點失敗。**至少 2 人有 rollback 執行權限**，且權限矩陣寫進 14-runbook。SmartTrip MVP 階段團隊小，但 DevOps 一個人請假就 release 開天窗，這是基本 bus factor。
